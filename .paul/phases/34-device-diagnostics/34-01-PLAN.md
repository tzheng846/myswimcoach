<objective>
## Goal
Give the coach an on-phone "Device Diagnostics" screen that shows, live, why a
recording fails — so "no recording found" stops being a black box. It surfaces
three things the firmware already knows but currently only logs over USB serial:
(1) AS5600 magnet / wiring health, (2) recording & buffer state, (3) BLE link
health. Built on a new firmware `STATUS` BLE command + a new iOS screen.

## Purpose
The user just hit the real failure: the LED flashed the 10 Hz error pattern then
returned to idle solid, and the app reported "no recording found." That is the
magnet-not-detected refusal path in `startRecording()` (ESP_32_V5.ino:274) — the
firmware will not record unless `readMagnetOk()` passes, and it logs the cause to
serial, which is invisible at poolside. The product thesis is "no laptop at
poolside" (PROJECT.md), so the diagnostic must live on the phone. Today the user
cannot tell a wiring fault from a misaligned magnet from a dead BLE link.

## Output
- Firmware: `STATUS` command returning a 15-byte live-status packet (this repo).
- iOS: `DiagnosticsScreen.js` (new) + a "Diagnostics" entry on `DevicesScreen`,
  registered in the nav stack (separate `swimnetics-mobile` repo).
- A device checkpoint validating it against the real magnet/wiring/record states.
</objective>

## Grounding facts (verified this session)
- The firmware already refuses to record when the magnet is not cleanly detected
  (MD set, ML/MH clear). That refusal = 10 Hz blink for ERROR_DISPLAY_MS (2 s) →
  back to solid idle. Empty buffer → META reports no session → app: "no recording
  found." This screen makes that cause visible BEFORE the swim.
- TX-notify packet demux is BY LENGTH today (RecordScreen.js:288/320):
  META = exactly 8 bytes, end-of-dump marker = exactly 1 byte (0xEE),
  samples = any multiple of 7. The STATUS packet MUST avoid all three.
- iOS BLE: useBle() exposes `connectedDevice`; commands go out via
  `writeCharacteristicWithResponseForService(SERVICE_UUID, RX_UUID, base64("CMD\n"))`
  (firmware does `val.trim()`, so the trailing \n is fine); notifications arrive via
  `monitorCharacteristicForService(SERVICE_UUID, TX_UUID, cb)` → `Buffer.from(value,'base64')`.
- AS5600 registers: STATUS 0x0B (bits MD=1<<5, ML=1<<4, MH=1<<3), RAWANGLE 0x0C,
  AGC 0x1A. `readAngle()` + `readMagnetStatus()` already exist; AGC needs a helper.

<acceptance_criteria>

## AC-1: Firmware answers a live STATUS query
```gherkin
Given the device is BLE-connected and idle
When the app writes "STATUS" to the RX characteristic
Then the firmware notifies a single 15-byte packet on TX whose layout is:
     [0]    0xDD  (status marker — distinct from 0xEE end marker)
     [1]    raw AS5600 status register (0x0B)
     [2]    magnet_ok (0/1, same logic as readMagnetOk)
     [3]    AGC register (0x1A)
     [4..5] raw angle uint16 LE (0x0C, 12-bit)
     [6]    flags bitfield: bit0=recording, bit1=dataReady, bit2=motorRunning
     [7..10]  bufCount  uint32 LE
     [11..14] maxSamples uint32 LE
And 15 is not 8, not 1, and not a multiple of 7, so existing sample/META/end
     parsers ignore it and are unaffected.
```

## AC-2: Magnet / wiring health is legible on-phone
```gherkin
Given the Diagnostics screen is open on a connected device
When STATUS packets arrive (~2 Hz)
Then the screen shows one of: "Magnet detected ✓" / "NOT DETECTED — check AS5600
     wiring (SDA→21, SCL→22) and that a magnet is on the shaft" /
     "Too weak — magnet too far from sensor" (ML) / "Too strong — magnet too close" (MH),
     derived from the status byte
And it shows the live raw angle with the hint "spin the wheel — this number should
     change"; if it never changes while spinning, that points at the encoder/wiring.
And it shows the AGC value (out-of-range AGC = magnet gap too large/small).
```

## AC-3: Recording / buffer state explains "no recording found"
```gherkin
Given the Diagnostics screen is open
When the user short-presses the device button to record, then stops
Then the screen reflects recording=ON with a climbing buffer count during the swim,
     and after stop shows dataReady=YES with the buffered sample count and capacity
     (e.g. "1843 / 11070 samples"), so an empty buffer is visibly distinct from a
     refused start.
```

## AC-4: BLE link health is shown
```gherkin
Given the Diagnostics screen is open
Then it shows connection state (connected device name), and a "last status received"
     freshness indicator (timestamp/age) so a silent/dropped link is distinguishable
     from a magnet fault.
```
