<objective>
## Goal
Make individual **underwater downkicks** visible on the Underwater inset: one alternating
blue/purple band per kick over the neutral-grey base, boundary ticks, an amber halo on the
interval-outlier kick, a `N kicks · auto` badge, and a per-band hover readout — reusing 83-01's
`buildBands` and `PhaseVelocity` **unmodified**.

Unlike 83-01 this half needs **backend**: `detect_underwater_kicks` returns peak indices only,
computed on the fly and never persisted, so the browser cannot see them. This plan derives band
edges trough-to-trough, persists them, and renders them.

## Purpose
Closes Phase 83. The seven underwater kick metrics (75-03) are all computed from kick peaks the
chart has never drawn — so `kick_count`, `kick_tempo` and `kick_consistency` are unauditable by
eye, exactly the gap 83-01 closed for stroke cycles. This is also the surface that makes the
75-03 over-detection cases (`udk` alternating peaks, shallow-freestyle ripple) visible instead of
theoretical.

## Output
- New pure `metrics.segment_kick_bands` (trough-to-trough, no new tuning constants)
- Kick bands persisted so `/process`, `POST /recompute`, `PUT /annotations` and the backfill all
  populate them (exact location = Task 1's decision)
- `SCHEMA_VERSION` 3 → 4
- Underwater inset banded in `PhaseReportCard`; breaststroke stays single-colour
- One shared backfill run over the stored library
</objective>

<task type="auto">
  <name>Task 2: Pure trough-to-trough kick band segmentation</name>
  <files>metrics.py, tests/test_phase_metrics.py</files>
  <action>
    Add `segment_kick_bands(vel, peaks, i0, i1)` to `metrics.py`, beside the underwater-kick
    detector so the two read together. Pure, never raises, returns a list of plain dicts:
    `[{"kick_num": n, "peak_idx": p, "start_idx": a, "end_idx": b, "duration_s": d}]`.

    - `kick_num` is **0-based** at append time, matching `cycles` (`metrics.py:131`), because
      83-01's `buildBands` reads `cycle_num + 1` to get its 1-based `n`.
    - Require **≥2 peaks**. With 0 or 1 there is no interior trough, and CONTEXT R2 is explicit
      that this must yield NO bands rather than one band spanning the whole window.
    - Split point between consecutive peaks `p[k]` and `p[k+1]` = `i0 + argmin` of the velocity
      slice between them — plain argmin, **no new tuning constant** (D4). This is the same rule
      `segment_cycles_trough` uses for stroke cycles, minus its prominence gate, which is
      unnecessary here because the peaks are already prominence-filtered by the detector.
    - First band starts at `i0`, last band ends at `i1` (clamped to the window, D4).
    - `duration_s` = `(end_idx - start_idx) / fs`. Take `fs` as an argument rather than
      recomputing it. Emitting `duration_s` (not `interval_s`) is deliberate: `buildBands` then
      works with its **default** `durationKey`, so 83-01's lib is reused with zero configuration.
      Band span is trough-to-trough, which is D7's inter-kick interval measured at the troughs.
    - Every emitted number must be a plain Python `int`/`float`, never `np.int64` — `_clean` is
      applied by callers, not by `compute_phases`, and a numpy int reaching `json` raises.
    - Guard: non-finite velocities in the slice, `i1 <= i0`, peaks outside `[i0, i1)`, and
      unsorted peaks must all degrade to `[]` rather than raise.

    Add tests to `tests/test_phase_metrics.py` (the existing home of the kick tests): a synthetic
    5-kick sine → 5 bands meeting at the minima with the peak inside each; 0 peaks → `[]`;
    1 peak → `[]`; peaks outside the window → `[]`; first/last edges equal `i0`/`i1`; and an
    assertion that every value is a plain int/float (`type(v) is int`), which is the check that
    would have caught a numpy leak.

    Avoid: re-running `find_peaks` here (the caller already has the peaks), and adding any
    threshold — the whole point of D4 is that this step introduces no tunables.
  </action>
