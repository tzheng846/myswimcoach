<objective>
## Goal
Harden the three core iOS flows — **pairing, recording, checking session results** — so each
either recovers automatically or fails gracefully with a *specific, actionable reason* (never a
silent hang or a dead-end). No session data is ever lost.

## Purpose
These are the flows a coach touches every session at the pool, with no laptop and no logs. A
silent connect-hang, an un-surfaced mid-record disconnect, or a stranded upload each look like
"the product is broken." Specific, recoverable failure states are the difference between a usable
demo and a lost session.

## Output
Three flows hardened (pairing/recording/results), two small shared helpers, device checks
appended to the mobile TEST-PLAN. Mobile-repo-only; export-green gate.
</objective>

## Decisions locked (user, 2026-06-22, AskUserQuestion ×4)
- **Recovery style:** auto-recover first; surface a message *only* when recovery fails, and make
  it name the actual cause.
- **Upload failsafe:** keep the saved CSV + a Retry button + a clear offline/server-unreachable
  message. NO background queue this pass (the full PROJECT.md queue is a later effort).
- **Pre-flight guards (3 of 4 chosen):** (a) Bluetooth-off / permission detection before
  scan+connect; (b) connect timeout + one auto-retry (kill the infinite spinner); (c) pre-record
  encoder/magnet health check via the Diagnostics STATUS packet. **NOT chosen:** explicit network
  reachability pre-check before upload (handled instead by mapping the upload failure to a clear
  offline reason).
- **Mid-record BLE drop:** detect it → tell the user the data is safe on the device (buffer-and-
  dump) → guide them to reconnect + retrieve. NOT silent auto-reconnect.

<acceptance_criteria>

## AC-1: Pairing fails specifically, never hangs
```gherkin
Given a coach taps "Pair New Device" or connects to a known device
When Bluetooth is off or permission is denied
Then a specific message is shown ("Bluetooth is off — turn it on in Control Center" / "Bluetooth permission is denied — enable it in Settings"), not a silent no-op
And when a connect attempt stalls, it times out and auto-retries once, then shows a clear "Couldn't connect" reason instead of an indefinite spinner
And when a scan finds nothing in its window, the user is told "No SwimLogger found" rather than left guessing
```

## AC-2: Recording guards the start and surfaces mid-record drops
```gherkin
Given a coach starts a recording
When the encoder magnet/sensor is unhealthy (STATUS says not-detected / wiring fault)
Then a specific warning names the cause and offers Record-anyway vs Cancel (does not hard-block on a possible false negative)
And when the device is not connected at plain "Start Recording", it is caught with a clear reason (parity with the video path)
When the BLE link drops mid-recording
Then the elapsed timer stops, a banner explains the link dropped BUT the device is still recording and the data is safe, and the user is guided to reconnect and retrieve
```

## AC-3: A failed upload never strands a session
```gherkin
Given a recording was saved locally and the upload to /process fails
When the failure is a network/offline condition vs a server error vs a bad response
Then the message names which one (e.g. "You appear to be offline", "Server error (500)", "Couldn't read the server response")
And a Retry button re-uploads the already-saved CSV (no re-record, no data loss)
And retry succeeds once connectivity returns, transitioning to the results view
```

## AC-4: Report-card load failures are specific and retryable
```gherkin
Given a coach opens a saved session's report card
When the load fails
Then the reason distinguishes offline/network from "session not found" from "data looks corrupt"
And a Retry button re-attempts the fetch
```
