<objective>
## Goal
Build the demo-data seeder's foundation and land **Stage 1**: a dedicated demo coach
account populated with 12 fictional athletes, each carrying ONE real archetype session
ingested through the production signal pipeline — the sessions the user will hand-annotate
in 50-02.

## Purpose
The demo can't show off long-term athlete tracking because no long-term history exists.
This plan builds the machinery (CSV → pipeline → backdated session row) and seeds the
real, annotatable base layer. 50-02 perturbs these archetypes into ~144 sessions and
propagates their annotations.

Ties to PROJECT.md core value — "objective biomechanical data on every swimmer" is
unsellable in a demo with empty trend charts.

## Output
- NEW `seed_demo_team.py` — config-driven, re-runnable seeder (`--validate` / `--stage1` /
  `--wipe` / `--dry-run`)
- `requirements-dev.txt` gains `python-dotenv` (already an undeclared dep of
  `fetch_sessions.py` / `fetch_annotations.py`; the seeder makes three)
- 12 `athletes` rows + 12 `sessions` rows in a demo team, visible in the web portal
</objective>

<acceptance_criteria>

## AC-1: Ingested sessions are shape-identical to /process output
```gherkin
Given a valid raw encoder CSV in raw/
When the seeder ingests it for a demo athlete
Then a sessions row is created whose metrics_json contains the same four keys
     /process writes (session, cycles, initial_phase, data_quality),
     with velocity_profile and distance_profile arrays of equal length,
     and the web portal renders its report card with no missing-data errors
```

## AC-2: Timeline is controlled by created_at, not insert order
```gherkin
Given the seeder inserts a session with an explicit backdated created_at
When the session list is queried the way the portal queries it (order by created_at)
Then the session sorts by its backdated date, not by when the row was written
```

## AC-3: Unusable archetype CSVs are rejected before they reach the DB
```gherkin
Given raw/ contains short, truncated, or malformed CSVs alongside good ones
When the seeder runs its validation pass
Then each candidate is reported PASS or FAIL with a reason,
     and only PASS files are eligible as archetypes
```

## AC-4: Demo data is fully reversible
```gherkin
Given a seeded demo team
When the seeder runs with --wipe
Then all demo athletes, their sessions, their annotations, and their
     raw-csvs storage objects are removed, and the coach + team rows survive
     so re-seeding needs no new signup
```

## AC-5: The real team is never touched
```gherkin
Given the seeder is pointed at the demo coach's email
When any write executes (including --wipe)
Then every write is scoped to that coach's team_id,
     and a --dry-run prints the intended writes without executing them
```

## AC-6: Stage 1 is visible in the portal
```gherkin
Given the demo coach account exists and Stage 1 has run
When the user logs into the web portal as the demo coach
Then 12 athletes appear on the roster and each has exactly one session
     openable as a report card
```

  <name>Task 1: Build the seeder core — client, config block, ingest, wipe</name>
  <files>seed_demo_team.py, requirements-dev.txt</files>
  <action>
    Create `seed_demo_team.py` at repo root, following the `fetch_sessions.py` pattern.

    **Mandatory boilerplate (copy the pattern, it exists for a reason):**
    - `sys.path = [p for p in sys.path if p not in ('', '.')]` BEFORE importing supabase —
      the local `supabase/` SQL folder shadows the installed package
      ([fetch_sessions.py:19](fetch_sessions.py:19)).
    - `load_dotenv()`; read `SUPABASE_URL` + `SUPABASE_SERVICE_ROLE_KEY`; exit with a clear
      message if unset.
    - Add `python-dotenv` to `requirements-dev.txt`.

    **CONFIG block at the top of the file** (clearly delimited, this is the re-tuning
    surface): `DEMO_TEAM_LABEL`, `WINDOW_MONTHS = 6`, `SESSIONS_PER_ATHLETE = 12`,
    plus empty `DEMO_ROSTER = []` and `TIMELINE = {}` placeholders that Task 2 fills.

    **`resolve_demo_target(sb, coach_email)`** — query `coaches` by email, return
    `(coach_id, team_id)`. Hard-fail if not found or if more than one row matches.
    Every subsequent write is scoped to that `team_id`. This is the AC-5 guard.

    **`ingest_csv(sb, csv_path, athlete_id, coach_id, created_at, name, notes,
    stroke_type, head_waist_m, dry_run)`** — mirror `/process`
    ([api.py:120-298](api.py:120)) exactly:
      1. Count `magnet_ok == 0` rows over total → `magnet_dropout_pct` (round 1dp).
      2. `vae.load_data(path)` → `vae.run_pipeline(df, 100.0)` → `(t_dec, dist_dec, vel, _, _)`.
      3. `m.compute_session_metrics(t_dec, vel, dist_dec, head_waist_m=head_waist_m)`.
      4. Build the same `data_quality` dict api.py builds, including the same four
         conditional warning strings.
      5. Upload the CSV bytes to the `raw-csvs` bucket at `{athlete_id}/{unix_ts}.csv`
         (same convention as api.py:256). Non-fatal on failure → `raw_csv_path = None`.
      6. Insert the `sessions` row with the SAME keys as `session_row` (api.py:280) —
         `athlete_id, coach_id, metrics_json, velocity_profile, distance_profile,
         raw_csv_path, upload_status="complete", name, notes, stroke_type` — PLUS explicit
         `created_at` AND `recorded_at` set to the backdated ISO-8601 timestamp.

    **Two things that will silently corrupt the seed if missed:**
    - **`device_id` is omitted/NULL** because demo sessions aren't tied to a physical
      encoder (roster decision: no fake device row). ~~The live column is still UUID
      (Phase 45 unfixed); writing a chip-id string raises 22P02.~~ **VOID as of
      2026-07-30** — patch_06 is applied live and the column is verified TEXT, so a
      chip-id string is now a legal value. Do not read this as a live constraint.
    - **`created_at` MUST be explicit.** Verified: `api.py` orders by `created_at` in 6
      places and the entire web portal sorts/displays on it — `recorded_at` is not what
      drives the UI. Omitting it collapses the whole 6-month timeline onto seed-day.

    Replicate api.py's `_clean` helper locally (NaN/Inf → None) — JSON cannot carry NaN
    and metrics output contains it. Do NOT import from `api.py` (drags in FastAPI + env).

    **`wipe(sb, team_id, dry_run)`** — list the team's athletes, remove their `raw-csvs`
    storage objects by `{athlete_id}/` prefix, then delete the athlete rows (sessions and
    session_annotations follow via ON DELETE CASCADE). Leave `coaches` + `teams` intact so
    re-seeding needs no new signup.

    **argparse:** `--coach-email` (required for anything touching the DB), `--validate`,
    `--stage1`, `--wipe`, `--dry-run`. `--dry-run` must print every intended write and
    execute none.
  </action>
  <verify>
    `python seed_demo_team.py --help` exits 0 and lists all five flags.
    `python -c "import ast;ast.parse(open('seed_demo_team.py').read())"` exits 0.
    `python seed_demo_team.py --coach-email nobody@example.com --wipe --dry-run` fails with
    the "coach not found" message and writes nothing.

<task type="auto">
  <name>Task 2: Validate archetype candidates and author the roster config</name>
  <files>seed_demo_team.py</files>
  <action>
    **Validation pass (`--validate`, no DB, no account needed).** For every CSV in `raw/`:
    run `load_data` → `run_pipeline` → `compute_session_metrics` in a try/except and print
    one line per file: PASS/FAIL, duration, cycle count, `magnet_dropout_pct`,
    `implausible_cycle_count`, and the failure reason on FAIL. Known-bad files exist and
    must be rejected gracefully, not crash the pass — e.g. `swim_ble_20260520_122759.csv`
    is 341 bytes and will trip run_pipeline's "Recording too short (< 2 s)" guard.

    FAIL, or a cycle count too low to carry a report card, disqualifies a file as an
    archetype.

    **Then author `DEMO_ROSTER`** in the CONFIG block from the PASS list — 12 entries:
    `{name, stroke_type, archetype_csv, trajectory, head_waist_m}`.

    - **Names:** fictional and plainly not-real people. Team label reads as a demo squad
      (CONTEXT.md labeling decision) — nothing that could be mistaken for a real club's
      roster.
    - **Stroke split: 8 breaststroke / 4 freestyle.** Breaststroke has deep source
      material (leo / lucas / itay / kenneth). Freestyle has exactly TWO usable sources
      (`carlos_fr_1.csv`, `swim_lucas_fr_1_20260515_192607.csv`), so two freestyle athletes
      necessarily share a source — give those two a mild time-warp on their archetype so no
      two sessions in the demo are byte-identical traces. **No backstroke or butterfly**
      (CONTEXT.md: no backstroke data exists; fly source material is too thin to carry
      distinct athletes).
    - **`trajectory`** is a label consumed by 50-02, authored here as data:
      2× `strong_improver`, 1× `regression_recovery`, 2× `needs_attention`,
      1× `plateau`, 6× `steady_improver`. These are the story beats to point at in a pitch.

    **Also author `TIMELINE`:** a 6-month window ending ~today, sessions clustered into
    ~6 "test weeks" spaced 3–4 weeks apart with 2 sessions per week, per-athlete jitter of
    a few days, and 1–2 athletes missing a given test week. Clustered beats evenly-spaced —
    clubs test periodically, and it makes the roster grid's "last tested" column read
    naturally. Consumed by 50-02; authored here so the config surface is complete.
  </action>
  <verify>
    `python seed_demo_team.py --validate` exits 0, prints one PASS/FAIL line per raw/ CSV,
    reports ≥10 PASS files, and does not raise on the known-bad short files.
    `python -c "import seed_demo_team as s; assert len(s.DEMO_ROSTER)==12; assert
    sum(1 for a in s.DEMO_ROSTER if a['stroke_type']=='freestyle')==4; assert all(
    a['archetype_csv'] for a in s.DEMO_ROSTER)"` exits 0.
  </verify>
