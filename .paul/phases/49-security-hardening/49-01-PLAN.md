<objective>
## Goal
Close the three highest value-to-effort security gaps in the FastAPI backend (`api.py`),
all found in a full-surface review 2026-07-20:
1. **Internal error detail leaks to clients** — 14 sites return raw `str(e)` (DB/library
   internals) in 500 responses and in the `/process` + annotation response bodies.
2. **Edge is wide open** — `allow_origins=["*"]` CORS + **no request-body size limit** on the
   two file-upload endpoints (a single authenticated caller can OOM the shared Railway instance
   with one large upload).
3. **Cross-tenant session write** — `POST /process` never verifies the posted `athlete_id`
   belongs to the calling coach's team before saving a session against it.

## Purpose
This is a pre-pilot hardening pass. Swimnetics stores **minors' performance data** and is
heading into paid demos with real clubs (PROJECT.md constraints). The backend runs on a shared
single-tenant Railway instance behind a `["*"]` CORS policy, using the Supabase **service-role
key** (which bypasses RLS entirely — every ownership guarantee is manual in `api.py`). The three
fixes above are cheap, backend-only, and each removes a concrete exposure: information
disclosure, availability/cost DoS, and a tenant-isolation hole. Higher-cost items (rate limiting,
report-token expiry, pinning the rest of `requirements.txt`) are deliberately deferred with
rationale (see SCOPE LIMITS) so this plan stays reviewable and low-risk.

## Output
- `api.py` — generic 500 messages + server-side logging; env-driven CORS allowlist; memory-safe
  upload size caps on `/process` + `/sessions/{id}/video` and a payload cap on `/coach/chat`;
  athlete-ownership check in `/process`
- `tests/test_api.py` — regression tests for the ownership check (foreign `athlete_id` → 403,
  no insert) and the upload size cap (oversized body → 413)
</objective>

## Review findings (2026-07-20) — what this plan fixes

**F1 — Internal error disclosure (info leak).** 14 sites return internal exception text to the
client. `HTTPException(500, detail=str(e))` at api.py:317, 649, 702, 832, 905, 968, 999, 1173,
1199, 1231, 1318; `detail=f"Video upload failed: {e}"` at 960; and raw error strings written into
the **response body** at 266 (`session_save_error = f"Storage upload failed: {upload_exc}"`), 298
(`session_save_error = str(e)`), and 871 (`recompute_error = str(e)` in the PUT /annotations body).
These expose DB/postgrest internals and code paths to any authenticated caller.

**F2 — Open edge: CORS + no size limit.**
- CORS `allow_origins=["*"]` / `allow_methods=["*"]` / `allow_headers=["*"]` (api.py:72-77). Real
  exploitability is LOW because auth is a Bearer token (no cookies, `allow_credentials` unset, so a
  foreign origin can't read a victim's token) — but it is the canonical scanner finding and is free
  to tighten. Only the **web portal** (browser) is CORS-bound; the iOS app is not.
- **No body-size limit anywhere** (grep-confirmed: no Content-Length guard, no `_read_capped`).
  `/process` does `raw_bytes = await file.read()` (api.py:121) and `/sessions/{id}/video` does
  `video_bytes = await file.read()` (api.py:946) — both buffer the **entire** upload into RAM with
  no cap. One authenticated coach (or a leaked JWT) can exhaust memory on the shared instance and
  take the API down for every tenant. This is the highest-severity availability issue.

**F3 — Cross-tenant session write.** `POST /process` (api.py:105-321) takes `athlete_id` from the
form, looks up the coach row, enforces limits, then inserts a session with
`{athlete_id, coach_id}` — **without ever checking that `athlete_id` belongs to this coach's
team.** A coach who knows another team's athlete UUID can create a session pointing at it. Because
sessions RLS is `athlete_id IN (SELECT id FROM athletes WHERE team_id = current_team_id())`, the
*victim* team would then see a foreign session in that athlete's history. Likelihood is low (needs
a valid, unguessable athlete UUID) but it is a genuine tenant-isolation break and the fix is one
scoped query.

## Verified NON-issues (do NOT "fix" these — reviewed and correct)
- **Stripe webhook signature IS verified** — `_stripe.Webhook.construct_event(...)` at api.py:1719
  with `SignatureVerificationError` → 400. Correct.
- **Report tokens are strong** — `crypto.randomUUID()` (v4, 122-bit) in
  web/components/portal/ReportBuilder.js:41. Not guessable; the public `/reports/{token}` design
  (no anon RLS, service-role lookup) is intentional.
- **No SQL injection** — everything goes through the supabase/postgrest query builder
  (parameterized); no raw SQL takes user input.
- **No committed secrets** — `.env` is gitignored; a repo-wide scan found no service-role key /
  `sk_live` / JWT. `.mcp.json` holds only a shadcn command.
- **No XSS sink** — no `dangerouslySetInnerHTML`/`eval`/`innerHTML` in web/; `{data.message}` on
  the report page is React-escaped.
- **RLS `WITH CHECK` present** on athletes/sessions/reports (patch_01, patch_03); read/update/delete
  paths in api.py consistently filter by `coach_id`. F3 is the one write path that does not.

<acceptance_criteria>

## AC-1: Internal error text no longer reaches clients
```gherkin
Given any endpoint whose handler catches an exception
When it returns a 5xx (or a *_error field in a 200 body)
Then the client receives a short generic message (no DB/library/internal exception text)
And the real exception is logged server-side (logger.exception) for debugging
And grep of api.py finds no `detail=str(e)` and no raw `{e}`/`{upload_exc}` in a client-returned string
```

## AC-2: CORS is an allowlist, not a wildcard
```gherkin
Given the CORS middleware
When the app configures allowed origins
Then origins come from an ALLOWED_ORIGINS env var (comma-separated) with a documented default
And "*" is not used as an allowed origin
And a request from an origin not on the list is not reflected in Access-Control-Allow-Origin
```

## AC-3: Oversized uploads are rejected before exhausting memory
```gherkin
Given the /process and /sessions/{id}/video upload handlers
When an upload exceeds its configured byte cap (MAX_CSV_BYTES / MAX_VIDEO_BYTES)
Then the handler returns HTTP 413 without buffering the whole body into RAM
And a normally-sized session CSV and phone video still upload successfully
And /coach/chat rejects an over-large messages payload with 400
```

## AC-4: /process rejects a foreign athlete_id
```gherkin
Given an authenticated coach and an athlete_id that is NOT in that coach's team
When POST /process is called with that athlete_id
Then the request is rejected with 403 before any storage upload or session insert
And a valid athlete_id owned by the coach still processes and saves normally
```

## AC-5: Live flows still work after hardening (human-verify)
```gherkin
Given the fixes are deployed and ALLOWED_ORIGINS is set on Railway to include the web portal origin
When the coach uses the web portal and the iOS app
Then the portal still loads and reads/writes (CORS allows it)
And recording a session, adding an athlete, and attaching a video all still succeed
And an intentionally huge upload is rejected rather than crashing the API
```

        async def _read_capped(upload: UploadFile, cap: int) -> bytes:
            buf = bytearray(); 
            while True:
                chunk = await upload.read(1024 * 1024)
                if not chunk: break
                buf.extend(chunk)
                if len(buf) > cap:
                    raise HTTPException(status_code=413, detail="Uploaded file too large")
            return bytes(buf)

## SCOPE LIMITS — deliberately deferred (documented, not forgotten)
- **Rate limiting** on `/coach/chat` (Anthropic $ cost), `/process` (CPU), and the public
  `/reports/{token}` — needs a limiter + shared store (Railway infra decision). The /coach/chat
  payload cap in Task 2 is a partial mitigation only. → future 49-02.
- **Parent report-token expiry / revocation** — a leaked `/report/{token}` URL exposes a minor's
  data indefinitely. Adding `expires_at`/revoke is a product + schema decision (patch_09). → future.
- **Pin the rest of `requirements.txt`** — only supabase/postgrest are pinned (Phase 48). Pinning
  numpy/scipy/fastapi/uvicorn/anthropic/stripe/etc. is cheap insurance but touches the whole
  dependency set + every deploy; keep it a separate, independently-verifiable change. → future.
- **Athlete-ownership on other write paths** — this plan covers `/process` (the one gap found);
  other writes already filter by coach_id.
- Tightening CORS `allow_methods`/`allow_headers` to the exact set used (cosmetic; low value).
