<objective>
## Goal
Make BLE session retrieval **lossless and self-recovering** so the random "The end-of-dump marker
never arrived" failure stops destroying recorded sessions. Firmware stops wiping the buffer on a
dump the phone hasn't confirmed and resends the end marker; the phone shortens its stall, auto-
retries the dump, confirms receipt with an explicit CLEAR, and reports how many samples it got.

## Purpose
At a pool test the error appeared at random and the affected session became **unretrievable**
(`CONTEXT.md` C1/C2). The failure is a single-point-of-failure (one 1-byte `0xEE` indication) sitting
on top of an unconditional buffer wipe. This plan removes the data loss with certainty and makes the
stall recoverable, without a blind, hardware-untestable transport rewrite (`CONTEXT.md` D1–D3).

## Output
- `ESP_32_V5.ino` — buffer retained until an explicit `CLEAR` (or next recording); `0xEE` resent;
  `TRACE_BUFFER 0`.
- `RecordScreen.js` — 8 s stall + auto-retry META→DUMP; `CLEAR` on confirmed save; received-count in
  the error.
- `BleContext.js` — `requestMTU` on connect (latent Android fix).
</objective>

## Protocol invariants that must not change
- Sample packets stay 7-byte `<IHB` records; META stays exactly 8 bytes; `0xEE` stays the 1-byte
  end marker. The phone's length-based discriminator (`RecordScreen.js:381-424`) is unchanged.
- Recording remains BLE-independent (`ESP_32_V5.ino` loop); a mid-dump disconnect still retains the
  buffer.
</context>

<acceptance_criteria>

## AC-1: Firmware never wipes an unconfirmed buffer
```gherkin
Given a buffered session on the device
When dumpBuffer() streams it and sends the end marker
Then bufCount / dataReady / sessionStartUs are NOT cleared by dumpBuffer()
And the buffer is cleared only by (a) a new recording start, or (b) an explicit "CLEAR" command
So a retrieval the phone did not confirm leaves the session fully retrievable on the device
```

## AC-2: End marker is resent
```gherkin
Given a complete dump
Then the 0xEE end-of-dump marker is sent MORE THAN ONCE (>= 3 times)
And the phone treats the first recognized 0xEE as end-of-dump and ignores the rest (idempotent)
```

## AC-3: Phone auto-retries a stalled dump before failing
```gherkin
Given retrieval has started and no packet has arrived for the stall window (~8 s) and no 0xEE seen
When there are retry attempts remaining
Then the phone clears its partial sample buffer and re-issues META -> DUMP on the same subscription
And only after the retries are exhausted does it show the "end-of-dump marker never arrived" error
And that error now states how many samples were received
```

## AC-4: Phone confirms receipt so the device can free the buffer
```gherkin
Given retrieval completed via the 0xEE marker (not a stall) and saveCSV succeeded
Then the phone writes "CLEAR" to the device (fire-and-forget, non-fatal on failure)
And the device clears its buffer, so a subsequent META reports no session
And a STALLED save (partial) does NOT send CLEAR (the device keeps the session for a later retry)
```

## AC-5: MTU is negotiated on connect
```gherkin
Given the app connects to a device
Then it requests an MTU large enough for 168-byte dump packets (>= 185), non-fatal if unsupported
```

## AC-6: Normal firmware build
```gherkin
Then ESP_32_V5.ino has TRACE_BUFFER defined 0 (no post-recording Serial buffer dump)
```

</acceptance_criteria>
