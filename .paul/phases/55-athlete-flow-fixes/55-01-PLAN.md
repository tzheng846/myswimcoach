## The one fact that shapes this whole plan
`RecordingConfig` is a **tab screen** (`RootTabs.js:29`). Tab screens mount once per app launch and
never remount. Every defect here follows from that:

| Consequence | Defect |
|---|---|
| `useEffect(..., [])` runs once ever | B1 — roster frozen at launch |
| `useState(...)` initializers run once ever | B2b — params ignored on arrival |
| It is a child of `Tabs`, not of Root | B2a — `navigate()` from Root can't reach it |

    Two changes to one screen. Both exist because this is a tab screen that never remounts.

    **1a — refetch the roster on focus (AC-1).**
    Replace the mount-only roster `useEffect` at :42-45 with a `useFocusEffect`, matching the
    pattern already used by `DashboardScreen`, `AthletesScreen` and `SessionHistoryScreen`. Import
    `useFocusEffect` from `@react-navigation/native` and wrap the callback in `React.useCallback`
    with a stable dep array — without the useCallback it refetches in a loop.

    Leave the second `useEffect` (`getStartSequenceEnabled`, :47-49) alone — it reads a device
    preference, not roster data, and mount-once is correct for it.

    **1b — apply route params after mount (AC-2, AC-3).**
    The params are currently read only in `useState` initializers (:29-34), which never re-run, so
    a navigation carrying `athleteId` is silently ignored. Add an effect keyed on
    `route.params?.athleteId` that, when an athleteId is present:
      - resolves the athlete from the fetched `athletes` list by id and sets it — prefer the DB row
        over the params, so `head_waist_m`, `name` and `stroke_type` are correct and current
      - falls back to constructing the object from params if the roster hasn't loaded yet
      - sets `strokeType` from that athlete's `stroke_type` when it is a known key in `STROKES`
      - then clears the consumed params via `navigation.setParams({ athleteId: undefined,
        athleteName: undefined, defaultStrokeType: undefined })`

    The clear is what satisfies AC-3: params on a never-unmounting tab screen otherwise persist
    indefinitely, so the next plain tab press would silently inherit the previous athlete. Do not
    skip it — this behavior is created by change 1b itself.

    Avoid: introducing a state library, a global store, or a navigation listener — `useFocusEffect`
    is the established pattern in this codebase and three sibling screens already use it.

  <name>Task 2: Fix the dead Record button and the comment that says it works</name>
  <files>../swimnetics-mobile/src/screens/AthleteDetailScreen.js, ../swimnetics-mobile/src/navigation/RootTabs.js</files>
  <action>
    **2a — nested navigate (AC-2).**
    `AthleteDetailScreen.js:137` calls `navigation.navigate('RecordingConfig', {...})`.
    `AthleteDetail` is a Root-stack screen; `RecordingConfig` is a child of the `Tabs` navigator.
    React Navigation resolves unknown route names by bubbling UP to parents only — it never
    descends into a child navigator — so the action reaches the top unhandled and is dropped
    silently. Rewrite it in the nested form:

        navigation.navigate('Tabs', {
          screen: 'RecordingConfig',
          params: { athleteId, athleteName, defaultStrokeType },
        })

    Keep the same three param names — Task 1's effect and the existing `useState` initializers both
    read exactly those keys. The bug is the envelope, not the payload.

    Do NOT add `headWaistM` to the params. Task 1 resolves head-waist from the roster row, which is
    more reliable than this screen's `hw`, a TextInput string that may be mid-edit.

    **2b — correct the stale comment.**
    `RootTabs.js:21-23` claims route names match "so cross-screen navigation keeps working:
    'RecordingConfig' (Record island) and 'SessionHistory' ... are reached by name from
    AthletesScreen." That is true only for tab siblings. It became false for `AthleteDetail` when
    Phase 38-03 moved that screen to the Root stack, and it is precisely the assumption that
    produced this bug. Rewrite it to state that Root-stack screens must use the nested
    `navigate('Tabs', { screen })` form to reach a tab.

    Boundary: do not restructure the navigators. Moving `AthleteDetail` into the tab navigator
    would also "fix" this and is explicitly NOT wanted — it would change the presentation of every
    screen pushed over the tab bar.
