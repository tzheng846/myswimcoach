<objective>
## Goal
Turn annotation from click-per-mark into **play-and-tap**: watch the active camera and press
number keys **1 / 2 / 4 / 5** to drop the four existing markers at the current video playhead, with a
report-card-style **velocity context strip** riding on the active camera tile so the coach sees where
they are marking. Delivers Phase 81's D4 (labeling throughput) for every already-persisted marker.

## Purpose
The ~20-session annotation backlog that Phases 78/80 depend on will not get labeled at click-per-mark
speed (CONTEXT "Why now"). This is the throughput win — and Phase 80 established that count + rough
timing tolerates play-and-tap's frame-precision, so it is worth building now. This plan is a pure
web-UI re-wire of plumbing that is already ~70% there: `playheadS` is tracked, `placeStrokeMark` and
the phase-set path exist, `M` already proves drop-at-playhead for one marker.

## Output
Modified web components only. No backend, no contract, no new field. The new underwater-kick marker
(key 3) and its recompute are the separate vertical slice **81-02**.
</objective>

<acceptance_criteria>

## AC-1: Number keys place/move the single boundaries at the playhead
```gherkin
Given the annotate page is open with a synced active camera and a video playhead at time T
When the coach presses 1, 2, or 4 (no modifier, focus not in a text field)
Then the corresponding boundary (dive_start_s / underwater_start_s / stroke_start_s) is set to T
  And it appears at T on the AnnotationChart, the change is undoable (Ctrl+Z), and pressing the same
      key again at a new playhead MOVES that boundary (overwrite), not adds a second one
  And the newly placed boundary is NOT auto-selected (arrows stay in frame-step mode, so the
      step -> mark -> step loop keeps working)
```

## AC-2: Key 5 (and M) append a stroke mark at the playhead, guarded
```gherkin
Given the annotate page is open with a video playhead at time T
When the coach presses 5 or M
Then a stroke mark is appended at T via the existing placeStrokeMark (same swim-window guard, undo,
     and sort as today's M)
  And when playheadS is null (no synced camera), pressing any of 1/2/4/5/M places nothing and shows
     the existing "No video playhead yet" hint instead of throwing
  And pressing 3 does nothing (key 3 / kick marking is 81-02)
```

## AC-3: A velocity context strip rides on the ACTIVE camera tile
```gherkin
Given the active camera tile has a synced video (effectiveOrigin is known)
When the video plays or is scrubbed
Then a rolling velocity strip on that tile follows the playhead (playhead line + live readout),
     built from the session's velocity_profile at the session's sample rate
  And dragging on the strip scrubs the video and moves the playhead (TraceOverlay onSeek -> the tile's
     seek), so it doubles as a scrubber
  And when the active camera is switched, the strip moves to the new active tile; a tile that is not
     active, has no video, or is unsynced (effectiveOrigin null) shows no strip (TraceOverlay idles)
  And the <video> element never moves in the DOM (playback position + signed URL preserved)
  And the report-card VideoTracePanel and Compare are unchanged (TraceOverlay itself is not edited)
```

## AC-4: The number-key workflow is discoverable in the editor
```gherkin
Given the annotate editor panel is visible
When the coach reads the "Keys" help and the tool palette
Then the help text documents 1/2/4 = place-or-move Dive/UW/Stroke at the playhead and 5 (or M) =
     stroke mark, alongside the existing arrow / Esc / Ctrl+Z docs
  And each phase tool button shows its digit so the map is readable without the help text
```
