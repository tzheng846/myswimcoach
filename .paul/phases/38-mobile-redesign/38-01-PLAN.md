<objective>
## Goal
Stand up the redesign's foundation in the `swimnetics-mobile` repo: a single shared
**design-token system**, a small set of **reusable UI primitives**, and a new
**bottom-tab navigation skeleton** (Dashboard · Team · History + a separate Record
"island") with four unique SVG icons. Restyle **Login** to the new tokens as the first
real proof the system reads well on device.

## Purpose
Today colors/spacing are hand-repeated and inconsistent across 9 screens (blue appears as
`#2196F3` / `#2563EB` / `#5B8DEF`; five different backgrounds; four oranges). Every later
Phase-38 slice (Dashboard, Team, History, Compare, Record) depends on one token source and
the tab shell existing. This plan creates that spine so subsequent plans are pure
screen-level restyles against stable primitives — no nav re-architecture mid-phase.

## Output
- `src/theme/` — `tokens.js` (palette, type scale, spacing, radii, pillar band colors) +
  `index.js` barrel.
- `src/components/ui/` — `AppText`, `Screen`, `Card`, `Button`, `SectionHeader`, plus
  `TabIcons` (SVG) and a custom `TabBar` (Record island).
- `src/navigation/RootTabs.js` — bottom-tab navigator; each tab nests a native-stack so
  detail screens push within their tab.
- `App.js` rewired: authed users land on `RootTabs`; Login restyled.
- `DashboardScreen.js` stub (themed placeholder; real content = 38-02).
</objective>

## Design decisions locked with the user (2026-06-19)
- Nav: 4 bottom tabs. **Record is a separate "island"** (visually detached / emphasized);
  Dashboard, Team, History are the grouped three. Each tab has a **unique icon**.
- Build order: **design system first**, then screen-by-screen vertical slices.

- Whole phase is **mobile-repo-only** — no backend changes. Existing endpoints

- Platform: **iPhone only** (iPad already de-scoped, TARGETED_DEVICE_FAMILY=1).

**Locked design decisions (carry to 38-02/38-03/all slices):**
- **Buttons:** primary = SOLID `primary` fill + white text; secondary = `surfaceAlt` fill +
  `primary` text; accent + ghost + danger variants per the mockup.
- **Accent restraint:** `accent` (#97dffc) is reserved for the AI assistant surfaces — do NOT
  use it for general buttons/chips/highlights.
- NO avatar/profile icon anywhere athletes are listed (saves space).
- **Team tab roster → LABELED TABLE** (one row per athlete; columns = the 4 pillars with an
  ICON header that doubles as the permanent legend; cells = band-colored dots). Best for
  scanning one pillar down the whole team. Row tap → athlete detail (full labeled `PillarCards`
  + edit fields + send report). Fits a 375px phone: name ~140px + 4 icon columns ~55px each.
  Header-tap-to-sort by a pillar = nice-to-have for 38-03 (not locked).
- **Dashboard needs-attention → 2-COLUMN SUMMARY CARDS** (critical-factors view) — each card =
  name + a derived **overall score** + the single **weakest pillar** (icon + band color); tap →
  athlete detail. This is the C pattern, used on the Dashboard only.
- **Overall score + weakest pillar are CLIENT-DERIVED** from `/team/overview` per-athlete
  pillars (overall = mean of available pillar scores, rounded, provisional handled; weakest =
  lowest score). No backend change. Fallback if "overall" feels arbitrary later: band tally
  (e.g. "3 good · 1 needs work").
- **Pillars are labeled by ICONS** (Speed=gauge, Stroke-Length=ruler, Consistency=wave-sine
  [weakest glyph — may swap to a letter], Endurance=battery), band-colored. Used as the table
  header and on the summary cards.
- **Pillar band colors:** primitives expose `good/ok/needsWork` as fallback, but PillarCards
  and any band UI MUST still read colors from the API payload (existing convention).

Type scale (system font): `display 28/700`, `title 22/700`, `heading 17/600`,
`body 15/400`, `label 13/500`, `caption 12/400`.
Spacing: `4 8 12 16 20 24 32`. Radii: `sm 8`, `md 12`, `lg 16`, `pill 999`.
