<objective>
## Goal
Persist each session's **true** decimated sample rate on the session row and make every consumer
read it instead of assuming 100 Hz. New sessions become correct immediately; existing sessions keep
today's exact behavior until a separate backfill plan (52-02) repairs them.

## Purpose
`vel_acc_extraction.run_pipeline` decimates by an **integer** factor, so the stored
`velocity_profile` is ~89.5 Hz, never the requested 100 Hz — and `api.py:143` throws the real value
away. Six consumers then assume 100 Hz. On real sessions today this means a 47.1 s swim displays as
42.2 s, and **recomputing metrics from a saved annotation shifts every time-derived metric by
~11.7%** (stroke rate, lap time, DPS). Phase 50-02 propagates annotations across ~144 demo sessions
and would bake that error in, so this lands first.

Findings F2 + F3 in `API-AUDIT.md`. Approach chosen by the user 2026-08-03: **persist the real rate
as `sessions.sample_rate_hz`** — correct per-session, survives firmware and device changes, fixes
the class rather than the instance.

## Output
- `supabase/patch_09_sessions_sample_rate.sql` — nullable `sessions.sample_rate_hz`
- `api.py` — writes the real rate on `/process`; reads it on the annotation, recompute and export paths
- `annotations.py` — `build_seed` / `annotation_to_overrides` take an explicit rate
- three `web/` files — time axes built from the session's rate, not `i / 100`
- tests + `CLAUDE.md`
</objective>

## The two precisions that bound this fix
Both carried from `API-AUDIT.md` F2 and independently re-verified:

1. **Cycle boundaries are not corrupted.** The coach clicks at displayed time `T`;
   `annotations.py:126` converts back with the *same* wrong constant. The round trip lands on the
   sample actually clicked. Only the time *interpretation* is wrong — do not "correct" existing
   stored indices.
2. **Original auto metrics are correct.** `compute_session_metrics` runs on the true `t_dec` clock
   inside `/process`, so `metrics_json.session` is right until an annotation overwrites it. The
   damage is confined to sessions that have been recomputed from an annotation.

## Why NULL must mean 100, not 89.5
Existing rows have no stored rate. Defaulting a NULL to `annot.FS_HZ` (100) reproduces **today's
exact behavior** for those rows, so this plan changes nothing for un-backfilled sessions — no
mid-flight shift in displayed times, no drift between a backend seed and a web time axis. The
native rate genuinely varies per device and session, so there is no correct constant to guess.
Repairing existing rows is 52-02's job, deliberately separated.

<acceptance_criteria>

## AC-1: The real rate is persisted
```gherkin
Given a raw CSV whose native rate decimates to something other than 100 Hz
When POST /process succeeds and saves the session
Then the session row's sample_rate_hz equals the actual_fs returned by run_pipeline
And it is not 100 unless the decimation genuinely produced 100
```

## AC-2: Annotation times use the session's own rate
```gherkin
Given a session with sample_rate_hz = 89.5 and a velocity_profile of N samples
When GET /sessions/{id}/annotations is called
Then duration_s equals N / 89.5
And the seed's phase times and stroke marks are indices divided by 89.5
```

## AC-3: Recompute-from-annotation runs on the true clock
```gherkin
Given a session with sample_rate_hz = 89.5 and a saved annotation with >=2 stroke boundaries
When PUT /sessions/{id}/annotations recomputes metrics
Then the time axis is arange(size) / 89.5
And the recomputed stroke_rate_spm matches the rate implied by the true clock, not one 11.7% off
```

## AC-4: A NULL rate is byte-identical to today
```gherkin
Given a session row whose sample_rate_hz is NULL
When any annotation, export or web path reads it
Then 100 Hz is used
And every output is identical to the pre-plan behavior
```

## AC-5: The web time axis matches the backend
```gherkin
Given a session with sample_rate_hz = 89.5
When the annotate page and the report-card page render the velocity chart
Then the x axis runs to N / 89.5 seconds
And a seeded phase mark from the API lands on the sample it describes
```

## AC-6: The round trip is preserved
```gherkin
Given any sample rate
When a mark is seeded at index i and converted back with annotation_to_overrides
Then the resulting index is i
```
