<objective>
## Goal
QR-slate backend contract (CONTEXT D6): a nullable `sessions.recording_token` column + `/process`
storing it when the phone sends one. No new endpoint — the web looks up the session by token via
supabase-js (sessions is already RLS-readable there).

## Purpose
The token is the pin that links an over-water clip to its session: phone generates + displays it as a
QR at record start (70-04 mobile), films it, then `/process` persists it here so the web decode
(70-03) can find the session. This plan lays the storage half.

## Output
- `supabase/patch_13_recording_token.sql` (user-applied, idempotent).
- `/process` accepts `recording_token` and writes it ONLY when provided (pre-patch safe).
- test_api.py: token carried when sent, absent when not.
</objective>
