<objective>
## Goal
Stop `DELETE /sessions/{id}` from leaking video storage, and reclaim the ~716 MB already leaked,
without touching the segmenter ground-truth videos that are still referenced by a live session.

## Purpose
Supabase free-tier storage is at 2.53 GB against a 1 GB cap; new uploads may already be silently
blocked (Supabase blocks storage writes after a grace period once over quota — confirmed via
[UI Bakery](https://uibakery.io/blog/supabase-pricing) and
[Automation Atlas](https://automationatlas.io/answers/supabase-free-tier-limits-2026/)). 716 MB of
that is dead weight from two leak sources in the session-delete path (documented in
[82-CONTEXT.md](CONTEXT.md)): `sessions.video_path` is never removed from the `videos` bucket, and
`session_videos` rows cascade-delete in Postgres without their storage objects ever being removed.
Fixing the leak and reclaiming the dead weight is free and required regardless of whether the user
also upgrades to Supabase Pro (already decided, separately, as an out-of-band billing action).

## Output
- `DELETE /sessions/{id}` removes every storage object tied to the session (raw CSV — unchanged;
  primary video; every external `session_videos` clip) before the row/its cascades disappear.
- `tools/cleanup_orphan_videos.py` — a dry-run-by-default script that finds and removes videos in
  the `videos` bucket referenced by no live row.
- Pytest coverage proving the fix.
</objective>

<acceptance_criteria>

## AC-1: Primary video removed on session delete
```gherkin
Given a session row with a non-null video_path
When DELETE /sessions/{id} is called by the owning coach
Then the session row is deleted AND storage.from_("videos").remove(...) is called with that
  video_path included
```

## AC-2: External session_videos clips removed on session delete
```gherkin
Given a session with 2 rows in session_videos, each with its own storage_path
When DELETE /sessions/{id} is called by the owning coach
Then both storage_path values are captured before the sessions row delete fires (since
  ON DELETE CASCADE removes the session_videos rows immediately after) AND both are included in
  a storage.from_("videos").remove(...) call
```

## AC-3: No-video sessions behave exactly as before
```gherkin
Given a session with video_path = NULL and no session_videos rows
When DELETE /sessions/{id} is called
Then no videos-bucket remove() call is made (or it is called with an empty list and is a no-op),
  no error is raised, and the existing raw-csv cleanup is unaffected
```

## AC-4: Storage removal stays non-fatal
```gherkin
Given storage.from_("videos").remove(...) raises an exception
When DELETE /sessions/{id} is called
Then the request still returns {"ok": true} — the row is already gone and an orphaned file is the
  documented pre-fix status quo, not a new failure mode
```

## AC-5: Cleanup script is safe by default and reclaims real orphans
```gherkin
Given the videos bucket contains files not referenced by any sessions.video_path or
  session_videos.storage_path (computed live at run time, not from a cached list)
When tools/cleanup_orphan_videos.py is run with no flags
Then it lists every orphan file and its size and total bytes, and deletes nothing
When it is run with --apply
Then it deletes exactly those orphan files and reports bytes reclaimed
```
