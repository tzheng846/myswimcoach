<objective>
## Goal
Draw a **grey dotted rolling mean over the raw velocity trace** on the web report card, with a
slider that sets the averaging window from 0.00 s (off) to 3.00 s. The raw trace is untouched and
stays on top of nothing — it keeps its own colour and weight; the trend is an addition, not a
replacement. The window persists per coach.

## Purpose
A raw butterfly trace at ~90 Hz is a sawtooth: five to twelve surge-and-glide peaks per lap, each
one real. That shape is the whole point of the encoder and it must not be smoothed away — but it
also **hides the lap-scale story**, which is what a coach is actually reading the chart for. A
prototype against Chantee's three 2026-08-20 butterfly swims showed the effect directly: at raw
resolution the three swims are three near-identical sawtooth walls; at a ~1 s window their trend
lines separate cleanly and say something a coach can act on (the dive's advantage is spent inside
the first quarter of the lap, and the 80% and 100% efforts are indistinguishable from 3 m to 18 m).

This is the same "within-athlete contrast over absolute thresholds" direction PROJECT.md records
for Phase 53, delivered as a reading aid rather than a new metric. **It computes nothing that is
stored and adds no metric to the registry** — it is a second rendering of `velocity_profile`, which
is why it is a plan and not a phase.

## Output
- new pure `web/lib/rollingMean.js` — null-aware centred moving average, no React, no recharts
- `web/lib/useTracePrefs.js` gains `smoothWindowS` / `setSmoothWindowS` on the existing

- `page.js` renders the slider inside the existing trace section and passes the prop
- `scratch/rolling_mean_check.mjs` — pure assertions incl. the decimation trap (T1 below)

<decisions>
Made at the user's direction, 2026-08-31, from a working prototype
(`scratch/chantee_traces.html`) reviewed against Chantee's three butterfly sessions.

**D1 — The window is expressed in SECONDS (0.00–3.00, step 0.05), not in stroke cycles.**
Cycles are the more meaningful unit — "one cycle" means the same thing on every stroke and every
swimmer, where 1.0 s is one butterfly cycle but roughly 1.4 breaststroke cycles. It was rejected
anyway because a cycle-denominated window would have to read `mean_isi_s`, and on butterfly that
number comes from the segmenter that CONTEXT and PROJECT.md both flag as unreliable (F1 0.526; on
the Chantee sessions it found 5 cycles where there should be ~12). **A cycle-unit slider would
silently inherit a 2× error.** Seconds are dumb and correct. Revisit only if the segmenter is
fixed.

**D2 — 0.00 s is a reachable slider position meaning "off", but the default is 1.00 s.**
The user chose a default-on trend. An off position costs one conditional and gives a coach who
wants today's chart back a way to get it without clearing storage. At 0.00 s no second `<Line>` is
rendered at all — it does not degenerate into a duplicate of the raw line drawn on top of itself.

**D3 — The rolling mean is computed on the FULL-RATE array, BEFORE `VelocityChart`'s decimation.**
This is the one way this plan can be quietly wrong. `VelocityChart.js:15` caps the chart at
`MAX_POINTS = 2000` and strides `step = ceil(n / MAX_POINTS)`. A 20 s session at 89.99 Hz is 1799
points, so `step === 1` and nothing decimates — **the bug would not reproduce on the sessions most
likely to be used for testing.** On a 40 s session `step` becomes 2, and a mean computed after
decimation would span 2× the requested seconds while the label still read "1.00 s". Smooth first
at the native rate, decimate the smoothed array with the same stride. T1 pins this.

**D4 — The trend line is grey and dotted, deliberately unlike the two dashed things already on
this chart.** `VelocityChart` already draws cycle boundaries as `#1e3a5f` / `strokeDasharray="3 3"`
and TimeToX's marker as amber `#f59e0b`. The trend uses `#9aa6b2` with `strokeDasharray="6 4"` at
`strokeWidth={2}` — a grey no other element on the chart uses, and a coarser dash than the cycle
boundaries. Do not reuse `#7f8c8d` (the axis-tick muted grey) — a data line must not share a colour
with chrome.

**D5 — The slider is a REPORT-CARD control, not a `VelocityChart` control.**
`VelocityChart` has two consumers: the report card and `/app/sessions/[id]/video` (`video/page.js:143`).
Only the report card gets the slider UI; the component just accepts a number. The video route
passes nothing, so it renders exactly as it does today. This also honours the boundary
`AccelerationChart.js:21-24` already records — that comment forbids a *second x-windowing slider*
next to VelocityChart's, because two of those would desync x-alignment. A smoothing window is a
y-domain control and cannot desync the x axes; the boundary is respected, not bent.

**D6 — Acceleration gets no trend line in this plan.** `AccelerationChart` is a separate sibling by
prior design. Smoothing a signed derivative raises a real question (does the coach want the mean of
a signal that crosses zero, or the mean of its magnitude?) that this plan does not answer. Out of
scope, stated in SCOPE LIMITS, not deferred silently.
</decisions>

<task type="auto">
  <name>Task 1: Pure null-aware rolling mean, with the decimation trap pinned</name>
  <files>web/lib/rollingMean.js, scratch/rolling_mean_check.mjs</files>
  <action>
    Create `web/lib/rollingMean.js` exporting one function:

      rollingMean(values, fsHz, windowS) -> Array<number|null>

    - Returns `values` unchanged (a copy) when `windowS <= 0` or when the computed sample
      width `N = Math.max(1, Math.round(windowS * fsHz))` is `<= 1`.
    - CENTRED window: for index j the span is [j - h, j + h] where `h = (N - 1) >> 1`, clamped
      to the array bounds. Do not use a trailing window — a trailing mean shifts every feature
      later in time by half the window and would misplace the breakout against the trace beneath it.
    - Null-aware via prefix sums so it stays O(n) regardless of window size: build a running sum
      array and a running COUNT array where nulls contribute 0 to both. The mean at j is
      `sum/count`, or `null` when `count === 0`.
    - Pure: no React, no recharts, no DOM. Guard `fsHz` — a null/0/NaN rate must fall back to 100
      to match `annotations.FS_HZ`, per the CLAUDE.md rule that a NULL rate is "unknown", not "100".

    Then write `scratch/rolling_mean_check.mjs` asserting at minimum:
    - a constant array returns that constant everywhere (no edge droop from the clamped span);
    - `windowS = 0` returns the input values;
    - nulls are skipped, not counted as zeros — [1, null, 3] over a 3-wide window gives 2, not 1.33;
    - an all-null window yields null;
    - THE DECIMATION TRAP (D3): build a synthetic 4000-point profile at 90 Hz — long enough that
      VelocityChart's `step` becomes 2 — smooth it at 1.0 s, then stride the RESULT by 2, and
      assert that equals smoothing the full array and striding, and does NOT equal striding first
      and then smoothing with the same N. Assert those two paths differ, so the test would fail
      if someone later moves the smoothing after the decimation.

    Avoid: recomputing per render inside the component (Task 2 memoises), and any dependency on
    `metrics_json` — this function sees an array and a rate, nothing else.
  </action>
  <verify>node scratch/rolling_mean_check.mjs exits 0 and prints a pass line per assertion</verify>
  <done>AC-2 and AC-6 satisfied at the library level</done>
