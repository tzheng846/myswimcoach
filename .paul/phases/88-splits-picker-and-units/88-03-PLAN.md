<objective>
## Goal
Make the yd/m toggle actually convert the phase-metric grid. **23 of the report card's 47 registry
metrics never convert today.** Value, baseline median, usual-range band, strip domain and unit
label all move together, so a length-dimensioned metric reads in yards without inventing a flag
that did not exist in metres.

## Purpose
Reported defect 2, verbatim: *"when toggling yd vs meter the metrics don't seem to change."*
CONTEXT F6, re-counted here directly off `DISPLAY` and confirmed exactly: **17 `m/s`, 3 `m`,
2 `m/s²`, 1 `m/s³` — 23 unconverted; the other 24 (`s`, `%`, `×`, `/s`, dimensionless) are
correctly invariant.** `unit` already drives the traces, the cycle and kick hover readouts,
`CycleCharts` and `TimeToX`; it stops dead at `PhaseReportCard.js:735-747`, which hands
`RangeStrip` a hardcoded `r.disp.unit` and a raw `r.value`.

  flag model that `PhaseTimeline` renders)
- `scratch/unit_check.mjs` — headless check whose central assertion is that **nothing about the
  flags or the strip geometry changes between the two unit systems**

<decisions>
Made by me at the user's direction, 2026-08-31.

**D1 — Conversion keys off the UNIT STRING, not a per-metric list.** Four strings carry exactly one
power of length — `m`, `m/s`, `m/s²`, `m/s³` — and every other unit in the table is dimensionless
or pure time. A table of 23 metric keys would need editing every time a metric is added; a table of
4 unit strings would not. ⚠ It is only correct while no unit has a length power other than 1
(no `m²`, no `s/m`); a comment says so and the harness pins the count.

**D2 — ⚠ The verdict is computed on SI values and NEVER on converted ones. Conversion is a
display transform applied at the last moment.** This is the whole of R6. `flagVerdict` compares
value against band and `computeDomain` places the dot; scaling both sides by 1.09361 preserves the
comparison in exact arithmetic but there is no reason to expose a flag to floating-point luck at
the band edge. Keeping the model in metres makes "toggling units cannot change a flag" a
structural property rather than a hope — and AC-2 asserts it anyway, so a future refactor that
converts too early fails loudly.

**D3 — Three display sites, and the third is one CONTEXT missed.** F6 named the `RangeStrip` call
(`:735-747`). Reading the file found a fourth surface on the same card:
`PhaseTimeline.js:156-158` renders each flag as `{value}{unit} vs {median}{unit}` from the
`activeFlags` model built at `PhaseReportCard.js:459-476`. So the sites are (1) the `RangeStrip`
props, (2) `metricExplain`'s body and comparison sentence, (3) the `activeFlags` push.
`AlertSummary` only counts flags and needs nothing.

**D4 — `RangeStrip` and `PhaseTimeline` are NOT modified.** They already take `unit`, `value`,
`baseline` and `domain` as props; handing them converted numbers and a converted label is the whole
change. Pushing a factor down into them would put the conversion rule in three files.

**D5 — The factor is `1.09361`, matching every other conversion on this page.** Not `1/0.9144`
(= 1.0936133…). `PhaseReportCard.js:141`, `CycleCharts.js:176` and `page.js:291` all use
`1.09361`; `TimeToX.js` uses `YARD_TO_M = 0.9144` in the other direction. A fifth, more precise
constant would make the same metric read two different numbers on one screen. `unitConvert.js`
exports it so the next surface has one place to import from.

**D6 — The scope is this page's metric grid, per CONTEXT D10, and that leaves the portal
internally inconsistent.** Compare, group comparison, parent report and the alert summary are not
audited. Accepted; STATE item, not silence (R7).
</decisions>

<task type="auto">
  <name>Task 1: The pure conversion module</name>
  <files>web/lib/unitConvert.js</files>
  <action>
    New pure module — no React, no Next imports, node-loadable like `web/lib/windowMetrics.js`
    and `web/lib/strokeStats.js`.

    ```
    export const M_TO_YD = 1.09361;                       // D5 — same constant as every other
                                                          // conversion on this page
    const LENGTH_UNITS = { "m": "yd", "m/s": "yd/s", "m/s²": "yd/s²", "m/s³": "yd/s³" };

    export function displayUnit(unit, imperial)  ->  { factor, unit }
    export function scaleBaseline(base, factor)  ->  base | scaled copy
    ```

    - `displayUnit`: `imperial` false, or the unit not in `LENGTH_UNITS`, returns
      `{ factor: 1, unit }` — the SAME string identity where possible, so an invariant row's
      markup is provably untouched. Otherwise `{ factor: M_TO_YD, unit: LENGTH_UNITS[unit] }`.
    - `scaleBaseline`: `factor === 1` or a null/undefined base returns the input unchanged (no
      allocation, so `===` still holds). Otherwise returns a copy with `median`, `band[0]`,
      `band[1]`, `mean`, `sd`, `mad`, `sMAD` scaled and `n` carried through untouched — `n` is a
      count, and scaling it is exactly the kind of slip this function exists to prevent.
    - Header comment states D1 (keyed on the unit string, correct only while every unit carries at
      most one power of length — no `m²`, no `s/m`) and D2 (this is a DISPLAY transform; verdicts
      are computed upstream in SI and must never be recomputed from its output).

    Avoid: converting `%`, `s`, `×`, `/s` or `""`; touching `n`; introducing a second precision of
    the yard constant.
  </action>
  <verify>node -e "const u=require('...'); ..." — or a direct assertion block inside scratch/unit_check.mjs Task 3; the module must import cleanly with no React present</verify>
  <done>AC-1's rule exists in one place.</done>
