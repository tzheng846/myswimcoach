<objective>
## Goal
Collapse the session report card onto **one** definition of "0 m". Time-to-Distance moves off
`metrics_json.session.baseline_end_s` minus `athlete.head_waist_m` and onto the same raw
`phases.boundaries.dive_start_s` the split rows already use, and the card states which instant it
measured from and where that instant came from.

## Purpose
CONTEXT F5, which the user did not report and which is larger than what they did. The page holds
three anchors today. Probed live across all 99 stored sessions: `dive_start_s` and
`baseline_end_s` are both present 99/99 and the median gap is 0.003 s (index quantization,
harmless) — but **27 of 99 differ by more than 0.1 s**, tail **12.39 / 12.27 / 11.62 / 8.16 s**.
On roughly a quarter of the library, the Time-to-Distance card and the split rows a few hundred
pixels below it are measuring from instants up to twelve seconds apart, with nothing on screen
saying so.

## Output
- `TimeToX` takes `anchorS`; `headWaistM` is gone from the component entirely
- `page.js` feeds it `phases.boundaries.dive_start_s`, and the existing 61-02 D7 caveat line
  becomes the page's single statement of its anchor and that anchor's provenance
- `scratch/anchor_check.mjs` — headless render check pinning both halves of the change
</objective>

<decisions>
Made by me at the user's direction, 2026-08-31.

**D1 — Open question 2 answered: D6 does BOTH halves.** The anchor swap
(`baseline_end_s` → `dive_start_s`) *and* the head-waist retirement. F5 measured that the anchor
swap is the larger effect by an order of magnitude — up to 12.39 s against head-waist's
0.4–0.5 s — so doing only the cheap half would leave the substantial defect in place while
claiming the page had been fixed.

**D2 — The prop is RENAMED `baselineEndS` → `anchorS`.** A prop named for the old boundary while
carrying the new one is exactly the drift that produced three anchors. One caller
(`page.js:362`), verified by grep, so the rename is contained.

**D3 — ⚠ Verified, and it makes this plan far cheaper than the discussion priced it: the backend
head-waist path is ALREADY DEAD CODE.** Re-confirmed here, not taken from CONTEXT:
`metrics.time_to_distance` (`metrics.py:1415`) has zero callers anywhere in the repo or tests, and
`compute_session_metrics` (`metrics.py:1656`) takes `head_waist_m` and never references it in the
body. `TimeToX` is the only live consumer. **No recompute, no stored `metrics_json` change, no
backfill.** This plan is web-only.

**D4 — Python is NOT touched, even though it holds dead code.** `metrics.time_to_distance`,
`compute_session_metrics`'s unused kwarg, `api.py:183/228`'s form field and
`tests/test_metrics.py:156`'s kwarg-accepted test all stay. Repo convention (`.claude/CLAUDE.md`
§3): mention unrelated dead code, do not delete it. Removing the kwarg would also ripple through
seven `tests/test_api.py` call sites and `seed_demo_team.py` for zero behavioural gain. It goes in
the SUMMARY and STATE instead.

**D5 — D7's dead edit field is marked in code, once, where it is retired.** R2: the athletes page
(`web/app/app/athletes/page.js:137`) and `AddAthleteModal` keep collecting and displaying
head–waist after the last consumer stops applying it — the user's explicit call. A comment at the
retirement point in `TimeToX.js` names D7 and says the field is deliberately still writable, so
the next reader does not "fix" it back. ⚠ Deliberately NOT a comment on the athletes page: that
file is out of scope and this plan's diff should not reach it.

**D6 — `page.js:147`'s athlete select drops `head_waist_m`.** It is fetched for exactly one
purpose — feeding `headWaistM` into `TimeToX` — so leaving it in the select would be a second dead
read. `name` stays; the athlete object is used elsewhere.

**D7 — Open question 7 answered: the page states its anchor ONCE, in the caveat line that already
exists.** `page.js:366-386` (the 61-02 D7 line) already prints the start instant and says whether
it was the coach's or auto-detected. D6 makes that one line true for the whole page, so it is
upgraded in place rather than joined by a second banner over the Swimming grid. Each split's
`desc` in `DISPLAY` already says "from the dive". ⚠ R1 asks whether the change should be announced;
a one-time "these numbers moved" banner would be chrome that ages into noise within a week — the
line naming the anchor and its source IS the standing explanation.

**D8 — Provenance now reads `boundaries.sources.dive_start_s`, not
`data_quality.recomputed_from_annotation`.** Verified: `resolve_boundaries`
(`phase_metrics.py:147-153`) records exactly one of `manual` / `detected` / `auto` / `none` per
boundary. `recomputed_from_annotation` says the *session* was recomputed from marks — it does not
say the *dive_start* came from one, and after 75-03 a boundary can be `detected` on an otherwise
annotated session. Wording: `manual` → "from your marks", `detected` / `auto` → "auto-detected"
plus the existing Set-it-yourself link.

**D9 — Legacy fallback: `dive_start_s ?? baseline_end_s`, and the line SAYS SO.** All 99 stored
sessions have `phases` and a `dive_start_s` (probed), so this is theoretical — but
`PhaseReportCard` still carries a `!phases` branch, and a silent fallback to the old anchor would
recreate the two-anchor bug in exactly the place nobody looks. When the fallback fires the line
reads "no dive detected — measured from the older start estimate".
</decisions>
