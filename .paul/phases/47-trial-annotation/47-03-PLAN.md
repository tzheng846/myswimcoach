<objective>
## Goal
Instagram-style background video upload on iOS: after Record-with-Video processes, the video
uploads through an app-wide FIFO queue that never blocks navigation — the coach keeps using
the app; a small in-app toast announces "Video saved to cloud ✓" wherever they are; failures
auto-retry ×2 then leave a persistent Retry chip. VideoOverlayScreen persists the end-anchored
sync origin. Trials then open on the web annotate page with video + sync attached, hands-off.

## Purpose
Last plan of Phase 47. Videos are large (a 1–2 min .mov over poolside LTE takes real time) —
tying the upload to the results screen would freeze the coach's flow between swimmers.
Decisions (user, 2026-07-12, AskUserQuestion ×3): in-app toast (no expo-notifications dep);
FIFO one-at-a-time queue (predictable poolside bandwidth); auto-retry ×2 with backoff, then a
persistent dismissible chip with Retry.

## Contract recap (47-01/04, LIVE on Railway since 627419c)
- POST /sessions/{id}/video — multipart `file` (optional) + `video_origin_s` form field
  (optional; at least one required). Stored at videos/{session_id}.mp4 (x-upsert);
  origin-only calls just update sessions.video_origin_s. Auth = same Bearer JWT as /process.
- video_origin_s = session-clock seconds at video t=0 (end-anchor: deviceDur − videoDur).

## Key technical facts
- FileSystem.uploadAsync keeps running when the enqueueing screen unmounts (JS promise +
  native transfer); `sessionType: FileSystem.FileSystemSessionType.BACKGROUND` additionally
  survives the app being backgrounded on iOS. No new native deps.
- expo-camera records .mov (video/quicktime); endpoint stores it as {id}.mp4 — path name
  only. H.264 .mov plays in the annotate page's <video>; known playback risk, NO transcode.
- String-only FormData is Hermes-safe (the known RN crash is the {uri,name,type} FILE
  pattern — the reason RecordScreen uses uploadAsync for files).


## AC-2: FIFO queue + toast
```gherkin
Given multiple back-to-back Record-with-Video sessions
When their videos are enqueued
Then uploads run strictly one at a time in enqueue order
And each completion shows a transient in-app toast ("Video saved to cloud ✓") on whatever screen is open
And an active upload is visible somewhere unobtrusive (e.g. the toast host shows "Uploading video…" briefly on start)
```

## AC-3: Retry ×2 + persistent chip
```gherkin
Given an upload attempt fails (network/server)
When it has failed fewer than 3 times total
Then it retries automatically with backoff (~3 s, ~10 s)
When all attempts are exhausted
Then a persistent dismissible chip appears above the tab bar ("Video upload failed · Retry ✕")
And Retry re-enqueues the same job (file still on disk); dismiss removes the chip
And a failed video upload NEVER affects session results or other queued uploads
```

## AC-4: Sync origin persisted from playback
```gherkin
Given VideoOverlayScreen opened with a sessionId param
When the video duration loads and videoOriginS becomes known
Then video_origin_s = videoOriginS + manualOffsetS posts once (origin-only, string FormData)
And nudging manualOffsetS re-posts debounced (~1 s) with a small saved/failed note
And with no sessionId, no network call is attempted
```

## AC-5: Export green
