<objective>
## Goal
Make Compare actually comparable: distinguishable session names (D8), two stacked traces on their
own true sample rates with a manual alignment nudge (D9), and per-cycle line charts replacing the
metric table (D11).

## Purpose
The user's report was concrete — *"on the drop down, it's almost impossible to tell the sessions
apart when they're all the same date"*, and *"for metrics use graphs… make it easy to compare how
the two sessions differ."* Underneath that sits the last known-wrong time axis in the system.

## Output
- NEW `web/lib/sessionName.js` — deterministic mnemonic labels, render-time only
- `CompareChart` rebuilt as two stacked panels on true per-session rates, with an offset nudge
- `MetricDeltaTable` replaced by per-cycle overlays
- `61-04-SUMMARY.md`
</objective>

## AC-1: Same-day sessions are distinguishable
```gherkin
Given an athlete with three sessions recorded on the same date and no typed names
When the coach opens the session dropdown on Compare
Then each option is a distinct, stable, human-readable string
And reloading the page yields the same label for the same session
And no write occurs to sessions.name
```

## AC-2: Each trace is drawn on its own true sample rate
```gherkin
Given two sessions with recorded sample_rate_hz
When Compare renders their traces
Then each x-axis is derived from that session's own rate, not a hardcoded 100
And a session with NULL sample_rate_hz falls back to 100 exactly as it always has
```

## AC-3: Two stacked panels, alignable by hand
```gherkin
Given two selected sessions
When Compare renders
Then each trace occupies its own panel, stacked, sharing a common time axis
And an offset control shifts one relative to the other
And the offset is in-memory only — nothing is written to the database
And resetting the offset returns both to their recorded alignment
```

## AC-4: Per-cycle comparison replaces the metric table
```gherkin
Given two sessions with cycles in metrics_json
When Compare renders
Then per-cycle line charts show both sessions overlaid per metric
And each series is colour-matched to its trace panel
And no metric delta TABLE is rendered
And a session with no cycles degrades to a message, not a crash
```

  <files>web/lib/sessionName.js, web/app/app/compare/page.js</files>
  <action>
    NEW `web/lib/sessionName.js`: `sessionLabel(session)` returning a stable mnemonic derived from
    `session.id`, e.g. `Amber Otter`. Use a small adjective list × noun list and a simple
    deterministic string hash of the id — same id must always yield the same pair, across reloads
    and across machines.

    ⚠ **DERIVED AT RENDER TIME. NEVER WRITTEN.** `sessions.name` is coach-editable and PATCHable;
    writing generated names into it would silently clobber names the coach typed. When a session
    HAS a typed name, prefer it and show the mnemonic as secondary.
    Compose the full option as mnemonic + typed name (if any) + time, so two sessions on one date
    differ in more than one place. Include the TIME, not just the date — that is what actually
    separates same-day sessions.

    Extend both Compare queries to select what the rest of the plan needs and the page currently
    lacks: `sample_rate_hz` (AC-2), `cycles:metrics_json->cycles` (D11), and keep
    `session:metrics_json->session`. The picker query needs `id, created_at, name` only.

    ⚠ MEASURED AT PLAN TIME, and it changes what AC-2 is worth: of 62 live sessions, **56 are
    90.0 Hz and 6 are NULL — none differ from each other.** So today the 100 Hz assumption is an
    ~11% error applied EQUALLY to both traces, not a differential misalignment. Fixing it is still
    correct and removes the last hardcoded rate on the web, but do NOT write up this plan as having
    fixed a visible two-rate skew; that case does not currently exist in the data.
  </action>
  <verify>npm run build clean; the same session id yields an identical label across reloads; two same-day sessions render distinct option strings; grep shows no PATCH/update of sessions.name</verify>
  <done>AC-1 satisfied; data available for AC-2 and AC-4</done>
</task>

<task type="auto">
  <name>Task 2: Two stacked traces on true rates, with a manual offset</name>
  <files>web/components/portal/CompareChart.js</files>
  <action>
    Rebuild `CompareChart` as TWO stacked recharts panels, one per session, sharing a common time
    axis so features line up vertically. Stacking is what makes "line up" readable — overlaying two
    similar shapes is hardest to read exactly when the comparison matters.

    ⚠ `CompareChart.js:28` currently builds `t: Math.round(i)/100` — a hardcoded rate for BOTH
    series. Each panel now derives its own `t` from that session's `sample_rate_hz`, falling back
    to 100 only when NULL (matching `sessions/[id]/page.js:120` — never invent a rate).
    ⚠ Update the CLAUDE.md note that calls the 100 Hz assumption here deliberate; that reasoning
    ("two sessions may have two rates, so there is no single axis") is superseded — stacked panels
    give each series its own axis, which is precisely the answer.

    Add an offset control shifting session B relative to A, applied by adding the offset to B's
    time values at render. **In-memory only — no persistence, no DB write** (matching the mobile
    start-marker precedent). Include a reset to zero, and show the current offset numerically.

    Keep each panel's colour: A `#2196f3`, B `#f59e0b` — Task 3 and a later video plan both key off
    these, so define them once and export them rather than repeating the hex.
  </action>
  <verify>npm run build clean; a session with NULL sample_rate_hz renders identically to before; a non-zero offset visibly shifts only panel B; reset restores alignment</verify>
  <done>AC-2, AC-3 satisfied</done>
</task>

<task type="auto">
  <name>Task 3: Per-cycle overlays replace the metric delta table</name>

    Render the same four metrics 61-02 settled on — `dist_m`, `coast_fraction`, `duration_s`,
    `arm_peak_vel` — with both sessions overlaid per panel, coloured to match their trace panels.
    X is cycle number; the two sessions will have DIFFERENT cycle counts, so the shorter series
    simply ends earlier. Do not pad, truncate, or resample to a common length — that would invent

    fits the visual brief, or state plainly in the SUMMARY that deltas were dropped. Do not let it
    vanish silently.

    ⚠ Sessions with no cycles (measured: 8 of 62 live rows) must render a message, not crash.
    ⚠ 61-02's legacy-vintage caption rule applies per session here — two sessions may be of
    DIFFERENT vintages, so the caveat is per-series, not per-panel. If that proves awkward, state
    the compromise rather than silently showing one session's caveat for both.
  </action>
