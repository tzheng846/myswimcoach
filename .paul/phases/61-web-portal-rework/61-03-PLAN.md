<objective>
## Goal
Give session video a front door on the web: a read-only `/app/sessions/[id]/video` route reachable
in one click from the report card (D1), with a chart that follows the playhead (D16), an upload
input when no video is attached (D13) — and a `video_origin_s` the web computes for itself instead
of silently defaulting to 0 (D2, **closing 58-04**).

## Purpose
The user's first ask was a button "so that it's not just hidden behind annotations". Shipping that
without D2 would surface a video that is silently out of sync on exactly the sessions it exists
for — 58-04 has been owed and homeless since 2026-08-07, and this is its home.

## Output
- NEW `/app/sessions/[id]/video` — `VideoPane` + windowed `VelocityChart`, no annotation tools
- `▶ Video + Velocity` on the report card
- `VideoPane` computing an end-anchored origin, never overwriting a stored one
- `VelocityChart` gaining an optional `viewRange`, backward-compatible
- `61-03-SUMMARY.md`
</objective>

<task type="auto">
  <name>Task 1: End-anchored origin in VideoPane — closes 58-04</name>
  <files>web/components/portal/VideoPane.js</files>
  <action>
    `VideoPane.js:27-28` is the whole defect: `useState(video?.origin_s ?? 0)`. A session whose
    `video_origin_s` is NULL — every session whose footage arrived via the mobile background
    upload queue, which posts the file without an origin — lands at 0 and is silently unsynced.

    Add a `sessionDurationS` prop and mirror the mobile rule exactly:
      endAnchoredOriginS = sessionDurationS − videoDurationS      // video's first frame
      effectiveOriginS   = storedOrigin ?? endAnchoredOriginS     // stored ALWAYS wins
    `videoDurationS` comes from the `<video>` element's `onLoadedMetadata`.

    ⚠ USE `??`, NOT `||`. A stored origin of exactly 0 is a real, deliberate value and must not be
    treated as absent. This is the single most likely way to reintroduce the bug.

    Persist once when — and only when — nothing was stored: POST `/sessions/{id}/video` with
    `video_origin_s` via the existing `apiUpload` path, then call `onVideoChange`. Guard with a ref
    so it fires once per mount.
    ⚠ Phase 60-03 hit a real bug here worth not repeating: its nudge-save was gated on the same ref
    the auto-post set, so skipping the auto-post silently swallowed the user's first manual nudge.
    Keep the auto-save guard and the manual-save path on SEPARATE refs.

    Until video metadata loads, `endAnchoredOriginS` is unknown. Do not fall back to 0 in the
    meantime — hold the origin as null and let the existing "Loading video…" state cover it, or the
    trace will jump when metadata arrives.

    Show which origin is in effect (stored vs computed) in the existing sync row — mobile added the
    same debug line in 60-03 and it is the only way to diagnose a bad sync from the UI.

    ⚠ SHARED COMPONENT: the annotate page renders this too, and inherits the fix. That is 58-04's
    entire point. Everything else about VideoPane must behave identically (AC-7).
  </action>
  <verify>npm run build clean; grep -n "origin_s ?? 0" VideoPane.js returns nothing; annotate page still renders video, seek, frame-step, speed and Save</verify>
  <done>AC-2, AC-3 satisfied; AC-7 protected</done>

<task type="auto">
  <name>Task 2: Optional viewRange on VelocityChart, proven not to change the report card</name>
  <files>web/components/portal/VelocityChart.js</files>
  <action>
    Add an optional `viewRange = null // [lo, hi] in seconds` prop. Use the SAME name and shape as
    `AnnotationChart.js:67`, which already does this — a second spelling of one concept in the same
    folder is how these two drift apart.

    When `viewRange` is null the component must behave EXACTLY as today. When set, restrict the
    plotted domain to [lo, hi].

    ⚠ Downsampling order matters and is the mobile lesson from 60-02: `MAX_POINTS` is applied
    across the whole trace first, so a 2 s window of a 47 s trace keeps only the handful of points
    that survived that pass. Filter to the window BEFORE the stride is chosen, so a narrow window
    gets a dense trace. Record the measured before/after point count in the SUMMARY.

    ⚠ Pin the y-domain to the FULL trace when windowed. Recomputing min/max from the visible slice
    makes the trace rescale on every frame during playback — 60-02 hit exactly this.

    ⚠ Hide the `<Brush>` when `viewRange` is set: a brush and a controlled window fight each other
    for the same axis. 60-02 kept them apart on mobile for the same reason.

    AC-5 IS THE GATE: capture the rendered point array for a real session before and after this
    change with `viewRange` absent, and prove them identical. Phase 60-02 did this by transcribing
    the old algorithm from git rather than from memory; do the same — `git show HEAD:web/components/portal/VelocityChart.js`.
  </action>
  <verify>npm run build clean; node comparison shows the unwindowed point array is identical pre/post; windowed point count measured and recorded</verify>
