<objective>
## Goal
Fix the bug where **no iOS session saves to the cloud**. The live Supabase
`sessions.device_id` column is type **UUID**, but `api.py /process` writes the device's
**chip-id string** (e.g. `"64CD4D"`) into it, so the row insert fails with
`invalid input syntax for type uuid: "64CD4D"` (Postgres 22P02). Because the save is
non-fatal, the swimmer sees the full report, then a `⚠ Save failed:` line and the session
never reaches Supabase. Migrate `sessions.device_id` UUID → TEXT (the shape the rest of
the system already assumes) so the insert succeeds.

## Purpose
Sessions not persisting = total data loss for every recording and breaks the product's
core promise ("session auto-stored and visible within 30 s"). It also blocks downstream
features: saved-session history, the Phase-36 ratings endpoint, parent reports, and the
Phase 39-05 **Advanced segmentation overlay** (which only renders on a *saved* session's
ReportCard → Advanced view — the user's "advanced segmentation view is gone" is a direct
symptom of this same bug).

## Output
- `supabase/patch_06_sessions_device_id_text.sql` — idempotent, user-applied migration.
- No application-code change: `api.py` already writes the chip id, which is correct once
  the column is TEXT (the devices table is chip-id-keyed per patch_04).
</objective>

## Root cause (confirmed 2026-06-22 via on-device error text)
- Error: `invalid input syntax for type uuid: 64CD4D` (code 22P02). `64CD4D` = chip id
  derived from the BLE name `SwimLogger-64CD4D` (../swimnetics-mobile BleContext.js:79-80),
  sent as the `device_id` form field (RecordScreen.js:240).
- `api.py` /process writes `session_row["device_id"] = device_id` (the chip-id string) at
  api.py:290, then `sb_admin.table("sessions").insert(...)` at api.py:292 → fails.
- Live `sessions.device_id` is still **UUID REFERENCES devices(id)** (original schema.sql:56).
- The intended migration (UUID→TEXT chip id) was DOCUMENTED in patch_04_backfill.sql:20-42
  but **never executed** against the live DB — the 22P02 error proves the column is still UUID.
- The FK target `devices(id)` is itself stale: Phase 14 reshaped `devices` to a chip-id PK
  with NO `id` column (patch_04:44-64), so the UUID FK is already meaningless. TEXT is correct.
