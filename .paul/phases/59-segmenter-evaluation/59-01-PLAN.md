<objective>
## Goal
Build the first instrument in this repo that can answer **"is this segmenter better than that one?"** —
a pure scoring module, a CLI that runs it over the 23 annotated sessions, and a checked-in fixture
driving a pytest regression. Score three candidate segmenters (wavelet / trough / peak-pick) against
human cycle boundaries, and score `detect_phases` + `detect_initial_phase` against the four human
phase markers, on **both** the annotated window and the production window.

## Purpose
`segmentation_reliable = False` (`metrics.py`) is a hardcoded constant, not a measurement. Phase 16-05
shipped the wavelet segmenter to production for all four strokes at self-declared "placeholder
quality" and nothing since has been able to quantify that. 23 annotated sessions now exist. Until
scoring exists, every downstream decision — tune vs replace, per-stroke routing, whether the
freestyle cycle rate is wrong by a factor — is an argument rather than an experiment.

## Output
Four NEW files. **No product code path is touched by this plan.**
- `segmenter_eval.py` — pure scorer (no I/O), mirrors the `metrics.py` / `ratings.py` / `annotations.py` convention
- `tools/score_segmenter.py` — CLI, mirrors `tools/schema_contract.py`
- `tests/fixtures/segmenter_truth.json` — 4 sessions, full traces + labels
- `tests/test_segmenter_eval.py` — unit tests + an offline regression pinning the scores
</objective>

<task type="auto">
  <name>Task 1: Pure scoring module + unit tests</name>
  <files>segmenter_eval.py, tests/test_segmenter_eval.py</files>
  <action>
    Create `segmenter_eval.py` at repo root. Pure functions only — no I/O, no network, no
    plotting, no argparse. Same convention as metrics.py / ratings.py / annotations.py.

    Public API:
    - `match_series(pred_s, truth_s, tol_s)` → `(pairs, unmatched_pred, unmatched_truth)`.
      **Use OPTIMAL assignment, not greedy.** Build a cost matrix of |pred − truth|, mask
      entries above `tol_s`, and solve with `scipy.optimize.linear_sum_assignment` (scipy is
      already a dependency via metrics.py). ⚠ A greedy matcher is order-dependent and will
      silently produce a different F1 for the same data — the plan's own preliminary numbers
      were greedy and must not be reproduced that way.
    - `score_series(pred_s, truth_s, tol_s)` → dict with `n_pred`, `n_truth`, `matched`,
      `precision`, `recall`, `f1`, `mae_s`. Empty pred or empty truth must return zeros, not
      NaN or a division error.
    - `sweep(pred_s, truth_s, tolerances)` → list of per-tolerance score dicts.
    - `coverage(marks_s, window_start_s, window_end_s)` → the D4 statistic:
      `n_marks / (window_span / median_ISI)`, plus the median ISI it used. Fewer than 3 marks
      → return `None` for the ratio (do not fabricate one from a 2-point ISI).
    - `aggregate(per_session_scores, exclude_ids)` → per-stroke rollup. Excluded sessions
      contribute to recall totals ONLY; they are dropped from precision and F1. Return the
      excluded ids in the result so the caller can print them.

    ⚠ Name the series generically (`score_series`, not `score_marks`) and key results by a
    caller-supplied label. Underwater-kick segmentation is coming and must be a caller change,
    not a rewrite of this module (CONTEXT D11).

    In `tests/test_segmenter_eval.py`, add unit tests with hand-constructed inputs:
    perfect match; all-miss; a duplicate prediction that must consume only ONE truth; a case
    where greedy and optimal assignment disagree (assert the optimal answer); empty inputs on
    both sides; coverage on a fully-labeled vs half-labeled synthetic mark list.
  </action>
  <verify>python -m pytest tests/test_segmenter_eval.py -q</verify>
  <done>AC-1 satisfied: scorer is pure, optimal, and matches hand-computed values.</done>
</task>

<task type="auto">
  <name>Task 2: CLI that scores cycles and phases over the live corpus</name>
  <files>tools/score_segmenter.py</files>
  <action>
    Create `tools/score_segmenter.py`, modelled on `tools/schema_contract.py` (module docstring
    with a Usage block, no import side effects) and `fetch_annotations.py` (Supabase access).

    ⚠ COPY THE sys.path HACK from fetch_annotations.py:22 verbatim — the local `supabase/`
    SQL directory shadows the installed supabase-py package when running from the repo root.
    Without it the import fails in a way that looks like a missing dependency.

    Data acquisition:
    - Default: fetch from Supabase with the service-role key (same env vars as
      fetch_annotations.py). Pull `session_annotations` plus `sessions.id, stroke_type,
      created_at, sample_rate_hz, velocity_profile, metrics_json, metrics_json_auto`.
    - `--export PATH` reads a previously saved JSON instead, so the tool runs offline.
    - `--out PATH` writes the full per-session report as JSON (default `segmenter_report.json`).
    - `--tol` (default 0.15) and `--sweep` (default 0.05,0.10,0.15,0.20,0.30).

    Sample rate: use `sessions.sample_rate_hz`; when NULL fall back to `annotations.FS_HZ`.
    ⚠ Do NOT backfill or assume 89.9 — the two June sessions genuinely ran at ~100 Hz
    (2033 samples ÷ 20.3 s lap = 100.1), so the fallback is correct for them.

    CYCLE SCORING — for each session, run three candidates and score their boundaries against
    the human cycle boundaries (`marks[0::k]`, k from `annotations.marks_per_cycle(stroke_type)`),
    AND against all human marks (arm entries). Report both framings; they are different questions
    and the wavelet scores very differently on each.
      - `metrics.segment_cycles_wavelet(t, vel)`
      - `metrics.segment_cycles_trough(t, vel, T_est)` where `T_est = metrics._estimate_period(t, vel)`
      - a peak-pick baseline built HERE (not in metrics.py): `find_peaks` on
        `metrics._detrend_for_cwt(vel, fs)` with a prominence floor scaled off the window's
        95th percentile and a minimum distance from `T_est`.
    ⚠ All three return `None` for short/flat input. Treat None as ZERO predictions and count
    how often it happens — do not crash and do not silently drop the session.
    Boundaries from a cycle list = every `start_idx`, plus the final `end_idx`.

    TWO WINDOWS, both scored:
      - ANNOTATED: `vel[stroke_start_s*fs : finish_s*fs]` — isolates the segmenter.
      - PRODUCTION: `vel[ip_end : swim_end]` derived by running `metrics.detect_phases` and
        `metrics.detect_initial_phase` exactly as `compute_session_metrics` does.
    The gap between them is how much error belongs to phase detection rather than segmentation.
    Nothing has ever separated the two.

    PHASE SCORING — predicted phase times come from
    `annotations.build_seed(metrics_json_auto, fs_hz)`, scored against the human `phases` dict,
    per marker, with signed error as well as absolute.
    ⚠⚠ **MUST use `metrics_json_auto`, never `metrics_json`.** For every annotated session
    `api.py:889` has already OVERWRITTEN `metrics_json` with metrics recomputed FROM the human
    annotation. Seeding from it and scoring against that same annotation is circular and would
    manufacture a near-perfect score. Sessions with a NULL `metrics_json_auto` (never
    recomputed, so metrics_json is still the auto result) are scorable; sessions where both are
    ambiguous must be reported as unscorable-for-phases, with a count.

    OUTPUT: per-stroke tables to stdout (cycles ×2 framings ×2 windows; phases per marker),
    plus a per-session line carrying n_marks, the D4 coverage statistic, and
    |auto_spm − human_spm| / human_spm. Write the same data to `--out` as JSON.
  </action>
  <verify>python tools/score_segmenter.py --out segmenter_report.json — exits 0, prints per-stroke tables for all three segmenters on both windows, and the phase-marker table; report JSON contains one record per annotated session</verify>
  <done>AC-2 and AC-3 satisfied: cycles scored 3 ways on 2 windows; phases scored from metrics_json_auto.</done>
</task>
