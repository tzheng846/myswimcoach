<objective>
## Goal
RecordingConfigScreen gains a device picker fed by BleContext's paired devices; RecordScreen drops its own BleManager/scan/connect machinery and is rebuilt around firmware 1.1.0's buffer-and-dump protocol: remote START/STOP, then META → clock correlation (`sessionStartPhoneMs`) → DUMP retrieval → save/upload exactly as today, now including `device_id`.

## Purpose
Completes Phase 21 (pair once, connection survives navigation) AND delivers the iOS half of the Phase 22 sync architecture in the same RecordScreen rewrite — avoiding two back-to-back rewrites of the same file. After this plan, a swimmer can button-record with no phone present, and any phone retrieves the session afterward with the wall-clock offset needed for video overlay. 22-02 then becomes pure validation (record real footage, run video_sync.py, assess).

## Scope note (deviation from original 21-02 description)
The original 21-02 scope ("RecordScreen drops scan/connect UI, reads device from context") implicitly assumed the live-streaming firmware. Firmware 1.1.0 (Phase 22-01) replaced live streaming with buffer-and-dump, so this plan refactors RecordScreen onto the protocol that actually exists. The live in-swim velocity graph (Phase 13-03) is inherently unavailable in dump mode and is removed; samples arrive only at retrieval.

- `RecordScreen.js` — no local BleManager; states driven by BleContext; remote record + retrieve flows; `sessionStartPhoneMs` computed and surfaced; `device_id` (chipId) sent to /process

## Protocol reference (firmware 1.1.0, bench-verified)
- Device name: "SwimLogger-<chipID>" (6-hex-char chip ID)
- RX commands (write-with-response, trailing \n): START, STOP, META, DUMP, REEL_ON, REEL_OFF
- TX notify packets:
  - Samples: any non-zero multiple of 7 bytes, <IHB per sample (timestamp_us u32 LE, angle u16 LE, magnet u8)
  - META response: exactly 8 bytes = [session_start_us u32 LE][device_now_us u32 LE]; start==0 → no session buffered
  - End-of-dump marker: exactly 1 byte 0xEE
- Recording runs on-device independent of BLE; DUMP clears the buffer on success, retains it if disconnected mid-dump

## AC-4: Retrieval with clock correlation
```gherkin
Given the device holds a buffered session (button- or app-recorded)
When retrieval runs (auto after Stop, or via the "Retrieve from Device" button)
Then the app subscribes to TX, writes "META\n", and on the 8-byte response records
  phoneNowMs = Date.now() and computes
  sessionStartPhoneMs = phoneNowMs - (((deviceNowUs - sessionStartUs) % 2^32 + 2^32) % 2^32) / 1000
And if session_start_us == 0, the user sees "No session on device" and returns to ready
Then the app writes "DUMP\n", accumulates sample packets (existing parsePacket), and on the
  1-byte 0xEE marker saves the CSV and uploads to /process as today
And the results screen displays sessionStartPhoneMs (ISO string) and it is console-logged
And a retrieval that stalls >30 s without the end marker saves what arrived with a warning
```

## AC-5: device_id reaches the backend
```gherkin
Given the connected device's chipId is known (from BleContext knownDevices)
When the CSV is uploaded to /process
Then the multipart parameters include device_id = chipId
And the session row in Supabase gets device_id populated (Phase 14 auto-registration path)
```
