# Spike: Pan Matrix Profile / motif-heatmap as a length-agnostic segmentation candidate

## Context

Plans 16-01 and 16-02 ([16-01-SUMMARY.md](16-01-SUMMARY.md),
[16-02-SUMMARY.md](16-02-SUMMARY.md)) converged on one diagnosis:
single-template motif-matching **"regime-locks"** — it (a) captures one local
pace/shape, *and* (b) uses one **fixed window length `m_len`**, derived once
from a single global `T_est`, so when stroke *rate* drifts, a fixed-length
window samples a different fraction of the cycle at different points in the
swim. Neither tried alternative escapes this — chains *relocate* the lock
rather than break it, Arc Curve/CAC is structurally inapplicable on short
sessions — leaving the wavelet/CWT ridge as the strongest standing
recommendation, plus a flagged-but-untried "dive/pulldown re-masking" probe.

The user then surfaced *"Matrix Profile XX: Finding and Visualizing Time
Series Motifs of All Lengths using the Matrix Profile"* (Madrid et al., UCR).
It names **exactly** defect (b) as a known general problem — "a poor choice
of \[subsequence length] can result in failing to find unexpected...
regularities... the user may have no idea as to the subsequence lengths at
which patterns are conserved" — and proposes the fix: the **Pan Matrix
Profile (PMP)**, matrix profiles computed across a *range* of lengths, read
via a **motif-heatmap** (length × time, color = conservation strength) so a
human can see at a glance which lengths/windows contain repeated structure,
without picking `m` in advance. If `leo_br_1` truly contains a "fast-stroke
shape" and a "slow-stroke shape" the way 16-01 hypothesized, this is a direct
way to *see* whether they form separate, well-conserved bands at *different*
lengths — turning an eyeballed hypothesis into a checkable visualization, and
potentially re-posing "single template, one regime" as something more useful:
a length-aware, data-driven answer to "how many regimes, and what shape/length
is each" (the open question that made `stumpy.motifs()`, 16-01's #2 and
weakened further in 16-02, unappealing).

**This isn't just "a relevant paper"** — `stumpy` (already a project
dependency since 16-01) ships `stumpy.stimp`, whose docstring states *"This
is based on the SKIMP algorithm"* and links `DOI: 10.1109/ICBK.2019.00031` →
`.../PAN_SKIMP%20(Matrix%20Profile%20XX).pdf` — **the exact PDF the user
attached**. A maintained, ready-to-call implementation of this paper's
central algorithm is already installed and importable (confirmed
empirically: `stumpy.stimp(T, min_m=, max_m=, step=, percentage=)` →
`.update()` in a loop → `.PAN_` / `.M_`, built on the same `stump`/`scrump`
primitives `find_motif_anchors` already validates NaN-masking against). The
paper's own novel contribution — SKIMP's anytime convergence — solves a
scale problem we don't have (its benchmarks run n = 525,600 / 16,326 / 8,330;
our active regions run to the low thousands at most), so `stimp` can simply
be driven to full/exact convergence here. Net: the most concrete new lead
since 16-02 concluded, and unusually cheap to test — an existing, installed,
paper-linked function call, not a new implementation effort.

This plan does **not** assume PMP is the answer — like 16-01/16-02, it's a
bounded spike to determine, by building it and reading real output, whether
searching across lengths surfaces the multiple shape-"regimes" the diagnosis
hypothesizes well enough to carry toward production, or whether (like
chains/CAC) it confirms the diagnosis without resolving it. It would not, on
its own, solve "how do you merge several match-lists into one coherent cycle
list," nor touch the dive/pulldown contamination 16-02 found (though a
contaminated stretch might show up as a conserved-nowhere column — a free,
independent echo of `detect_initial_phase`'s boundary, worth noting if seen).
It's also complementary to, not competing with, the wavelet/CWT front-runner:
a motif-heatmap (length × time) and a CWT scalogram (scale/frequency × time)
are structurally similar 2-D views that may both be tracking the same
underlying quantity — instantaneous stroke period over time — via unrelated
mechanisms; agreement between them would be strong cross-validation,
disagreement would itself be informative.

## Steps

Same boundary as 16-01/16-02: standalone spike file only, no production-file
changes, reuse established masking/conventions, human-eyeball checkpoint (no
automated pass/fail).

### 1. Compute the PMP on the masked active region
Call `stumpy.stimp(vel_masked, min_m=, max_m=, step=)` on the **same**
NaN-masked `vel_masked` `find_motif_anchors` already builds and validates
([segment_motif_spike.py:126-128](../../../segment_motif_spike.py#L126-L128))
— the same reuse-not-recompute rationale `find_chain_anchors`/
`find_regime_change` already follow for `mp`. Confirm masked input is
handled the same way `stump` already is (it should be — `stimp` is built on
`stump`/`scrump` — but verify empirically first, the same care 16-02 took
before trusting CAC's output).

**Length range — anchor to an existing, validated bound, not a new one**:
`metrics._estimate_period` already searches ACF peaks between **0.5 s and
4.0 s** ("the physically possible range for breaststroke \[15-120 SPM]")
([metrics.py:534-541](../../../metrics.py#L534-L541)). Convert to samples via
the session's own `fs` for `min_m`/`max_m` — a bound the production code
already chose for this exact purpose, not one invented for this spike.

**`step` and `percentage` — tune empirically, but start informed**: the
paper's `step=1` targets ranges of thousands of samples on n in the hundreds
of thousands; our range (≈50-400 samples) and n (hundreds to low thousands)
are smaller by orders of magnitude, but `step=1` would still mean roughly 350
self-joins per session. Time one session first; a coarser step (e.g. 5-10
samples) likely keeps the full sweep in spike-territory, since
regime-locking's diagnosed length-drift is plausibly tens-of-samples /
fractions-of-a-second, not single-sample, in scale. Prefer `percentage=1.0`
(exact `stump`, not approximate `scrump`) — the whole point of the heatmap is
letting a human spot *faint* secondary bands, which approximation noise could
obscure, and n is small enough that "exact" shouldn't be expensive here.

### 2. Visualize as a motif-heatmap
Plot `pmp.PAN_` (rows = `pmp.M_` lengths, columns = time index) as a 2-D
heatmap, restricted/labeled to the active-swim region — the paper's central
"see conserved structure at a glance" tool. 16-02's mid-checkpoint lesson
("having red green and gray line is too confusing... one method per row")
argues for its own clearly-separated figure/section rather than folding a
2-D heatmap into the existing line-trace grid — a heatmap is a visually
distinct kind of object from a velocity-trace overlay.

Per-session checkpoint questions (mirrors 16-01/16-02's "eyeball it"
protocol, no automated pass/fail): does the heatmap show **multiple,
distinct, well-conserved length-bands** — visual evidence of more than one
stroke-shape "regime," each with its own native length? Mark the current
single `m_len` on the heatmap for reference — where do any extra bands sit
relative to it, and relative to where today's motif anchors are concentrated
vs. absent (`leo_br_1`'s "fast strokes only")?

### 3. (Conditional, cheap) Probe a heatmap-suggested length
If Step 2 shows a clearly distinct second band at some length `m'` ≠ today's
`m_len`: re-run the existing template→match logic (`find_motif_anchors`'s
`stumpy.stump` + `stumpy.match` steps,
[segment_motif_spike.py:133-139](../../../segment_motif_spike.py#L133-L139))
at `m'`, convert via the existing `_anchors_from_marks`
([segment_motif_spike.py:61-84](../../../segment_motif_spike.py#L61-L84)),
and overlay it the same way trough/motif/chain are today. Tests the practical
question directly — does a heatmap-informed length spread anchors across more
of the session (e.g. picks up `leo_br_1`'s slow strokes) — not just produce a
nicer picture.

### 4. Re-run + checkpoint
Same 11-session set 16-02 ended on (`leo_br_1`, `carlos_fr_1`, `carlos_fl_1`,
`swim_lucas_fl_1`, `sid_br_1/2`, `jimmy_br_1`, `connor_br_1..4`). Present the
heatmaps (+ any Step-3 overlay); user reads what they see per session — same
human-verify protocol as both prior spikes.

## Out of scope
- **Dive/pulldown re-masking** — 16-02's own still-pending recommendation
  ("worth a cheap, fast, independent look"). Deliberately not folded in here:
  it's an independent variable (cleaner input vs. better search), and
  bundling it would make this spike's read ambiguous — a messy heatmap could
  mean "PMP doesn't help" *or* "the input was contaminated," with no way to
  distinguish. Keep it its own follow-up regardless of this spike's outcome.
- **Implementing PMP/SKIMP from scratch** — moot; `stumpy.stimp` already *is*
  this paper's algorithm, already installed, already importable.
- Any change to production files (`metrics.py`, `vel_acc_extraction.py`,
  `api.py`) — same boundary both prior plans held.
