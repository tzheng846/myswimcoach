# Spike: Time-series chains + Arc Curve as drift-tolerant segmentation candidates

## Context

Plan 16-01's spike ([16-01-SUMMARY.md](16-01-SUMMARY.md)) found that naive
single-template matrix-profile motif-matching (`stumpy`: self-join → consensus
template → `match`) does not produce usable stroke-cycle segmentation. After fixing
an initial baseline-hijacking bug, a deeper problem surfaced — **"single-template
regime-locking"**: the self-join's one global-minimum template captures only one
local pace/shape, and matching then finds only recurrences of *that exact shape*,
missing strokes elsewhere that look different because **swim sessions aren't
stationary** — pacing, fatigue, and effort drift stroke shape over the course of a
swim.

Two tools from the matrix-profile literature, surfaced in research since that spike
concluded, map onto this *specific* "continuous drift" structure far more directly
than "add more templates" — a path this plan deliberately does not pursue (see Out
of scope):

- **Time series chains** (`stumpy.atsc`/`allc`) — defined as a sequence of motifs
  that gradually evolve link-to-link (A resembles A′, A′ resembles A″, and the chain
  as a whole may drift far from where it started). That is close to a textbook
  description of "pacing/fatigue drift stroke shape over a swim." Unlike
  multi-template, a chain has no "how many regimes" parameter — it follows drift
  wherever it leads — and *is* already a single ordered sequence, so there's no
  multiple-match-list merge problem to solve.
- **Arc Curve / Corrected Arc Curve** (`stumpy.fluss`, the mechanism behind FLOSS —
  "Matrix Profile VIII", Gharghabi et al.) — finds where a *continuously-repeating,
  same-type* signal's sub-population shifts. Worked example from the paper: a
  recording that is entirely heartbeats, before *and* after bleeding is induced in
  the subject — CAC still finds a clean valley at the moment bleeding began, because
  "most healthy beats have a nearest neighbor that is another healthy beat, most
  bleeding beats have a nearest neighbor that is another bleeding beat." That is a
  much closer structural twin to "fast-stroke-shape vs. slow-stroke-shape" than
  anything tried in 16-01 — and gives an independent, principled way to *test*
  (rather than visually guess at) whether `leo_br_1` really contains two
  shape-sub-populations the way Round 2 hypothesized.

Both tools consume outputs the existing self-join **already computes and currently
discards**: `find_motif_anchors`'s `mp = stumpy.stump(vel_masked, m_len)`
([segment_motif_spike.py:95](../../../segment_motif_spike.py#L95)) returns a
4-column array — `mp[:, 1]` (profile index, what `fluss` needs) and `mp[:, 2:4]`
(left/right indices, what chains need) sit there completely unused; only
`mp[:, 0]` is read today. **No new self-join, no new dependency** — `allc`, `atsc`,
and `fluss` are already importable from the installed `stumpy` (verified against
the env: `fluss(I, L, n_regimes, excl_factor=5, custom_iac=None)`,
`atsc(IL, IR, j)`, `allc(IL, IR)`).

## Steps

### 1. Thread the unused matrix-profile columns out of `find_motif_anchors`
`mp`'s columns 1–3 (`profile_idx`, `left_idx`, `right_idx`) are computed inside
`find_motif_anchors` and thrown away today (only `mp_distance = mp[:, 0]` survives
the function's return). Return them — or the raw `mp` array — alongside the
existing `(anchors, mp_distance, baseline_end, swim_end)` so the two analyses below
reuse the *same* self-join rather than recomputing it. `stumpy.stump` is the
expensive step here (numba JIT + the join itself); recomputing it twice more per
session would be pure waste, and would also risk the two new analyses silently
operating on a different `vel_masked`/`m_len` than the one already validated.

### 2. Chain discovery
Restricted to the active-swim region (the existing `[baseline_end, swim_end)`
bounds — same masking rationale as 16-01, no new threshold logic):
- `stumpy.allc(IL, IR)` using `mp[:, 2]`/`mp[:, 3]` → the all-chain set and the
  single longest unanchored chain
- Convert the chain's member indices into the same `{cycle_num, peak_idx,
  start_idx, end_idx}` shape `find_motif_anchors` already produces, so it overlays
  through the existing `_add_overlay` machinery with a third color/style
- Print chain length + member start indices (mirrors the existing
  `template_idx`/`matches` diagnostic prints — same "show your work" convention)

### 3. Arc Curve / CAC
Restricted to the same active-swim region, using `mp[:, 1]` and the already-known
`m_len`:
- `stumpy.fluss(I, L=m_len, n_regimes=2)` → corrected arc curve + candidate
  regime-change location(s)
- Add a third subplot row (alongside velocity and matrix-profile distance) plotting
  the CAC curve with a vertical marker at the detected regime-change index

### 4. Re-run + visual read
Re-run across the same sessions 16-01 used (`leo_br_1`, `carlos_fr_1`, `carlos_fl_1`,
`swim_lucas_fl_1` — excluding `swim_lucas_fr_1` per prior user direction: "the other
three are fine"). Per-session questions to read visually (same "eyeball it"
criterion as 16-01 — no automated pass/fail):
- **Chains** — does the discovered chain span more of the active-swim region than
  the single template's matches did? In particular, does it pick up `leo_br_1`'s
  "slower paced" strokes the single template missed?
- **CAC** — does the curve show a valley, and does its location land near where the
  single-template's matches dried up (`leo_br_1`, ~t = 20 s — where the
  matrix-profile-distance curve's periodic dips were noted reaching back to
  ~t = 14 s)?

### 5. Checkpoint — human-verify
Present the overlay plots; user describes what they see per session (same protocol
as 16-01's checkpoint). This determines whether either tool produces a visibly
better candidate worth carrying into a production design — or whether both confirm
the "non-stationary, continuum drift" diagnosis without resolving it, in which case
the wavelet/CWT ridge (16-01-SUMMARY's #1 recommendation) becomes the clear next
move for production segmentation.

## Out of scope

- **Multi-template (`stumpy.motifs`)** — discussed and not pursued: it re-introduces
  a "how many regimes" parameter that likely models the wrong shape of the problem
  if drift is a continuum, on top of new merge-multiple-match-lists logic that
  doesn't exist yet. Time series chains target the same gap natively, with neither
  issue.
- **Rescaled AB-join** ("are fast/slow strokes the same gesture at different
  tempo?") — a reasonable follow-up probe if this spike's results are inconclusive,
  but its own investigation (which rescale factor(s)? validated how?). Parked
  rather than bundled in here.
- Any change to production files (`metrics.py`, `vel_acc_extraction.py`, `api.py`)
  — standalone spike extension, same boundary 16-01 held.
