<objective>
## Goal
Convert ESP_32_V5 firmware from live-streaming to buffer-and-dump (record to RAM with no phone present, dump over BLE afterward, report session-start metadata), update `logger_ble.py` so the dump can be bench-tested without the iOS app, and add `--video-origin-s` to `video_sync.py` so a wall-clock offset can drive the overlay instead of a visual sync cue.

## Purpose
Highest-leverage step from the business-model assessment (Risk #0): produce one velocity-overlay demo video — the "why not TritonWear" proof point — using only a phone. Buffer-and-dump frees the phone to be the camera during the swim and decouples data capture (device button + LED only) from data retrieval (any phone, afterward), which is also the long-term product UX. This plan delivers everything testable without the iOS app; Plan 22-02 adds the app retrieval flow and the end-to-end overlay.

## Output
- `ESP_32_V5/ESP_32_V5.ino`: standalone RAM-buffered recording, META + DUMP BLE commands, data-ready LED state, buffer-full handling.
- `logger_ble.py`: META/DUMP commands, length-tolerant packet parsing (fixes latent 14-vs-28-byte mismatch), end-of-dump detection.
- `video_sync.py`: `--video-origin-s` option, additive to the existing `--sync-tether-us`/`--sync-frame` workflow.
</objective>

## Design Background (from phase discussion)
- Sampling currently requires `recording && deviceConnected` — drop the connection requirement. Capture is phone-free; retrieval happens after the swim.
- Sync strategy: the phone both records video and retrieves the session, so one wall clock bridges them. ESP32 reports `session_start_us` relative to its own `micros()` clock; the phone correlates at retrieval time (Plan 22-02). No visual marker needed — camera-agnostic, extends to underwater footage later.
- The existing iOS app's live-stream flow will break against this firmware. That is accepted: Plan 22-02 converts RecordScreen to the retrieval flow. Live velocity graph during the swim is inherently gone in dump mode.
- One rep per dump for validation. Multi-rep buffering, flash/SD storage, and Supabase persistence of the sync offset are productization, not this phase.
</context>

<acceptance_criteria>

## AC-1: Phone-free recording with LED status
```gherkin
Given the flashed device is powered on and NOT BLE-connected
When the button is pressed once
Then sampling begins into a RAM buffer at ~270 Hz with the 5 Hz recording blink
And `session_start_us` is captured as the micros() timestamp of the first sample
When the button is pressed again
Then sampling stops, the buffer is retained, and the LED shows the data-ready double-pulse
```

## AC-2: META returns session metadata
```gherkin
Given a session is buffered (data-ready state) and a BLE client is connected
When the client writes "META" to the RX characteristic
Then the device notifies one 8-byte packet: [session_start_us: uint32 LE][device_now_us: uint32 LE]
And device_now_us is captured at send time
And (device_now_us - session_start_us) mod 2^32 is plausibly >= the recording duration
And when NO session is buffered, the packet has session_start_us == 0
```

## AC-3: DUMP streams the full buffer
```gherkin
Given a session is buffered and a BLE client is connected and subscribed to TX
When the client writes "DUMP" to the RX characteristic
Then all buffered samples are notified in packets whose length is a multiple of 7 bytes
And each sample is the existing <IHB layout (timestamp_us, angle_counts, magnet_ok)
And a 1-byte end-of-dump marker (0xEE) is notified after the last sample packet
And the received row count equals the device's reported sample count
And afterward the buffer is cleared and the LED returns to idle/pairing
```

## AC-4: Buffer-full stops cleanly
```gherkin
Given recording is active and the RAM buffer reaches capacity
When the next sample would overflow
Then sampling stops automatically, buffered data is retained (truncated, not lost)
And the LED indicates the condition (error pattern, then data-ready)
```

## AC-5: video_sync accepts a direct origin
```gherkin
Given a processed CSV and a video file
When video_sync.py is run with --video-origin-s X (and no --sync-frame / --sync-tether-us)
Then the overlay renders with t_video_origin == X
And the existing --sync-tether-us/--sync-file + --sync-frame workflow still works unchanged
And supplying neither (or both) sync methods produces a clear argparse error
```

  <name>Task 1: Rewrite ESP_32_V5.ino as buffer-and-dump firmware</name>
  <files>ESP_32_V5/ESP_32_V5.ino</files>
  <action>
    Restructure recording around a RAM buffer instead of live notify:

    **Buffer**
    - Packed 7-byte sample storage (packed struct or parallel arrays — avoid the
      8-byte padded struct doubling memory waste).
    - `BUFFER_SECONDS 60` default → 16,200 samples ≈ 113 KB. Allocate with
      malloc() in setup() AFTER BLE init and check the result; Serial-print free
      heap (`ESP.getFreeHeap()`) so the cap can be raised at the bench if room allows.
    - Track `bufCount` and `session_start_us` (micros() of first sample).

    **Recording state machine**
    - Button press while idle → start buffering. Remove the `deviceConnected`
      requirement from the sampling branch in loop() — sample whenever `recording`,
      writing to the buffer (no notify during recording).
    - Button press while recording → stop, keep buffer, enter data-ready.
    - Button press while data-ready → start a NEW recording (buffer overwritten —
      matches "press = record" mental model; one rep per dump).
    - Remove the `pendingRecord`/arm logic and LED_PENDING-as-arming — arming is
      obsolete now that recording doesn't need a connection. Reuse the double-pulse
      pattern as the new LED_READY (data-ready) state.
    - Buffer full → stop sampling, retain data, show LED_ERROR for ERROR_DISPLAY_MS,
      then LED_READY. Serial-log truncation. (AC-4)

    **BLE commands (RxCallbacks)**
    - "META": notify one 8-byte packet [session_start_us uint32 LE][device_now_us
      uint32 LE], device_now_us = micros() at send. If no buffered session,
      session_start_us = 0. 8 bytes is not a multiple of 7, so sample parsers
      naturally reject it. (AC-2)
    - "DUMP": stream the buffer via pTxChar notify as fast as the stack allows.
      Use DUMP_SAMPLES_PER_PACKET = 24 (168 bytes — any multiple of 7 is valid for
      all existing parsers; requires negotiated MTU ≥ 171, which bleak and iOS both
      provide). Insert a small delay (~5 ms vTaskDelay) per packet to avoid Bluedroid
      TX-queue saturation. After the last packet, notify a single byte 0xEE as
      end-of-dump (1 byte ≠ multiple of 7 → ignored by sample parsers, detectable
      as a sentinel). Serial-print "dump complete: N samples". Then clear the buffer
      and set LED idle/pairing. (AC-3)
      Fallback note: if bench testing shows truncated packets (MTU not negotiated),
      drop DUMP_SAMPLES_PER_PACKET to 4 — correctness over speed.
    - Keep "START"/"STOP" mapped to startRecording()/stopRecording() (buffer mode)
      for convenience; they no longer imply live streaming.

    **Keep unchanged**: NUS UUIDs, device name "SwimLogger", 7-byte <IHB sample
    layout, AS5600 I2C code, debounce logic, magnet-check gate on start.

    Update the file-header comment block (LED states, button behavior, BLE commands)
    to describe the new protocol — bench testing reads from it.
  </action>
