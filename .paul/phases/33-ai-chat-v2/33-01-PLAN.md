<objective>
## Goal
Make the coaching chat athlete-aware instead of single-session. Give Claude two
read-only tools — `list_athlete_sessions` and `get_session_metrics` — so it can pull
the athlete's other sessions on demand and answer trend / comparison questions
("how does this compare to her last few swims?", "is she improving?"). Uses the
Anthropic SDK's native tool-use loop. No LangChain, no new dependency.

## Purpose
The chat today only sees the one session the coach is viewing (`POST /coach/chat`
rebuilds the prompt from a single `metrics_json`). Coaches think in trends across an
athlete's history — that is the biggest product gap in the chatbot. Tool-use delivers
both "cross-session trends" and "self-serve data access" (PROJECT.md "Should Have":
AI coaching chat) without bloating every prompt with the full history.

## Output
- `coach.py`: tool schemas (`COACH_TOOLS`) + a one-line system-prompt hint that the
  model may call them; existing voice/biomechanics/guardrails text unchanged.
- `api.py`: `/coach/chat` runs a bounded tool-use loop; server-side executors run the
  Supabase queries scoped to the anchor athlete + owning coach.
- `tests/test_api.py`: tool-loop tests (executes a tool, enforces ownership/athlete
  scoping, terminates, stays backward-compatible).
</objective>

<acceptance_criteria>

## AC-1: Chat can reach the athlete's other sessions
```gherkin
Given a coach is chatting on a session they own (the "anchor" session)
When they ask a question that needs other sessions ("how does this compare to her last few swims?")
Then the model can call list_athlete_sessions and/or get_session_metrics
And the server executes those tools and returns a grounded answer in {reply}
And summary data for the athlete's recent sessions (date, stroke, key metrics) is available to the model
```

## AC-2: Every tool call is ownership- and athlete-scoped
```gherkin
Given a tool call references a session_id (or implicitly the anchor athlete)
When the server executes the tool
Then it returns data only for sessions belonging to the anchor session's athlete AND owned by the requesting coach
And a get_session_metrics call for a session_id outside that athlete returns a tool error result, not data
And no other coach's or other athlete's data can ever enter the model context
```

## AC-3: Backward compatible and always terminates
```gherkin
Given the existing client body {session_id, messages, simple?} (no client change)
When the question needs no tool
Then the response matches today's single-session behavior and returns {reply}
And when tools are used, the create→tool_use→tool_result loop is capped at a fixed max iterations
And the endpoint always terminates by returning {reply} (never loops unbounded)
```
