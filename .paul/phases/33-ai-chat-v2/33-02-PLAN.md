<objective>
## Goal
Let the coaching chat answer **team-wide** questions — "who's lagging on [metric]?",
"who progressed the most?", "how's my team overall?" — by adding three roster-scoped
tools backed by pure aggregation helpers. Reuses 33-01's tool-use loop. Backend only;
no new dependency.

## Purpose
A coach's highest-value questions are triage across the whole roster, not one swimmer.
33-01 made the chat athlete-aware; this makes it team-aware. Delivers the "who do I pay
attention to" questions (PROJECT.md AI coaching chat / business value: per-swimmer triage).

## Output
- `roster_metrics.py` (new): pure functions — latest-session-per-athlete, rank-by-metric,
  progress-over-window. No I/O.
- `coach.py`: `TEAM_TOOLS` schemas + a one-line prompt hint that team questions exist; a
  guardrail line that kick-specific ranking is NOT answerable (kick metrics unreliable).
- `api.py`: register `TEAM_TOOLS` in the loop; coach-scoped executors that load the roster
  once and aggregate via `roster_metrics`. **Hedge for future visual proof:** the loop also
  collects the structured tool results and `/coach/chat` returns them as `data` alongside
  `reply`, so a later "show the data" panel / compare deep-link is front-end-only (no backend
  rework). Applies to 33-01's tools too. Backward compatible (new field; body unchanged).
- Tests: `tests/test_roster_metrics.py` (pure logic) + `tests/test_api.py` (tool integration,
  coach scoping, kick-question refusal).
</objective>

<acceptance_criteria>

## AC-1: Team ranking + summary answerable
```gherkin
Given a coach chatting (on any of their sessions) about their whole team
When they ask "who has the lowest DPS?" or "who progressed most this month?" or "how's my team overall?"
Then the model can call rank_athletes / rank_progress / team_summary
And the server returns a compact, pre-aggregated table (athlete name + value), newest session per athlete
And the answer names specific swimmers from real roster data
```

## AC-2: Roster tools are coach-scoped (and only coach-scoped)
```gherkin
Given a team tool runs
When it queries sessions and athletes
Then both queries are filtered by coach_id (the requesting coach's roster only)
And no athlete outside the coach's roster can appear in any result
And aggregation happens server-side (the model never receives raw multi-athlete cycle data)
```

## AC-3: Honest about the kick limitation and thin data
```gherkin
Given the coach asks "who's worst at underwater kicks?"
When the model considers a ranking on a kick-specific metric
Then it declines/﻿caveats because kick metrics are flagged unreliable (kick_metrics_reliable=False)
And given an athlete with too few sessions for a progress delta
Then rank_progress excludes/marks them rather than inventing a trend
```
