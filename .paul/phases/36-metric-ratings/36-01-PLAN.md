<objective>
## Goal
Build the single source of truth that turns raw session metrics into a coach-friendly
**good / ok / needs-work** read across four headline pillars — **Speed, Stroke Length,
Consistency, Endurance** — each with an absolute band (the "is it good") AND a trend vs the
athlete's own history (the "is it improving"). Pure Python module + an API endpoint so web,
iOS, and the AI chat all consume identical verdicts.

## Purpose
Coaches said specific numbers don't help — they want "good/ok/bad." Phase 2 shipped draft
breaststroke thresholds but only inside Streamlit `app.py`; the product still shows raw
numbers. This plan promotes that logic into a shared, stroke-aware, data-quality-gated
backend module so the web UI (36-02) and the later iOS pass implement against one spec.

## Output
- `ratings.py` — pure module: `rate_session()`, `select_baseline()`, pillar/threshold/explanation tables.
- `GET /sessions/{id}/ratings` in `api.py` (auth + ownership; baseline = previous session).
- `RATINGS-SPEC.md` — the shared design spec iOS implements from later.
- Tests: `tests/test_ratings.py` + an api.py endpoint test.
</objective>

## DESIGN SPEC (decisions locked with user 2026-06-17)

### Four pillars (primary metric drives the band; others shown on expand)
| Pillar | Band driver (primary) | Contributing (expand) | Better = |
|--------|----------------------|------------------------|----------|
| **Speed** | `mean_vel_ms` | `max_vel_ms`, `mean_trough_vel_ms`, `stroke_rate_spm` (tempo context) | higher |
| **Stroke Length** | `mean_dps_m` | `mean_impulse_m`, `stroke_rate_spm`, `mean_coast_fraction` | higher |
| **Consistency** | worst-of(`cv_arm_peak_vel`,`cv_isi`) | both CVs (power + rhythm) | lower |
| **Endurance** | `fatigue_index_pct` | (decline context) | lower |

### Absolute bands — breaststroke (seed from app.py draft; mark DRAFT, coach review owed)
- Speed (mean_vel_ms): good ≥1.2 · ok ≥0.8 · else needs-work
- Stroke Length (mean_dps_m): good ≥1.5 · ok ≥1.0 · else needs-work
- Consistency (CV, both): good <0.10 · ok <0.20 · else needs-work  → pillar = worst of the two
- Endurance (fatigue_index_pct): good <8 · ok <20 · else needs-work

### Hybrid verdict per pillar
- `band`: "good" | "ok" | "needs_work" | "unknown" (primary missing/NaN)
- `score`: 0–100 continuous position of the primary metric within the band range (drives the
  marker on the meter). Piecewise-linear so needs_work ≈ 0–33, ok ≈ 33–66, good ≈ 66–100, clamped
  [0,100]; each band-driver metric has (worst_anchor, ok_threshold, good_threshold, best_anchor)
  in THRESHOLDS. For "lower is better" metrics (Consistency CV, Endurance fatigue) the mapping is
  inverted so higher score always = better. `score=None` when band is "unknown".
- `trend`: "improved" | "steady" | "declined" | "first_session" (no baseline)
  - direction-aware, ±5% deadband vs baseline value (reuse the compare convention)
  - "better" direction per pillar (speed/length up = improved; consistency/endurance down = improved)
- `provisional` (bool): true when the verdict shouldn't be trusted as absolute (see gating)

### Visual system (locked with user 2026-06-17 — for 36-02 web + iOS, written into RATINGS-SPEC.md)
- **Fixed traffic-light band, identical on every card** — the meter always renders all three
  segments in the SAME colors regardless of score (no per-card desaturation): red = needs_work,
  yellow/amber = ok, green = good. Reuse the shipped Phase-2 semantic trio for cross-product
  consistency (app.py `_rate_metric`): **needs_work `#c0392b` · ok `#d4860a` · good `#2d9e5f`**.
  These are tokens (`RATING_COLORS`) so web/iOS/chart all reference one source.
- **Marker** sits at `score`% along the band = "is this swim good" (absolute). **Trend chip**
  (↑ improved / → steady / ↓ declined, semantic-colored) = "is it improving" (relative). Two
  separate glances = the hybrid.
- Card collapsed = pillar name + band meter + verdict word (in band color) + trend chip. Expanded
  (tap) = explanation + contributing metrics. Linear band (not a dial) — cleaner at 4-up + mobile.
- `band` is the source of the verdict word + color; clients must derive color from `band` via the
  shared `RATING_COLORS` map (never hard-code per component) so colors stay consistent.

### Trend architecture (must be future-proof per user)
`rate_session(session_metrics, baseline_metrics=None, stroke="breaststroke")` — the caller
supplies the baseline. `select_baseline(prior_sessions, mode="previous")` is a separate helper
with modes scaffolded: **"previous"** (default, used now), `"recent_avg"`, `"first"`. Adding a
user-chosen comparison scope later = new mode + caller arg only; `rate_session` unchanged.

### Data-quality gating
- `segmentation_reliable == False` → every pillar `provisional=true` (it's always False today,
  so ship reading "provisional"; flips automatically when 16-06 validates segmentation).
- Stroke ≠ breaststroke → **no absolute band** (`band="unknown"`), `provisional=true`,
  trend still computed (trend-only behavior). No freestyle/fly thresholds exist yet.
- Kick metrics (`pct_cycles_with_kick`, `mean_arm_kick_ratio`, `mean_arm_kick_delay_s`)
  excluded from every pillar (`kick_metrics_reliable=False`).
- Any contributing metric None/NaN → omit it; if a pillar's primary is missing → `band="unknown"`.

### Payload shape (what the endpoint returns; web/iOS/chat render this)
```
{
  "stroke": "breaststroke",
  "has_baseline": true,
  "pillars": [
    { "key":"speed", "label":"Speed", "band":"good", "score":79, "trend":"improved",
      "provisional": true, "explanation":"How fast the swimmer moved …",
      "primary": {"key":"mean_vel_ms","label":"Average speed","value":1.25,"unit":"m/s"},
      "metrics": [ {"key":"max_vel_ms","label":"Top speed","value":2.99,"unit":"m/s",
                    "explanation":"Fastest instant in the lap"}, … ] },
    …
  ],
  "rating_colors": {"good":"#2d9e5f","ok":"#d4860a","needs_work":"#c0392b"}
}
```
Explanation text + `RATING_COLORS` live in `ratings.py` (so chat + every client share wording
and colors). `score` drives the marker; `band` drives the verdict word + color (via RATING_COLORS).

## AC-1: Pure rating logic produces the four pillars
```gherkin
Given a breaststroke session's metrics dict (and optionally a baseline dict)
When rate_session(metrics, baseline, "breaststroke") is called
Then it returns the 4 pillars with band ∈ {good,ok,needs_work,unknown}, a 0–100 score matching
  the band (higher always = better, inverted for CV/fatigue, None when band unknown), a
  direction-aware trend (or "first_session" when baseline is None), provisional=true (segmentation
  unreliable), the primary metric, the contributing metrics each with label/value/unit/explanation,
  and a shared RATING_COLORS map (good/ok/needs_work hexes)
```

## AC-2: Non-breaststroke + missing data behave safely
```gherkin
Given a freestyle session, OR a session with NaN/missing primary metrics
When rate_session is called
Then freestyle pillars return band="unknown" + provisional=true with trend still computed,
  kick metrics never appear, and a missing primary yields band="unknown" (no crash, no fabricated rating)
```

## AC-3: Endpoint returns ratings for an owned session with auto baseline
```gherkin
Given an authenticated coach requesting GET /sessions/{id}/ratings for their own session
When the handler runs
Then it loads the session metrics, selects the athlete's previous session of the same stroke as
  baseline (select_baseline mode="previous"), and returns the pillar payload; a foreign/unknown
  session returns 403/404 (never another coach's data); unauthenticated returns 401
```
