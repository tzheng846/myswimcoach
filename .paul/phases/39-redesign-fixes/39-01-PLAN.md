## AC-1: Opening any athlete no longer crashes (BUG 3 — BIGGEST)
```gherkin
Given the Team table with tested athletes (athletes that have pillar data)
When the coach taps any athlete row
Then AthleteDetail renders the pillar cards with correct band colors (good=green, ok=amber, needs_work=red)
And no ReferenceError/redbox occurs
```
ROOT CAUSE: AthleteDetailScreen.js:149 `const c = (p.band && rc[p.band]) || colors.textMuted;`
references `rc`, which is undeclared (the `const rc = colors` line was removed in the 38-04
self-review when `BAND_COLOR` was introduced, but this line was missed). Crashes only for athletes
WITH pillars (untested athletes skip the map). Metro bundles fine — runtime ReferenceError.

## AC-2: Pillar expand view respects the m/yd unit (BUG 1)
```gherkin
Given a session report with units set to yd (Settings) and a pillar card expanded
When the contributing/primary metrics are shown
Then distance metrics (unit "m") display in yd (×1.09361, label "yd") and velocity metrics
  (unit "m/s") display in yd/s; spm / % / s units are unchanged
And toggling m↔yd updates the expanded values live
```
ROOT CAUSE: PillarCards.js renders `fmt(m.value)` + raw `m.unit` straight from /ratings (always
metric); it receives no unit prop and does no conversion. ReportCardScreen mounts `<PillarCards
sessionId token />` without passing its `unit`.

## AC-3: Team-name edit persists (BUG 4)
```gherkin
Given Settings → edit team name → reload the app
When the Dashboard/Settings re-read the team
Then the new name is shown (the supabase update succeeded)
```
ROOT CAUSE: `teams` has only a SELECT RLS policy (schema.sql ~line 78); SettingsScreen's
`supabase.from('teams').update(...)` is silently blocked (0 rows, no error). FIX: add an UPDATE
policy on `teams` (USING + WITH CHECK `id = current_team_id()`), user-applied SQL.

## AC-4: Band-vs-trend presentation decided (BUG 2)
```gherkin
Given a pillar that is band=good (green bar) but trend=declined
When the coach views the pillar card
Then the card makes clear the green bar = absolute quality and "declined" = vs the previous session
  (per the chosen option in the decision checkpoint)
```
INVESTIGATION: ratings.py `_trend` (155) is correct (direction-aware, ±5% deadband). band/score are
absolute; trend is vs baseline — independent by design (Phase 36 hybrid). "declined" + green is
valid (down vs last session, still good). This is a UI-clarity issue, not a logic bug.
</acceptance_criteria>
