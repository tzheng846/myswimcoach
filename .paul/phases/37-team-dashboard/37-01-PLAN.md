<objective>
## Goal
Add the backend that powers a team-level coach dashboard: one authenticated, coach-scoped
endpoint `GET /team/overview` that returns, for the whole roster, each athlete's latest-session
pillar verdicts (band + trend), a team band-distribution per pillar, a needs-attention list, a
recent-activity feed, and counts — all from the existing `ratings.py` + per-athlete baseline
logic. No new metric logic; this is wiring + a small pure rollup.

## Purpose
The current dashboard ([web/app/app/page.js](web/app/app/page.js)) only lists athletes with raw
numbers and does zero aggregation. The coach can't see team health at a glance. `ratings.py`
(pillar bands) and `roster_metrics.py` (team aggregation) already exist but were never surfaced
visually. This plan produces the single payload the web dashboard (37-02) and iOS (later) render.
Bands stay computed in Python — the Phase-36 single-source-of-truth decision — so the dashboard
*must* call the backend rather than recompute bands in JS.

## Output
- `ratings.summarize_team(...)` — new pure helper (band distribution + needs-attention).
- `GET /team/overview` in api.py — auth + coach-scoped; reuses `rate_session` / `select_baseline`.
- Tests: `tests/test_ratings.py` (summarize_team) + `tests/test_api.py` (endpoint).
- The locked payload contract (below) that 37-02 builds against and iOS mirrors later.
</objective>

<design_spec>
## Payload contract — `GET /team/overview` (LOCKED; 37-02 + iOS build against this)

```json
{
  "athlete_count": 7,
  "tested_this_week": 4,
  "pillars": [
    {"key": "speed", "label": "Speed", "good": 4, "ok": 2, "needs_work": 1, "unknown": 0}
  ],
  "athletes": [
    {
      "athlete_id": "uuid", "name": "Maya R.", "stroke_type": "breaststroke",
      "last_tested": "2026-06-17", "last_session_id": "uuid",
      "pillars": [
        {"key": "speed", "label": "Speed", "band": "good",
         "trend": "improved", "score": 72, "provisional": false}
      ]
    }
  ],
  "recent": [
    {"athlete_id": "uuid", "name": "Maya R.", "session_id": "uuid",
     "date": "2026-06-17", "stroke_type": "breaststroke"}
  ],
  "needs_attention": [
    {"athlete_id": "uuid", "name": "Theo K.",
     "reasons": [{"type": "needs_work", "pillar": "Consistency"},
                 {"type": "stale", "days": 19}]}
  ],
  "rating_colors": {"good": "#2d9e5f", "ok": "#d4860a", "needs_work": "#c0392b"}
}
```

### Field rules
- `pillars[]` (top level) = team **band distribution** across all athletes that have ≥1 session,
  in `ratings.PILLARS` order. Bands are counted as-is (a provisional band still counts toward its
  bucket — distribution is a rough glance). Athletes with no sessions contribute nothing.
- `athletes[].pillars[]` = compact projection of `rate_session(...)` pillars
  (`key,label,band,trend,score,provisional` only — drop `explanation`/`primary`/`metrics`; the
  full report card already serves those). Athletes with no sessions → `pillars: []`,
  `last_tested: null`, `last_session_id: null`.
- `recent[]` = newest sessions team-wide (NOT per-athlete), cap **10**, no per-session rating
  (keeps compute O(athletes), not O(sessions); the web links each to its report card).
- `needs_attention[]` reasons, only from **non-provisional** pillars for band/trend:
  - `{"type":"needs_work","pillar":<label>}` per non-provisional pillar with `band=="needs_work"`
  - `{"type":"declined","pillar":<label>}` per non-provisional pillar with `trend=="declined"`
  - `{"type":"stale","days":N}` when last_tested older than `STALE_DAYS` (14) vs today
  - `{"type":"never_tested"}` when the athlete has no sessions
  - Athlete omitted when reasons is empty. Sort: more reasons first, then name.
- `tested_this_week` = count of athletes whose `last_tested` is within 7 days of today.
- `rating_colors` straight from `ratings.RATING_COLORS` (no hard-coding client-side).

### Per-athlete rating (reuse, do NOT reimplement)
Identical to the `/sessions/{id}/ratings` handler: `stroke = latest.stroke_type or
athlete.stroke_type or "breaststroke"`; `metrics = {**session, **data_quality}`; baseline =
that athlete's earlier same-stroke sessions (newest-first, before latest) →
`ratings.select_baseline(prior, mode="previous")` → `ratings.rate_session(metrics, baseline, stroke)`.
</design_spec>

<acceptance_criteria>

## AC-1: summarize_team distribution + counts
```gherkin
Given a list of per-athlete rating summaries (some with sessions, some without)
When ratings.summarize_team(athletes, today, stale_days=14) is called
Then it returns pillars[] band counts (good/ok/needs_work/unknown) in PILLARS order,
  counting only athletes that have pillars, ignoring athletes with no sessions
```

## AC-2: needs_attention reasons
```gherkin
Given athletes with needs_work bands, declined trends, stale last_tested, and never-tested
When summarize_team runs with a fixed today
Then needs_attention contains the right reason objects, provisional pillars never produce
  band/trend reasons, athletes with no reasons are omitted, and the list is sorted by
  reason-count desc then name
```

## AC-3: endpoint shape + auth + coach scope
```gherkin
Given a signed-in coach with a roster and sessions
When GET /team/overview is requested with a valid Bearer token
Then it returns 200 with athlete_count, tested_this_week, pillars, athletes, recent,
  needs_attention, rating_colors; only this coach's athletes appear; a request with no
  token returns 401; a coach with no profile returns 403
```

## AC-4: no-session + DB-failure behavior
```gherkin
Given a roster where one athlete has zero sessions
When GET /team/overview runs
Then that athlete appears with pillars=[] and last_tested=null (no crash);
  and a genuine Supabase query failure surfaces as 5xx (not masked as empty/200)
```
