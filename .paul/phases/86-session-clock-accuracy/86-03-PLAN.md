<objective>
## Goal
Replace every estimated alignment figure in Phase 86 with a measured one. Build an offline analyzer
that reads a tap's time from the **raw** encoder CSV and from the **video** (audio onset, frame-index
cross-checked), pre-register the pass bars, then run the tap test on a device and report the residual
of both video-to-trace mappings the product actually contains.

## Purpose
Every accuracy number in 86-01 and 86-02 is an estimate. `rtt/2` assumes symmetric BLE legs; the
"20–80 ms" flight time was inferred from BLE characteristics, never observed; and the corrected
overlay has never been compared to ground truth. This plan is the only thing in the phase that
produces a measurement.

🔴 **PLANNING FOUND THAT PHASE 86's STATED MOTIVATION IS WRONG ABOUT THE OVERLAY.** 86-01 and 86-02
both justify themselves as fixing "a live bug in the shipped video overlay," carrying an unmeasured
20–80 ms error. **The shipped overlay does not use the mapping 86-02 corrected.**
[VideoOverlayScreen.js:69](../../../../swimnetics-mobile/src/screens/VideoOverlayScreen.js:69)
computes `endAnchoredOriginS = deviceDurationS − videoDurationS` — a difference of two **durations**,
in which `sessionStartPhoneMs` cancels exactly. That value is what gets persisted to
`sessions.video_origin_s` ([:168-170](../../../../swimnetics-mobile/src/screens/VideoOverlayScreen.js:168)),
and it is what both the iOS overlay and the web annotate page read back. Its own header comment says
the start-anchored predecessor was abandoned in Phase 60 because camera warm-up put it **~2 s off** —
25–100× larger than the error this phase chases.
⚠ [RecordScreen.js:769](../../../../swimnetics-mobile/src/screens/RecordScreen.js:769) still carries
the stale comment `video_origin_s = (sessionStartPhoneMs − videoStartPhoneMs)/1000`, which is how the
mistaken framing survived into two plans. Not fixed here — this plan does not edit mobile code.

**What 86-02 genuinely changed is therefore narrower than claimed, and both things are real:**
`session_start_utc_ms` — the absolute export for an external video system, which has no end-anchor
available because its camera is not stopped by our tap — and 84-02's `go_signal_s`, which resolves
against the corrected start. The overlay a coach looks at today was never affected either way.

This makes the tap test **more** valuable, not less, and redirects its primary target:
1. It measures the residual of the **end-anchored playback origin** — the number the coach actually
   sees, never validated against ground truth, and independent of everything 86-02 did.
2. Differencing the two origins on the same rep yields the **first real measurement of camera
   warm-up**, currently a "~2 s" guess in a code comment.
3. It bounds — and cannot isolate — the `rtt/2` correction. Said up front in `<measurement_honesty>`.

<measurement_honesty>
Fixed before any data is collected, so a disappointing result cannot be re-framed afterwards.

**"Before vs after" is not an experiment here.** 86-02 D5 makes the uncorrected start recoverable in
closed form: `uncorrected = corrected + minRtt/2`. Comparing them re-reports `minRtt/2` and measures
nothing. The only real quantity is the **absolute residual of the corrected mapping**.

**A single session cannot separate clock error from camera warm-up.** Within one recording both are
constant, so every tap in it sees the same sum. Only across sessions does `sync_error_ms` vary, which
is why the protocol calls for many short sessions rather than one long one.

**`rtt/2` is bounded, not isolated, and this instrument is underpowered to falsify it alone.**
`sync_error_ms` spans perhaps 30 ms across sessions; warm-up jitter is plausibly ±100 ms. The
regression of residual on `sync_error_ms` is reported with its confidence interval and **no
conclusion is drawn from a slope whose interval contains both 0 and 2**.

**`clock_offset_ms` is not tested at all.** Both readouts sit on the phone's own clock, so the
phone-to-server offset cancels. Validating it needs a different instrument; it is out of scope.

**Null results are results.** If the end-anchored residual is already under one frame, that is a
finding worth recording — it retires a suspicion, and the code comment that claims the end-anchor is
warm-up-agnostic becomes measured rather than asserted.
</measurement_honesty>

<task type="auto">
  <name>Task 1: Build the offline tap analyzer</name>
  <files>scratch/tap_test.py</files>
  <action>
    A standalone script. Inputs: `--raw` (the session's raw CSV), `--video` (the clip),
    `--session-start-utc-ms`, `--video-start-phone-ms`, `--mic-distance-m`. Reads nothing from
    Supabase — the operator supplies files, which keeps the instrument runnable offline and keeps
    credentials out of it.

    Encoder side — read the RAW CSV, never the processed trace. Raw is 270 Hz with a real
    `timestamp_us` per sample; the pipeline decimates to ~89.5 Hz and its antialias filter smears an
    impulse across neighbouring samples. (Both stages are zero-phase — `decimate(zero_phase=True)`
    and `savgol_filter(mode="interp")` — so there is no group delay to remove; the reason to prefer
    raw is resolution and impulse shape, not bias.) Session time = `(timestamp_us − timestamp_us[0])
    / 1e6`, using uint32 modular subtraction, since `micros()` wraps at 71.6 min. Locate taps as
    threshold crossings of `|diff(angle_counts)|` against a robust baseline (median + k·MAD over the
    quiet trace), then refine each to the sample of steepest rise. Drop crossings within 0.5 s of
    another so one physical strike cannot register twice.

    Video side — two independent readouts of the same tap.
    (a) Audio: `ffmpeg -i clip.mp4 -ac 1 -ar 48000 -f s16le -` piped to numpy; onset = first sample
        where a short-window energy envelope crosses a MAD-based threshold. Resolution ~0.02 ms.
        Subtract `mic_distance_m / 343.0` — at 2 m that is 5.8 ms, the same order as the effect being
        measured, so it is a correction and not a rounding detail.
    (b) Frames: `ffprobe -show_frames` for the real frame timestamps (do NOT assume 30 fps or
        constant frame duration — iOS writes variable frame rate), then locate the tap frame by
        per-frame mean-absolute-difference within the operator-supplied crop region.
    Reject any tap where they disagree by more than half a frame (AC-4).

    Residuals, per accepted tap, with the sign convention stated in the output header
    (positive = the video readout lands LATER in session time than the encoder's):
      end_anchored_origin_s   = device_duration_s − video_duration_s
      start_anchored_origin_s = (video_start_phone_ms − session_start_utc_ms) / 1000
      residual_end            = (t_video + end_anchored_origin_s)   − t_encoder
      residual_start          = (t_video + start_anchored_origin_s) − t_encoder
      camera_warm_up_s        = start_anchored_origin_s − end_anchored_origin_s
    Print a per-tap table and per-session means, and write a JSON sidecar so Task 5 aggregates
    across sessions without re-running ffmpeg.

    Avoid: reading the processed CSV, assuming a fixed frame rate, hardcoding a Supabase path, and
    silently dropping a rejected tap without counting it.
  </action>
  <verify>Build the five synthetic fixture pairs in-script under `--self-test` and confirm each injected offset is recovered within 2 ms; `python scratch/tap_test.py --self-test` exits 0 with a PASS line</verify>
  <done>AC-1 and AC-3 satisfied; AC-4's rejection path exercised by a deliberately desynchronised fixture</done>
