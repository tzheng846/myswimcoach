<objective>
## Goal
Give the backend a place to store an **accurate, absolute** session start time, and a clock-check
endpoint the phone can measure itself against. Three additive form fields on `POST /process`
(`session_start_utc_ms`, `sync_error_ms`, `clock_offset_ms`), three new `sessions` columns behind
`patch_14`, and an unauthenticated `GET /time`.

## Purpose
Every encoder sample is stamped with `micros()` — microseconds since the ESP32 booted
([ESP_32_V5.ino:797](../../../ESP_32_V5/ESP_32_V5.ino:797)). Absolute time exists only as
`sessionStartPhoneMs`, computed on the phone from the META packet
([RecordScreen.js:457](../../../../swimnetics-mobile/src/screens/RecordScreen.js:457)), used for the
local video overlay, and then **discarded** — it is never sent to the server. `api.py` never sets
`recorded_at`, so the DB default `NOW()` records **upload time, not swim time**.

Two consequences:
1. The existing in-app video overlay carries an unmeasured 20–80 ms error (the BLE flight time between
   the ESP32 sampling `micros()` in `sendMeta()` and iOS firing the notification callback). This is a
   live bug in the shipped product, independent of any partner.
2. Nothing in the system can answer "what UTC instant was encoder sample #0?", which is the one thing
   any external video system needs in order to align its frames to our trace.

This plan builds the **server half**. It is deliberately useful on its own: it fixes nothing until
86-02 sends the fields, but it must be live on Railway *before* that app ships (see DEPLOY ORDERING).

## Output
- `supabase/patch_14_session_clock.sql` — three new `sessions` columns (NOT applied by this plan)
- `api.py` — `GET /time`; three optional form fields on `POST /process`, persisted to the new columns
- `tests/test_api.py` — coverage for both, following 84-02's `_post_csv` optional-kwarg precedent
</objective>

## ⚠ DEPLOY ORDERING IS LOAD-BEARING

`api.py` must be **live on Railway before** the 86-02 app build that sends these fields — otherwise
FastAPI drops the unknown form fields silently and sessions recorded in the gap lose their absolute
start with no error anywhere. Identical to 84-02's constraint, and it now applies to both phases.

## ⚠ NO BACKFILL IS POSSIBLE

`session_start_utc_ms` can only be filled by the phone at recording time. All 99 existing sessions
will hold NULL permanently. Every consumer must treat NULL as "unknown", never substitute
`recorded_at` (which is upload time), and never coalesce to a default — the same reasoning that
forbids backfilling NULL `sample_rate_hz` with 100.
</gating>

  <name>Task 1: Add patch_14 with the three session-clock columns</name>
  <files>supabase/patch_14_session_clock.sql</files>
  <action>
    Create the patch following the shape of patch_09_sessions_sample_rate.sql (the closest precedent —
    session provenance, nullable, no default, no backfill).

    ALTER TABLE sessions ADD COLUMN session_start_utc_ms BIGINT;
    ALTER TABLE sessions ADD COLUMN sync_error_ms        DOUBLE PRECISION;
    ALTER TABLE sessions ADD COLUMN clock_offset_ms      DOUBLE PRECISION;

    Use BIGINT epoch milliseconds, NOT timestamptz. Reason to record in a header comment: this is the
    number the phone computes and the number an external video system consumes; converting to
    timestamptz on write and back on read adds two places to get a timezone wrong and buys nothing
    (Postgres timestamptz is microsecond-precision, so no accuracy is gained).

    Header comment must also state, for the next reader:
    - NULL means "unknown", never "assume recorded_at". recorded_at is UPLOAD time, not swim time.
    - No backfill is possible. Pre-Phase-86 sessions hold NULL permanently.
    - sync_error_ms is the phone's measured one-way BLE flight time to the encoder; clock_offset_ms is
      the phone's measured offset from server UTC. Both are diagnostics, not corrections — the
      correction is already baked into session_start_utc_ms.

    Do NOT apply the patch. The user applies patches against the live DB (standing pattern:
    patch_11 / patch_12).
  </action>

- `metrics_json` and `metrics_json.phases`. Nothing in this plan writes them. `phases` is rewritten by
  recompute and `PUT /annotations`; session provenance must not live somewhere that gets replaced.
- `vel_acc_extraction.py`, `metrics.py`, `phase_metrics.py` — no pipeline change. The sample stream and
  every metric are byte-identical before and after this plan.
- The auth posture of every existing endpoint.

- Do NOT apply patch_14 to the live DB — the user runs patches.
