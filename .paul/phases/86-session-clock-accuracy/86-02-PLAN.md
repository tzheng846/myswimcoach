<objective>
## Goal
Make the phone's encoder-to-UTC mapping **measured instead of assumed**, and send it. Replace the
one-shot META with a burst of timed round trips, correct `sessionStartPhoneMs` by the minimum
observed one-way BLE latency, measure the phone's offset against `GET /time`, and put all three
numbers on the swim's own `POST /process` request.

## Purpose
Every encoder sample is stamped `micros()` — boot-relative, wraps at 71.6 min. The only bridge to
absolute time is built in the META handler
([RecordScreen.js:457](../../../../swimnetics-mobile/src/screens/RecordScreen.js:457)):

```js
const phoneNowMs   = Date.now();          // when the REPLY arrived
const elapsedUs    = (deviceNowUs - sessionStartUs + 2**32) % 2**32;
const startPhoneMs = phoneNowMs - elapsedUs / 1000;
```

`deviceNowUs` was captured on the ESP32 **when it built the reply**
([ESP_32_V5.ino:426](../../../ESP_32_V5/ESP_32_V5.ino:426)), not when the phone received it. The
inbound BLE leg — 20–80 ms — is silently attributed to the encoder, so **`sessionStartPhoneMs` is
biased late by roughly one one-way flight time**. That number drives the in-app video overlay today,
so this is a live defect in the shipped product, not partner-driven work.

It is also **thrown away**: never sent to the server, and `api.py` never sets `recorded_at`, so the DB
records upload time. 86-01 built the columns and `GET /time`; this plan is the only thing that can
ever fill them (STATE item 22).

## Output
- New pure `swimnetics-mobile/src/lib/sessionClock.js` — the clock math, zero imports
- `RecordScreen.js` — probe burst, corrected start, offset probe, three new form fields
- New `scratch/session_clock_check.mjs` — headless harness + cross-repo constant guard
</objective>

- **D2:** the sanity window is a 2020-01-01 floor to `now + 48 h`. **The phone must not send seconds**

## ⚠ DEPLOY ORDERING IS LOAD-BEARING (the same constraint as 84-02, and it now bites twice)

The order is fixed and each step must actually complete:

1. Apply `patch_14` to the live DB (user-run).
2. Commit + push `api.py` → Railway deploys.
3. Verify live: the deployed `/openapi.json` contains `session_start_utc_ms`, and
   `GET /time` returns 200 **with no Authorization header**.
4. Only then build and ship the app from this plan.

If the app ships first, FastAPI drops the unknown form fields **silently** — no 4xx, no log, no
symptom — and every session recorded in the gap loses its absolute start permanently. 86-01's
subscript-assignment design means steps 1 and 2 may swap, but neither may follow step 4.

## ⚠ NO BACKFILL IS POSSIBLE

Only the phone can produce this, at record time. The 99 existing sessions hold NULL forever. A
consumer must read NULL as *unknown* and must never substitute `recorded_at` (upload time) — the same
reasoning that forbids backfilling NULL `sample_rate_hz` with 100.

## ⚠ EVERY ACCURACY NUMBER HERE IS AN ESTIMATE

`rtt/2` assumes the two BLE legs are symmetric. Two facts bound the risk, both verified rather than
assumed: the ESP32 services META from `processPending()`, the **first** call in a free-running
`loop()` with no `delay` while `recording` is false, so device-side queueing is negligible; and both
directions are acknowledged operations (`writeCharacteristicWithResponseForService` outbound,
`notify(false)` — an indication — inbound). The residual asymmetry is BLE-stack plus JS callback
dispatch. **86-03's tap test is the only thing that converts this from plausible to measured**, and
until it runs, no document may state a corrected-overlay accuracy figure as fact.

  <action>
    New module in the mobile repo with **no imports at all** — that is a hard requirement, not a
    style note: it is what lets `scratch/session_clock_check.mjs` load the source through a data: URL
    and test it, exactly as `uploadRetry.js` is tested (the mobile tree has no test runner, 84-03 G28).

    Export:

    - `META_PROBE_COUNT = 10`, `META_PROBE_TIMEOUT_MS = 400`, `META_PROBE_BUDGET_MS = 2500`.
      Rationale to write down: 10 probes at an expected 20–80 ms RTT costs well under a second before
      a ~20 s dump; the per-probe timeout is generous against a ~15–30 ms connection interval; the
      overall budget is the hard ceiling so a dead link cannot stretch retrieval.
    - `EPOCH_MS_FLOOR` and `EPOCH_MS_FUTURE_SLACK_MS` — mirrors of api.py:133-134. Comment that
      the harness asserts equality and WHY: a value outside the server's window is dropped with a
      log line the phone never sees, which is the same silent-loss shape 84-02 was written to avoid.
    - `elapsedUs(deviceNowUs, sessionStartUs)` — the existing modular u32 subtraction, moved here so
      the wrap handling is testable. Do not change its arithmetic.
    - `probeRttMs(probe)` → `probe.tRecvMs - probe.tSendMs`.
    - `pickBestProbe(probes)` → the entry with the **minimum** RTT, or null for an empty/all-failed
      array. Minimum, not mean or median: Cristian's algorithm — the least-delayed sample is the one
      whose symmetric-legs assumption is least polluted by congestion. Averaging would bake queueing
      delay into the correction.
    - `sessionStartUtcMsFrom(probe)` → `(tRecvMs - rtt/2) - elapsedUs(...)/1000`. Comment the
      derivation: deviceNowUs was captured when the ESP32 built the reply, so its instant on the
      phone clock is tRecvMs minus the inbound leg, estimated as rtt/2.
    - `syncErrorMsFrom(probe)` → `rtt/2`. It is simultaneously the correction applied and the
      residual uncertainty; say so.
    - `clockOffsetMs({ tSendMs, tRecvMs, serverUtcMs })` → `(tSendMs + tRecvMs)/2 - serverUtcMs`.
      **Document the sign: positive means the phone clock is AHEAD of the server.** A consumer
      converts to server time with `session_start_utc_ms - clock_offset_ms`. An undocumented sign
      on a diagnostic is worse than no diagnostic.
    - `isPlausibleEpochMs(ms, nowMs)` → finite, integral-safe, within [FLOOR, nowMs + SLACK].

    ⚠ `clockOffsetMs` is **measured and reported, never applied** to `session_start_utc_ms`. State the
    reason in the module header: the app records at poolside where `GET /time` may fail entirely, so
    applying it would make the primary number's meaning depend on whether an unrelated network call
    succeeded. `session_start_utc_ms` is therefore always "on the phone's clock, corrected for BLE
    flight only" — one definition, every session. This also matches the comment already shipped in
    api.py:292-297 ("the diagnostics are NOT corrections").

    Avoid: any React, any `Date.now()` inside the module (callers pass timestamps in, so the harness
    can be deterministic), any state.
