<objective>
## Goal
A pure, node-verifiable module holding everything the leaderboard needs except React and Supabase:
the eight-metric catalog, the eligibility guard, the **derived** lap time, the last-N mean, and the
ranking with a defined tie-break and a defined behaviour for a missing value.

## Purpose
CONTEXT D3 chose eight metrics that do not depend on stroke-cycle segmentation, because the
segmenter undercounts strokes by ~2–3× (CONTEXT F4) and a leaderboard would publish that failure by
name. Planning re-measured the eight against the live library and found **one of them is not the
number its name says** — see the box below. Isolating the arithmetic in a pure module is what lets
that be pinned by a harness instead of trusted.

🔴 **`metrics_json.session.lap_time_s` IS NOT A LAP TIME — measured this session, not in CONTEXT.**
[metrics.py:1870](metrics.py:1870) computes it as `float(t[-1])`: the **duration of the recording**.
Across the 84 eligible sessions it disagrees with `finish_s − dive_start_s` on **84 of 84**, median
**5.75 s**, max **28.29 s**, and **19 of 84 read exactly 39.0 s** — the firmware's fixed record
length, not a swim. Ranking on it ranks who stopped recording soonest. `finish_s − dive_start_s` is
present on **84 of 84** eligible sessions (median 15.1 s, range 4.8–21.9 s) and uses the same
`dive_start_s` anchor Phase 88-02 hoisted, so this plan derives lap time and never reads the stored
scalar.

⚠ **This corrects CONTEXT R6.** R6 says *"avg speed, top speed and lap time are the only three with
no detector dependence at all."* That is wrong on all three: `mean_vel_ms` and `max_vel_ms` are both
computed over `vel[b_end:swim_end]` ([metrics.py:1763](metrics.py:1763)), and the derived lap time
needs two boundaries. **All eight metrics are boundary-dependent.** The distinction that survives —
and the one F4 was actually about — is **cycle-independence**: none of the eight reads `ctx.cycles`.

<acceptance_criteria>

## AC-1: Lap time is derived, never read
```gherkin
Given a session row carrying boundaries { dive_start_s: 4.0, finish_s: 19.1 } and a stored
  lap_time_s of 39.0
When metricValue(row, "elapsed_s") is called
Then it returns 15.1
And the string "lap_time_s" does not appear anywhere in web/lib/leaderboard.js
And metricValue returns null when either boundary is missing, non-finite, or finish <= dive
```

## AC-2: The eligibility guard is a stated constant, applied by one function
```gherkin
Given rows with total_dist_m of 0, 14.31, 15.0 and 21.5
When isEligible(row) is called on each
Then it returns false, false, true, true
And MIN_DIST_M is exported and equals 15
And a row with a null or missing total_dist_m is ineligible (never treated as 0-and-pass)
```

## AC-3: A row value is the mean of the athlete's last N swims, newest first
```gherkin
Given an athlete's eligible rows already ordered newest-first with values [2, 4, 6, 8, 10, 12]
When lastNMean(values, 5) is called
Then it returns 6 (the mean of the first five), not 7 (the mean of all six)
And nulls are dropped BEFORE the window is taken, so N counts values, not rows
And an empty list returns null, never 0 or NaN
```

## AC-4: Ranking is direction-aware, stable, and refuses to rank a missing value
```gherkin
Given four athletes on a "higher is better" metric with values 1.9, 1.4, 1.4 and null
When rankBoard is called
Then the two 1.9/1.4 entries rank 1 and 2, the tied 1.4 entries take the same rank ordered by
  name, and the null entry is LAST with rank null and value null
And re-running rankBoard on the same input produces an identical order (no reliance on input order)
And a "lower is better" metric inverts the order without changing any other behaviour
```

## AC-5: The catalog carries exactly the eight chosen metrics and the query that feeds them
```gherkin
Given LEADERBOARD_METRICS
When it is inspected
Then it has exactly 8 entries with keys mean_vel_ms, max_vel_ms, elapsed_s, uw_avg_speed,
  splits_5m, splits_10m, splits_15m, splits_20m
And every entry carries { key, label, unit, direction }, direction is "higher" or "lower" and
  never "neutral", and elapsed_s is the only "lower" entry
And SESSION_SELECT is exported and names every field the catalog and the guard read
```

## AC-6: The harness is green and needs neither auth nor network
```gherkin
Given a checkout with no dev server running and no Supabase credentials
When `node scratch/leaderboard_check.mjs` runs
Then every check passes and the process exits 0
```

  <action>
    New pure ES module. No React, no `@/` alias imports, no Supabase — it must be importable
    directly by `node` (verified: `import("../web/lib/rollingMean.js")` resolves this way today).
    Follow `web/lib/groupStats.js` for tone: a header comment stating what it is and the decisions
    that are easy to get wrong, then small named exports.

    Export, in this order:

    1. `MIN_DIST_M = 15` and `DEFAULT_N = 5`.

    2. `LEADERBOARD_METRICS` — 8 entries, each `{ key, label, unit, direction }`:
       - `mean_vel_ms`  "Average speed"     "m/s"  higher
       - `max_vel_ms`   "Top speed"         "m/s"  higher
       - `elapsed_s`    "Lap time"          "s"    lower
       - `uw_avg_speed` "Underwater speed"  "m/s"  higher
       - `splits_5m`    "Split 0–5 m"       "m/s"  higher
       - `splits_10m`   "Split 5–10 m"      "m/s"  higher
       - `splits_15m`   "Split 10–15 m"     "m/s"  higher
       - `splits_20m`   "Split 15–20 m"     "m/s"  higher
       Labels are copied from `PhaseReportCard.js`'s DISPLAY table (lines 61, 77–80) so the same
       metric is not named two things across two portal pages — CONTEXT F10's "extend the
       convention" applied to labels as well as to `direction`. `direction` matches
       `reportMetrics.js`'s vocabulary exactly. No `neutral` entry exists: CONTEXT F8 excluded every
       metric without a sort order, so a `neutral` direction here would be a contradiction.

    3. `SESSION_SELECT` — the exact PostgREST select string, as one exported constant so the page
       cannot drift from the catalog and the harness can pin the pair together. Measured working
       against the live DB during planning (99 rows, 47 KB, 0.76 s):
         `id, athlete_id, stroke_type, recorded_at,`
         `mean_vel_ms:metrics_json->session->mean_vel_ms,`
         `max_vel_ms:metrics_json->session->max_vel_ms,`
         `total_dist_m:metrics_json->session->total_dist_m,`
         `dive_start_s:metrics_json->phases->boundaries->dive_start_s,`
         `finish_s:metrics_json->phases->boundaries->finish_s,`
         `uw_avg_speed:metrics_json->phases->underwater->uw_avg_speed->value,`
         `splits_5m:metrics_json->phases->swim->splits_5m->value,`
         `splits_10m:metrics_json->phases->swim->splits_10m->value,`
         `splits_15m:metrics_json->phases->swim->splits_15m->value,`
         `splits_20m:metrics_json->phases->swim->splits_20m->value`
       Deep scalar selection is what keeps this cheap: the same 99 rows cost 503 KB if the phase
       objects are pulled whole and 1.5 MB for the full `metrics_json`. `lap_time_s` is
       deliberately ABSENT from the select — see AC-1.

    4. `isEligible(row)` → `Number.isFinite(row?.total_dist_m) && row.total_dist_m >= MIN_DIST_M`.
       Null/missing must be ineligible; do NOT write `(row.total_dist_m ?? 0) >= 15`-style coercion
       that silently reclassifies unknown as zero.

    5. `metricValue(row, key)` → the finite number or `null`. For `elapsed_s`, compute
       `finish_s − dive_start_s` and return null unless both are finite and the difference is > 0.
       For every other key, return `row[key]` when finite, else null. Never return NaN or 0 as a
       stand-in for missing — `lastNMean` and `rankBoard` both key off null.

    6. `lastNMean(values, n = DEFAULT_N)` → mean of the first `n` non-null values, or null when
       there are none. Drop nulls BEFORE slicing (AC-3): a swim that lacks this one metric must not
       consume a slot in the window.

    7. `rankBoard(rows, metric, { n = DEFAULT_N, nameFor })` → one board.
       - Group eligible rows by `athlete_id`; the caller passes rows already ordered newest-first
         (`recorded_at` desc, non-null on 99/99 sessions — measured).
         ⚠ **State this in the header comment, do not let it be discovered later:** `recorded_at`
         stores **upload** time, not swim time (STATE owed item 22 — `api.py` never sets it, so it
         takes the schema default `NOW()`). "Last 5 swims" is therefore "last 5 uploads", which is
         the same thing whenever upload follows the swim by minutes and is wrong for a late queued
         upload. `session_start_utc_ms` (86-01) is the correct field and exists only for sessions
         recorded after Phase 86 ships, so it cannot order the library today. Do not silently
         substitute it; do not add a fallback chain.
       - For each athlete emit `{ athleteId, name, value, n, swims }` where `value` is
         `lastNMean(...)`, `n` is how many values went into it, and `swims` is the athlete's total
         eligible swim count for this stroke.
       - Sort: entries with a value first, ordered by `direction`; ties broken by `name` with a
         plain `<` comparison (not `localeCompare` — locale-dependent ordering would make the
         harness environment-sensitive). Entries with `value === null` sort last, keeping their
         name order.
       - Assign `rank`: 1-based over the valued entries, with **ties sharing a rank** (1, 2, 2, 4).
         A null-valued entry gets `rank: null` — it appears on the board, unranked. This is the
         CONTEXT D7 promise ("every swimmer appears") held together with honesty: measured, **Dane
         has no `splits_20m` on either of his two eligible breaststroke swims**, so this branch is
         live on the real data on day one, not hypothetical.
       - Pure: never mutate `rows`.

    Avoid: importing `unitConvert.js` here. Ranking runs on SI only — 88-03 D2 made "toggling units
    cannot reorder anything" structural rather than hoped for, and this module is where that
    structure lives.
