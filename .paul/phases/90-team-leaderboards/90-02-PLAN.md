<objective>
## Goal
The `/app/leaderboard` route exists, is reachable from the portal nav, loads the coach's roster and
their eligible swims through **one** function, and partitions them into stroke tabs with honest
counts. The metric boards themselves are 90-03; this plan is about the page having the *right
swims* in it.

## Purpose
CONTEXT R4: Phase 89 D1 deletes `athletes.team_id NOT NULL` in favour of a membership table, so
whatever fetches "the team's athletes" is already on 89's rewrite list. Cheap to absorb if the
roster fetch is one function; expensive if it is inlined into eight boards. That is the whole
reason this is its own plan — the seam is the deliverable.

Splitting data from presentation is a horizontal cut, which `plan-format.md` warns against. It is
deliberate here: what is most likely to be wrong on this page is *which swims are in it* (a guard,
a stroke partition, a last-N window over `recorded_at`), and that is verifiable on its own, before
any pixels exist to argue about.

## Output
- `web/lib/leaderboardData.js` — new; the single roster + sessions read
- `web/app/app/leaderboard/page.js` — new route with stroke tabs, counts, caveat line
- `web/app/app/layout.js` — one nav entry
- `scratch/_lb_expect.py` — new read-only probe printing the expected counts, for 90-03's verify
</objective>

  <action>
    New `"use client"`-free module (it is imported by a client component but holds no hooks).
    Export exactly one async function, `fetchLeaderboard()`, returning
    `{ athletes, rows, excluded, total }`:
    - `athletes` — `Map<id, name>` from `supabase.from("athletes").select("id, name").order("name")`.
      RLS scopes this to the coach (DATA-FLOW.md: `sessions.coach_id` is the ownership column and
      reads go straight to Postgres under RLS), so no `team_id` filter is written. ⚠ Put the
      Phase-89 comment here: this is the one place a membership-table rewrite has to land.
    - `rows` — `supabase.from("sessions").select(SESSION_SELECT).order("recorded_at", { ascending:
      false })`, then dropped to those whose `athlete_id` is in `athletes`, then filtered by
      `isEligible`. Both imported from `@/lib/leaderboard`; do not retype the select string.
      ⚠ `recorded_at` is **upload** time, not swim time (STATE owed item 22). It is nonetheless the
      only ordering key that exists across all 99 sessions — `session_start_utc_ms` (86-01) covers
      only sessions recorded after Phase 86 ships. Use it, and carry 90-01's comment forward rather
      than inventing a fallback chain.
    - `excluded` / `total` — counts before and after the guard, so AC-4's caveat is computed, not
      hard-coded.
    Attach the athlete's `name` to each row once here, so no board has to reach back into the Map.

    Measured expectations for the verify: 99 sessions in, **84 eligible**, 15 excluded — three
    "Test" bench sessions (0.00–0.59 m), two zero-distance rows, Leo's five 39.0 s udk partials, and
    four short Tony/Leo swims.

    Avoid: a second sessions query per stroke or per metric. One query, 47 KB, 0.76 s measured — the
    partition is a client-side `filter`.
  </action>
