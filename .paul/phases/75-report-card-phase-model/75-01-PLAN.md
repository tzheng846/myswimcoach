<objective>
## Goal
Build **Step 1 — the skeleton/integration layer** for the phase-organized report card
(CONTEXT D11/D15/D16): a metric **registry** (declarative source of truth per metric), a
**`phases` slot** inside `sessions.metrics_json` (jsonb, no migration), and a
**`POST /sessions/{id}/recompute`** endpoint that re-derives the phases object from STORED
profiles. Zero metrics are *implemented* in this plan — every taxonomy metric gets a space
(`status: planned`), so Step 2 can plug them in one at a time.

## Purpose
The user resequenced Phase 75 backend-first: "define + provide space" before any metric or any
UI. This plan is that seam. It lets a later metric be added in one place (flip `status`, set a
compute fn) and backfill every existing session via `/recompute` — no raw-CSV reprocessing,
mirroring Phase 64's acceleration backfill. It touches no metric math, no schema, no UI, no mobile.

## Output
- `phase_metrics.py` — new pure module: `MetricSpec`, `REGISTRY` (all `planned`), `PhaseContext`,
  `compute_phases()`.
- `api.py` — `/process` writes an additive `phases` object into `metrics_json` + response;
  new `POST /sessions/{id}/recompute` endpoint.
- Tests: `tests/test_phase_metrics.py` (registry + engine), `tests/test_recompute.py` (endpoint),
  a small additive assertion in `tests/test_api.py`.
- `.paul/phases/75-report-card-phase-model/75-01-SUMMARY.md`.
</objective>

      Doc-comment maps these to CONTEXT §"Metric taxonomy": start | underwater | swim | whole race.
    - `SCHEMA_VERSION = 1`.
    - `MetricSpec` — a frozen dataclass: `key: str, phase: str, label: str, unit: str,
      tier: str, status: str = "planned", compute: Callable | None = None`. Add `__post_init__`
      asserting phase in PHASES, tier in TIERS, status in {"planned","implemented"}, and
      (status == "planned") == (compute is None) — a planned metric has no fn, an implemented one must.
    - `PhaseContext` — a namedtuple/dataclass carrying the stored signal the Step-2 compute fns will
      read: `t, vel, dist, accel, fs, stroke_type, go_signal_s`. This is the deliberate "compute-
      function slot" seam (CONTEXT D15) — the ONE piece of forward-structure the user asked for;
      keep it to exactly these fields, nothing speculative.
    - `REGISTRY: tuple[MetricSpec, ...]` — seed ONE entry per metric from the CONTEXT taxonomy tables,
      ALL status="planned", compute=None. Cover: start (time_to_peak_vel, max_accel, peak_vel,
      dive_duration, glide_duration/distance/avg_speed, glide_decel, streamline_drag,
      break_into_kick_vel, reaction_time); underwater (uw_duration, uw_distance, uw_avg_speed,
      uw_surface_ratio, kick_count, dist_per_kick, kick_tempo, kick_consistency, uw_ivv,
      per_kick_decay, first_kick_impulse, pulldown_peak_vel, pulldown_duration); swim (ivv,
      breakout_vel, breakout_vel_loss, breakout_vs_steady, splits, sr_dps_coupling,
      dead_spot_timing, accel_asymmetry, breathing_dip); whole (phase_time_budget,
      phase_dist_budget, vel_envelope, jerk_smoothness). Use short snake_case keys + human labels +
      units ("s","m","m/s","m/s^2","%","count","ratio",""); tiers per the ✅/🟡/🔶 feel
      (✅/🟡 → low/medium, 🔶 → high). Getting a tier slightly "wrong" is fine — it is re-rankable in
      Step 2; the point is that the SPACE exists. Do NOT invent metrics beyond the taxonomy.
    - `compute_phases(ctx: PhaseContext) -> dict`: partition REGISTRY by phase; return
      `{"schema_version": SCHEMA_VERSION, "go_signal_s": ctx.go_signal_s,
        "start": {...}, "underwater": {...}, "swim": {...}, "whole": {...}}` where each phase maps
      key -> `{"value": v, "unit", "label", "tier", "status"}`. For status=="implemented" specs call
      `spec.compute(ctx)` inside a per-metric try/except (failure -> value None, never raises); for
      "planned" specs value is None. With today's all-planned REGISTRY every value is None — that is
      the intended skeleton output.

    Avoid: importing api.py or supabase; any DB/file access; implementing any metric; reading raw CSV;
    a plugin/registration framework — REGISTRY is a plain literal tuple edited by hand in Step 2.
