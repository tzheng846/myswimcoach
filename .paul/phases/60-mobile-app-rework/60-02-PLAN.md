<objective>
## Goal
Replace pinch-to-zoom with a draggable window bar, and give `VelocityChart` the one primitive that
Plan 60-03's rolling video window will also need: **a controlled `[tStart, tEnd]`**. (D6, D7)

Three things:
1. A pure `chartWindow.js` — window clamping, in-window resampling, pixel↔time mapping. Pure
   because there is **no jest on mobile**, so the only way to verify this math without a paid EAS
   build is to run it in node (58-01's `clampAutoStopS` precedent, reused in 60-01's
   `dropoutWarning`).
2. `VelocityChart` accepts a controlled `window` prop, loses pinch entirely, and picks up the three
   performance fixes that decide whether 60-03's 20 Hz rolling window feels smooth.
3. A brush strip — full-trace mini-chart with two draggable handles and a draggable body.

## Purpose
The user's words: *"pinch zoom on velocity trace is too annoying. Do the same method as web — a bar
window with adjustable length and scrubbable."*

The web `<Brush>` cannot be ported — recharts is web-only and `react-native-svg` is all mobile has —
so this is hand-built. Doing it once, as a controlled primitive, is what stops 60-03 from becoming a
second implementation of the same windowing math.

## Output
- `src/lib/chartWindow.js` — NEW, pure, node-runnable.
- `src/components/VelocityChart.js` — controlled window, brush strip, pinch removed, memoized.
- `src/screens/ReportCardScreen.js` + `src/screens/RecordScreen.js` — one `brush` prop each (D12).
</objective>

<task type="auto">
  <name>Task 1: Pure windowing math in chartWindow.js, verified in node</name>
  <files>swimnetics-mobile/src/lib/chartWindow.js</files>
  <action>
    Create the module with no React and no react-native imports — it must be importable by node
    directly, the way `dropoutWarning.js` is. Export:

    - `MIN_SPAN_S = 0.5` — the floor that stops brush handles crossing. Matches the `> 0.5` guard
      the pinch code used at `VelocityChart.js:145`, so behaviour carries over rather than changing.
    - `clampWindow(win, tMin, tMax)` → `{tStart, tEnd}`. Keeps the window inside the trace,
      **preserving its span when panning** (the existing pan code at `:169` gets this right — reuse
      the logic, do not reinvent it), and enforcing `MIN_SPAN_S`. A window wider than the trace
      collapses to the full trace.
    - `resampleWindow(time, velocity, tStart, tEnd, maxPoints)` → `{indices}`. Selects the sample
      indices inside `[tStart, tEnd]`, skips null/NaN velocities, and strides to at most
      `maxPoints`. **This is the fix for the 17-point problem** — striding must be computed from
      the count of in-window samples, not from the full trace length.
    - `timeToPx(t, tMin, tMax, width, pad)` and `pxToTime(px, tMin, tMax, width, pad)` — inverses
      of each other, matching the existing `px()` at `:115`.
    - `fullRange(time)` → `{tStart, tEnd}` for the first/last finite entry.

    Every function must tolerate degenerate input without throwing: an empty or 1-element `time`,
    `tMax === tMin`, `width <= pad*2`. Return something sane rather than NaN — the chart's callers
    include a live-updating video page where one NaN would blank the trace mid-playback.

    Then write a node script in the scratchpad exercising AC-1's cases plus the degenerate ones, and
    paste its output into the SUMMARY. Do not add a test framework to the mobile repo.
  </action>
  <verify>node script prints expected values for every AC-1 case and every degenerate case; no throws, no NaN</verify>
  <done>AC-1 satisfied: windowing math correct and proven without a device.</done>
</task>

  <files>swimnetics-mobile/src/components/VelocityChart.js</files>
  <action>
    **Behaviour-preserving except for pinch.** This is deliberately separated from Task 3's brush,
    following the lesson Phase 59 D14 recorded: a refactor sharing a diff with a new feature makes
    an unexpected movement unattributable, and this codebase has a documented history of silent
    drift (51/52/57/59).

    **Remove**, entirely: `pinchRef`, the `touches.length >= 2` branch (`:132-150`), the
    `zoomWindow` internal state (`:32`) and `zoomWindowRef`, the pan-when-zoomed branch
    (`:155-170`), the double-tap reset (`:60-65`), and the "Reset zoom" button (`:234-238`) with its
    `vcStyles`. ⚠ The double-tap reset is already dead code in practice —
    `onStartShouldSetPanResponder: () => false` (`:46`) means a plain tap never grants the
    responder, so it only ever fired if the user dragged twice. Deleting it removes a bug, not a
    feature; say so in the SUMMARY rather than presenting it as a loss.

    After removal the chart body's single-finger drag has exactly one job: the velocity cursor.
    Keep the cursor, its 2-second auto-hide, and `onInteractionStart`/`onInteractionEnd`.

    **Add** the controlled prop: `window = null`. When non-null it wins; when null the chart shows
    the full trace. Task 3 adds internal brush state, at which point the resolution becomes
    `window ?? internalWindow ?? full` — the standard controlled/uncontrolled pattern. Do not lift
    window state into the screens; that would make Task 3's call-site change more than one prop.

    **The three performance fixes**, all measured at discussion time and all invisible until run at
    20 Hz on a device:
    1. `useMemo` the full-trace downsample (`:86-95`). The component currently has **no `useMemo`
       anywhere** and re-walks the whole sample array on every render.
    2. Resample **within** the window via `resampleWindow`. Today `:98-100` filters an
       already-globally-decimated index list, so a 2 s window of a 47 s trace keeps ~17 points.
    3. **Pin the y-scale to the full trace whenever a window is active.** `vMin`/`vMax` come from
       the visible slice at `:107-108`; under a rolling window that rescales 20×/second and the
       trace visibly jitters. Unwindowed behaviour is unchanged — y still fits the data.

    Also replace the `Math.min(...v)` / `Math.max(...v)` spreads (`:107-108`) with a loop. Spreading
    ~400 arguments per render is wasteful and will throw on very large arrays.

    ⚠ Three call sites consume this component — `ReportCardScreen.js:473`, `RecordScreen.js:929`,
    `VideoOverlayScreen.js:170`. All must keep working untouched in this task. **VideoOverlay in
    particular must render exactly as before**; 60-03 wires its window, not this plan.
  </action>
