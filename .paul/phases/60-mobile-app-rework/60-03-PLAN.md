<objective>
## Goal
Make a session's video reachable forever, and make the trace beside it readable. (D4, D5, D11)

1. **A `▶ Video + Velocity` button on the report card**, shown only when the session has video.
   It fetches a signed URL and opens the existing overlay screen. Today the overlay is reachable
   from exactly one place — the just-recorded results state — and only with a *local* file path, so
   navigating away makes the footage unreachable on the phone forever. (D4)
2. **A short window that follows the playhead** — presets 1 s / 2 s / 5 s / All, default 2 s. (D5)
3. **Stored origin wins, and the read path never auto-writes.** (D11)

## Purpose
The user's ask: *"a way to view the video + velocity trace in the session card. currently its only
viewable immediately after recording"* and *"the velocity trace is too zoomed out. show the user
just a 2 second window that rolls along with the video."*

This is the last plan of Phase 60. It is also the one with a data-loss hazard rather than a display
bug: `VideoOverlayScreen` currently **auto-posts** a recomputed `video_origin_s` the moment it knows
one. Reached from a second entry point, that would silently overwrite an origin the user had already
nudged into place — the same silent-plausible-corruption shape Phases 51, 52, 57 and 58 each found.

## Output
- `ReportCardScreen.js` — video button + signed-URL fetch.
- `VideoOverlayScreen.js` — remote source, stored-origin precedence, write guard, rolling window.
</objective>

### ⚠ Diagnosed but NOT fixed — recorded deliberately
The user also reported the trace "dancing" during playback. **One cause was measured and fixed**
(D15, above: span 5 s showed two alternating lattice phases). **At 1 s and 2 s the resampling is
provably stable** — constant point count, single lattice phase — so if it still dances at the
default 2 s, the lattice was not the cause.

Leading unverified hypothesis: `player.currentTime` wobbling between polls. The window is centred
on it, so a ±10 ms wobble moves the whole trace ±2 px at 20 Hz.
**Diagnostic if it persists:** log successive `currentTime` deltas in the poll at
`VideoOverlayScreen.js:103`; if they are not a steady ~0.05 s, that is it, and the fix is to advance
the window on a monotonic clock rather than raw player time. Not speculatively "fixed" here, because
it has not been measured.
