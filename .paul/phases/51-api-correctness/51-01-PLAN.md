<objective>
## Goal
A full correctness and leanness audit of `api.py` — every endpoint, every database call, every
column, every swallowed exception — producing one ranked findings document. **No production code
changes.** Fixes land in 51-02, informed by what this finds.

## Purpose
Three defects in a row (Phase 45 `device_id`, Phase 48 `.single()`, and the still-open phantom
`athletes.coach_id`) were all found the same way: a user hit them in production. None was caught by
149 passing tests, because the DB layer is mocked with a `MagicMock` that answers every attribute.
`api.py` is 1808 lines and 24 endpoints, it is the sole path between the iOS app, the web portal and
the database, and it is about to carry a customer demo.

The phantom-column bug already proved that a single wrong column name silently breaks four
unrelated features. Auditing before fixing means 51-02 fixes the whole class at once, rather than
patching the one site that happened to throw a visible error.

## Output
- `tools/introspect_schema.py` — read-only live-schema snapshot generator (audit instrumentation)
- `supabase/live_schema.json` — committed snapshot of the real schema
- `API-AUDIT.md` at repo root — findings ranked by severity, each with file:line, reproduction,
  blast radius, and a recommended fix (**not applied**)
</objective>

## Already-known findings — confirm, quantify and rank; don't re-derive
1. **Phantom `athletes.coach_id` at four sites** — the open live bug. Confirm the blast radius:
   - `api.py:1298` POST /athletes insert → hard 500 PGRST204
   - `api.py:1277` POST /athletes limit count → raises → `except: count = 0` → **athlete limits have
     never been enforced**
   - `api.py:1517` /coach/chat `_load_roster_rows` → raises and **deliberately propagates** → team-wide
     chat broken since Phase 33-02
   - `api.py:1784` GET /billing/status → raises → `except: pass` → `athlete_count` always 0
   `api.py:513-515` already documents that athletes must be scoped by `team_id` — the file
   contradicts itself. Confirm `team_id` availability at each site (two coach-row selects do not
   currently fetch it).
2. **Dual limit systems.** `coaches` carries `athlete_limit`/`device_limit`/`monthly_session_limit`
   while `teams` carries `swimmer_limit`/`device_limit`/`coach_limit`. Phase 39-03 shipped an iOS
   display reading `teams.swimmer_limit ?? 20`; `api.py` enforces `coaches.athlete_limit` (default 3).
   **The number the app shows and the number the API enforces are different columns.** Determine
   which is authoritative — this feeds 51-02's limit toggle.
3. **Duplicated billing state.** `subscription_tier` and `stripe_customer_id` exist on BOTH `coaches`
   and `teams`. Determine which the Stripe webhook writes and which the reads trust.
4. **11 hand-rolled coach lookups.** `_get_coach_row` exists at L1330 but is used at only ~5 sites;
   L342, 431, 500, 632, 670, 722, 1016, 1158, 1184, 1210, 1396 each re-implement it inline with
   varying select lists and error handling. Prime leanness target — but diff the variants before
   recommending consolidation.
5. **Swallowed exceptions that produce wrong data.** `except: pass` / `count = 0` patterns turn a
   failed query into a confident wrong answer — exactly how the phantom column stayed invisible in
   `/billing/status`. Enumerate all of them; classify surface-as-5xx vs legitimately-non-fatal.
6. **No input validation layer.** Six handlers hand-parse `await request.json()` + `body.get(...)`
   with no schema. Assess real risk given every route is authenticated, and say plainly whether
   pydantic models are worth it or would be ceremony.
7. **`GET /sessions/{id}/export` has no caller** anywhere (iOS builds its CSV client-side). Confirm,
   then recommend keep-or-delete.
8. **⚠ Sample-rate contract violation — likely the highest-severity item here.** Per
   `50-01-SUMMARY.md` finding #5: `run_pipeline` decimates by an integer factor, so stored profiles
   are ~**89.51 Hz**, not 100 Hz. But `annotations.py` hardcodes `FS_HZ = 100` and api.py's
   annotation recompute builds `t_arr = np.arange(size) / annot.FS_HZ`. On real sessions the annotate
   page misreports a 47.1 s swim as 42.2 s, and **recomputing metrics from a saved annotation shifts
   every time-derived metric by ~11.7%**. Verify independently, quantify the blast radius, and rank.
   Do **not** fix it — it is its own phase and should probably precede 50-02.

## Task 1: Introspection tooling + schema snapshot
**Files:** `tools/introspect_schema.py` (new), `supabase/live_schema.json` (new)

Fetch `{SUPABASE_URL}/rest/v1/` — PostgREST's OpenAPI document — and write `{table: {column: type}}`.
Read-only: catalog metadata only, no table data, no writes.

Requirements:

- `--out PATH`, default `supabase/live_schema.json`.
- Exits non-zero with one clear line if the host is unreachable or credentials are missing.
- Docstring states that the snapshot is point-in-time and how to refresh it.

**Verify:** exits 0; the file contains `athletes` **without** a `coach_id` key.

## Task 2: Endpoint and data-flow inventory
**Files:** `API-AUDIT.md` (create)

Enumerate all 24 routes. For each: method + path, auth requirement, tables read/written, scoping
column, which client calls it (grep `web/` and `../swimnetics-mobile/src/`), and whether behavior
matches `CLAUDE.md`. Flag undocumented routes and documented-but-absent ones.

**Verify:** route count matches `grep -c "^@app\." api.py`; every route appears exactly once.

## Task 3: Schema contract sweep
Build an **AST-based** extractor: parse `api.py`, walk call chains rooted at `.table("<name>")`,
collect column literals from `.select("a, b")`, `.eq/.neq/.gt/.gte/.lt/.lte/.is_/.in_("col", …)` and
`.order("col")` within that chain. Check each against the snapshot.

Use `ast`, **not** regex. A regex over source text picks up response-dict keys (`"session"`,
`"cycles"`, `"ok"`) that are not columns — a throwaway regex version produced roughly two false
positives per true hit. Walking the AST scopes names to genuine builder chains and eliminates that.

Handle: `.select("*")`, `count="exact"`, and PostgREST embedded-resource selects (`athletes(name)`)
without emitting false failures. Report both directions — code-references-missing-column, and
live-columns-never-touched.

Keep the extractor in a form 51-02 can promote into a permanent test.

**Verify:** the sweep reproduces the four known `athletes.coach_id` hits and no false positives on
`sessions`/`devices`/`reports`.

## Task 4: Consistency, leanness and error-handling review
Work through known findings 2-7 plus anything new:
- Ownership rule per table, and every deviation.
- The two competing limit systems — which is authoritative, and what the app actually displays.
- The 11 inline coach lookups — diff them; recommend consolidation only where behavior is identical.
- Every `except` that swallows: classify surface-as-5xx vs legitimately-non-fatal.
- Duplicated/dead code, endpoints with no caller.

**Verify:** each finding cites file:line and is independently reproducible from the citation.

## Task 5: Sample-rate contract investigation
Verify known finding #8 independently: read `vel_acc_extraction.run_pipeline`'s decimation, compute
the true output rate, and trace how `annotations.FS_HZ` and api.py's recompute path consume the
stored profile. Quantify the real error percentage, which endpoints are affected, how many stored
sessions carry recomputed metrics, and whether `sessions.metrics_json_auto` makes it reversible.

Report only. Recommend a phase boundary and whether it must precede 50-02.

**Verify:** the error figure is derived from the code, not quoted from the prior summary.

## Task 6: Rank, cross-reference, write up
Order findings by severity. Cross-reference 49-01 for security items rather than restating them.
Close with the recommended fix sequence (AC-5) and a "what this audit could not check" section
(runtime behavior, RLS policy correctness, concurrency, anything needing live data).

**Verify:** `API-AUDIT.md` satisfies AC-1 through AC-6.
