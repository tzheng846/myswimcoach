## Why `team_id`, not "add the column"
Athletes belong to a team; coaches belong to a team. The web portal scopes the roster by RLS team
policy, `api.py:516-521` scopes it by `team_id`, and `seed_demo_team.py:487` inserts athletes with
`team_id` and no `coach_id`. Adding `coach_id` would introduce a second, redundant ownership axis
and require backfilling every existing athlete.

**Behavior change to state explicitly:** on a multi-coach team, athlete counts and the chat roster
become team-wide rather than per-coach. That is the intended semantics (`teams.coach_limit` exists;
`athletes` has no per-coach ownership) and matches what the portal already displays.

## Athlete limit — RESOLVED ELSEWHERE, no longer this plan's job
The 2026-07-30 decision (disable enforcement, keep it trivially re-enablable) has already been
implemented by **54-01**, which chose ONE switch for all three tier limits rather than an
athlete-specific one:

- `ENFORCE_TIER_LIMITS` at `api.py:34`, `os.getenv(..., "0")`, default **off**
- already wraps the athlete-limit block at `api.py:1308` (`if ENFORCE_TIER_LIMITS and limit is not
  None:`), so the count query does not run when off
- the `if limit is not None` NULL-means-unlimited behavior is preserved nested inside, exactly as
  the original decision required

Task 2 is therefore **struck**. Adding `ENFORCE_ATHLETE_LIMIT` now would double-gate the same block
with two switches. This plan still fixes the *column* on that count query (L1311) so the guard is
correct whenever someone flips the switch on.

⚠ 54-01's change is in the working tree and **uncommitted** at the time of this apply.

**A mock-based test cannot guard this bug class.** The guard must be static — hence the AST
extractor.
