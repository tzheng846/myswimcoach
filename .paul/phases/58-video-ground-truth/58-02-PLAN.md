<objective>
## Goal
Make the annotate page usable for reading arm entries off footage, and remove the Breakout
marker from the phase model.

Three outcomes, all verifiable:
1. **Video and chart are visible at the same time** — the video is height-capped and the page
   widened, so the whole editor fits one viewport.
2. **Marks can be placed from the video, frame-accurately** — frame-step + slow-motion + a
   "mark at the playhead" key, so the video can drive annotation instead of merely accompanying it.
3. **Breakout is gone from the contract and the UI** — and, critically, **no metric changes and
   no session recomputes**.

## Purpose
Phase 58's goal 3 is *"make annotation driven by the footage."* Today it cannot be: the video is
rendered unbounded (`VideoPane.js:143`, `w-full`, no height constraint) inside a `max-w-5xl` page,
so on any normal viewport it pushes the 340 px chart off-screen. You cannot mark an arm entry on a
trace you cannot see next to the footage you are reading it from. That is the blocker this plan
removes — and it is the direct consequence of Phase 57's still-unanswered **R1** (whether ~40
arm-entry marks are placeable from the trace alone; the answer, from the 19-session batch, was no
for freestyle and backstroke).

Breakout removal rides along because it lands in the same three web files and the user has already
stopped placing the marker in practice.

    **Height cap (D6).** Change the `<video>` className (`:143`) from `w-full rounded-lg bg-black`
    to `w-full max-h-[34vh] rounded-lg bg-black object-contain`.
    - `object-contain` is what letterboxes portrait footage inside the capped box instead of
      letting its aspect ratio set the page height. Without it the cap crops.
    - 34vh, not 50: on a 900 px viewport the page must also seat ~110 px of header, the sync row,
      the new controls row and a 340 px chart. AC-1 is the real arbiter — if it fails at the
      checkpoint, tune this one number and nothing else.

    **Playback speed.** Add `const [rate, setRate] = useState(1)` and a 0.25× / 0.5× / 1× button
    group, styled like the existing sync-offset buttons. Apply it in an effect keyed on
    `[url, rate]` (`v.playbackRate = rate`) AND in an `onLoadedMetadata` handler — loading a new
    `src` resets `playbackRate` to 1, so setting it once on click silently reverts.

    **Frame step.** Add `const FRAME_S = 1 / 30` at module scope with a comment that 30 fps is an
    assumption (HTML5 video exposes no frame rate; `requestVideoFrameCallback` would, and is
    deliberately not used here — it is a bigger change than this plan warrants).
    Add a `step(frames)` function:
    - `v.pause()` FIRST — stepping during playback fights the playhead.
    - `v.currentTime = clamp(v.currentTime + frames * FRAME_S, 0, v.duration)`.
    - Call `onPlayhead?.(originS + v.currentTime)` explicitly. Do not rely on `timeupdate`; it is
      throttled and does not reliably fire for sub-100 ms seeks, which would leave the chart
      playhead stale exactly when precision matters.
    Render `−1 frame` / `+1 frame` buttons.

    **Expose the step to the page.** Add a `frameStepRef` prop and assign
    `frameStepRef.current = step` in an effect, mirroring the existing `seekRef` contract at
    `:49-61` exactly — including the cleanup that nulls it. Buttons are the primary affordance;
    the keyboard binding in Task 3 is the accelerator, and it must keep working when the video
    element does not have focus.

    Do not restructure the component, the upload path, or the sync-offset row.
  </action>
