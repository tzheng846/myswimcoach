<objective>
## Goal
Build the **instrument before the experiment**. Deliver the analysis tool that answers Track A5 —
*which of the 18 session metrics can carry an alert?* — plus the written collection protocol that
makes the pool day produce analyzable data.

Nothing in this plan requires the pool day to have happened. It is the tooling that makes the pool
day worth doing.

## Purpose
Phase 53's go/no-go is A5: measure the noise floor, detect segmenter saturation, and rank metrics by
usability. If no metric survives, Tracks B–D are moot. Building the analyzer first means the moment
clean data lands the answer is one command away — and, critically, it means the collection protocol
can be written against what the analyzer actually needs rather than guessed at afterward.

Secondary payoff: because the analyzer reads `actual_fs` from `run_pipeline` rather than assuming
100 Hz, it answers Phase 52's open question ("does the sample rate vary session to session?") for
free, without touching any file Phase 52 owns.

## Output
- `repeatability.py` — pure noise-floor / saturation / usability logic, no I/O
- `tools/analyze_repeatability.py` — CLI: raw CSVs → pipeline → metrics → printed report
- `tests/test_repeatability.py` — synthetic fixtures with *known* injected variance
- `COLLECTION-PROTOCOL.md` — the pool-day checklist
</objective>

  <name>Task 1: repeatability.py — pure noise-floor, saturation, and usability logic + tests</name>
  <files>repeatability.py, tests/test_repeatability.py</files>
  <action>
    Create `repeatability.py` at repo root as a PURE module — no I/O, no plots, no network. Match the
    conventions of `ratings.py` / `annotations.py` (module docstring stating the contract, `_is_num`
    style guards, plain dicts in and out).

    Public API:

    - `summarize_trials(trials, rails=None)` — `trials` is an ordered list of flat metric dicts
      (metrics.py `session` keys merged with `data_quality`). ORDER MATTERS: the moving range is
      computed on consecutive trials as collected. Returns
      `{"n_trials": int, "metrics": {key: {...}}, "warnings": [...]}` where each metric entry has
      `n`, `n_missing`, `mean`, `sd`, `cv`, `median`, `mad`, `sigma_mr`, `mdc_abs`, `mdc_pct`,
      `saturated`, `saturation_reason`.
      - `sigma_mr = mean(|x_i - x_{i-1}|) / 1.128` — the SPC individuals-chart estimate. Use this,
        not the plain SD, as the primary noise figure: it is insensitive to slow drift, which is
        exactly the thing we later want to DETECT rather than absorb into the limits.
      - `mdc_abs = 3 * sigma_mr`; `mdc_pct = 100 * mdc_abs / |mean|` (None when mean is ~0).
      - Skip non-numeric and boolean values (the data_quality flags are booleans — they belong in
        the input dict but must not be treated as metrics).
      - n < 2 usable values → `sigma_mr`/`mdc_*` = None, plus a warning. Never raise.

    - `default_rails()` — DERIVE the wavelet stroke-rate rails from metrics.py rather than
      hardcoding: `{"stroke_rate_spm": (60.0 / metrics._PERIOD_MAX_S, 60.0 / metrics._PERIOD_MIN_S)}`
      → (15.0, 120.0) today. Import metrics lazily or read the constants defensively so a rename
      surfaces as a clear error, not a silent wrong ceiling.

    - Saturation rules, applied inside `summarize_trials`:
      - any trial value within a small epsilon of a rail → `saturated=True`, reason naming the rail
        and how many trials sit on it;
      - `sd == 0` or `cv` below a near-zero constant → `saturated=True`, reason "zero variance".
      Zero variance MUST read as suspect, never as perfect repeatability — a railed or stuck metric
      is the failure mode this whole check exists to catch.

    - `rank_usability(summary, min_trials=3, max_missing_frac=0.0)` — returns
      `{"usable": [...], "excluded": [...], "caveat": "<string>"}`. `usable` = non-saturated metrics
      meeting the data gate, ascending by `cv`, each `{key, cv, sigma_mr, mdc_pct}`. `excluded`
      carries `{key, reason}`. `caveat` states in words that low CV means REPEATABLE, not
      DISCRIMINATIVE — a metric can be perfectly repeatable and still useless if it never differs
      between athletes or across time.

    - `fs_spread(fs_values)` — `{min, max, mean, spread_pct, varied: bool}` over per-trial sample
      rates. `varied` True when spread_pct exceeds a small threshold.

    Then create `tests/test_repeatability.py` in the style of `tests/test_ratings.py` (plain pytest,
    no network, no fixtures beyond synthetic dicts). Cover:
      - sigma_mr recovers a KNOWN injected sigma on a generated series within a stated tolerance
        (use a fixed seed; assert a real tolerance, not just "is not None");
      - a series pinned at 120.0 SPM is flagged saturated naming the ceiling;
      - a series pinned at 15.0 SPM is flagged saturated naming the floor;
      - a constant non-rail series is flagged zero-variance, NOT ranked usable;
      - boolean data_quality keys are excluded from the metric table;
      - n=1 and n=0 return None figures with a warning and do not raise;
      - rank_usability orders by cv ascending and lists every excluded metric with a reason;
      - fs_spread reports varied=True on a set with differing rates.

    Avoid: numpy-only APIs that would force a dependency shift — numpy is already a dependency, use
    it, but keep the module importable without scipy/pywt (it must not import metrics' heavy path
    just to read two float constants).
  </action>
