<objective>
## Goal
Eliminate the two confirmed recording defects in one pass: (1) the startup velocity
pulse, caused by a ~52 ms transient of garbage angle reads at record start (trace head:
`3444 ×12 → 0 → 488 → 651…`, true=651), and (2) the BLE dump sample loss that grows with
recording length (firmware buffers N, iOS receives fewer).

## Purpose
These are the two things standing between the device and usable recordings. 44-01 proved
the sensor read is otherwise clean (1183±1) and localized both defects: the pulse lives in
the firmware buffer at record start; the loss is BLE notify congestion during DUMP.

## Output
- Firmware: a record-start warmup gate (clean buffer from sample 0) + guaranteed-delivery
  dump (no dropped packets).
- iOS: whatever is needed for guaranteed delivery to work end-to-end (ideally none — verify).
</objective>

  <name>Task 1: Record-start warmup gate (kills the pulse at the source)</name>
  <files>ESP_32_V5/ESP_32_V5.ino</files>
  <action>
    In startRecording(), after the magnet check and BEFORE buffering begins, discard reads
    until the angle has settled, so sampleBuf[0] is the true value:
    - Loop reading readAngle() at the sample interval, discarding results, until either
      K consecutive reads are within ±TOL counts of each other (settled) OR WARMUP_MAX_MS
      has elapsed (bound it). Suggested: K=5, TOL=4, WARMUP_MAX_MS=100 — tune from the trace
      (observed transient ≈52 ms). Seed lastGoodAngle from the final warmup read.
    - Only then set recording=true / lastSampleUs=micros() and start buffering.
    - Keep it a bounded blocking loop in startRecording (≤100 ms; BLE runs on its own task).
    Rationale: the transient is time-based (~52 ms), so a few fast throwaway reads are NOT
    enough — gate on stability/time. Note the Phase-41 race-start interaction: the cap is the
    max data lost after the blare; 100 ms mostly overlaps reaction time, but keep it small.
    Avoid: an unbounded wait (a moving start never "settles" → must hit the cap).
    Quick confirm available to the user: a BUTTON-started recording (no BLE) — if its trace
    head is ALSO 3444→…, the transient is sensor/bus (warmup is right); if clean, it's
    BLE-write-timing at START (warmup still fixes it). Either way the warmup is the fix.
  </action>
  <verify>TRACE_BUFFER trace head starts at the true angle (no 3444/0/488); app velocity
    shows no startup pulse.</verify>
  <done>AC-1 satisfied.</done>
</task>

<task type="auto">
  <name>Task 2: Guaranteed-delivery dump via ATT indications</name>
  <files>ESP_32_V5/ESP_32_V5.ino, ../swimnetics-mobile/src/screens/RecordScreen.js</files>
  <action>
    Make the TX path acknowledged so the dump can't outrun the link (no silent drops):
    - Firmware: give the TX characteristic the INDICATE property (instead of / in addition
      to NOTIFY such that the client subscribes to indications) and send DUMP sample packets
      as indications — `pTxChar->notify(false)` (Bluedroid waits for the ATT confirm, which
      provides flow control). Apply the same send path to META, STATUS, and the 0xEE end
      marker (all go through pTxChar). The per-packet vTaskDelay(5 ms) is then redundant —
      the confirm paces it; drop or shrink it. Keep the `if (!deviceConnected) return` abort
      guard; ensure the indicate confirm has a sane timeout so a mid-dump disconnect can't
      hang the loop.
    - iOS: monitorCharacteristicForService()/CoreBluetooth enables the indicate CCCD
      automatically when the characteristic is indicate-capable, so ideally NO iOS change —
      VERIFY by checking the received count equals # DUMP_SENT. Packet formats are unchanged
      (7-byte samples, 8-byte META, 1-byte 0xEE), so parsePacket() is untouched.
    - FALLBACK (only if ble-plx keeps subscribing to notifications and loss persists):
      app-driven windowed flow control — firmware sends a window of K packets then waits for
      an "ACK" written to RX before the next window. Document this; do not build unless needed.
    Note the tradeoff: indications send ~one packet per connection interval, so the dump is
    slower than the old fire-and-forget notify (a ~25 m swim ≈ a few seconds). Correctness
    over speed; packet-size or connection-interval tuning is a later optimization, not this plan.
  </action>
  <verify>Record N > 2000 samples; # DUMP_SENT == iOS received count == # TRACE n=
    (the old build lost packets at this N).</verify>
  <done>AC-2 satisfied.</done>
</task>
