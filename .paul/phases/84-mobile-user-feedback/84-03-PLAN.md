<objective>
## Goal
Ship **item 5 — indicator formalization**: collapse the app's four independent band vocabularies
into one shared module, so the same pillar reads the same way on the roster, the athlete page, the
dashboard and the report card.

## Purpose
The user reported "disparity between athlete page indicator and dashboard". The disparity is real,
but **it is not the one CONTEXT diagnosed** — see G20 below. What a coach actually sees today for
one identical pillar is four different *forms*: a colored dot on the roster, a lowercase word on
the athlete page, a 0-100 number on the dashboard, and a title-case word over a meter on the report
card. Three of those four derive the vocabulary inline, so the day the server's colors or bands
change, they will drift apart in three different directions.

## Output
- One pure, node-importable module owning band label, band color and the provisional/unknown
  treatments, plus one shared dot component.
- Four surfaces rewired to it; every local band map and inline band ternary deleted.
- A headless harness in the backend repo that proves the vocabulary is single-sourced and total,
  and prints a specimen matrix so the visual call can be judged **without** paying for a build.
- No endpoint change, no payload change, no backfill. The data was always there and always correct.
</objective>

### G20 — `provisional` is structurally unreachable. CONTEXT's item-5 consequence cannot happen today.
`ratings.py:206` is the whole rule:
```python
provisional = (thr_table is None) or (thr is None)
```
Both halves are dead:
- `thr_table` is `THRESHOLDS.get(stroke) or THRESHOLDS["breaststroke"]` (`:251`) — **never None**
  since Phase 54 made every stroke borrow the breaststroke table.
- `thr` is `thr_table[primary_key]`, and all four pillar primary keys — `mean_vel_ms`,
  `mean_dps_m`, `cv_arm_peak_vel`, `fatigue_index_pct` (`:58,72,87,97`) — **are present** in that
  table (`:110,111,133,134`).

So `provisional` is `False` for every pillar, every stroke, every session. `tests/test_ratings.py:142`
confirms it from the other side: the test named `test_provisional_driven_by_missing_threshold`
could not construct a provisional pillar and had to assert `is False` instead.

Consequences that rewrite the item's justification:
- `PillarCards.js:166-168`'s provisional banner **has never rendered**.
- `DashboardScreen.js:39`'s provisional exclusion **has never excluded anything**.
- `ratings.py:334`'s "an untrusted band must never raise an alarm" skip **never skips**.
- Therefore **there is no device test for provisional.** Any human-verify step asking the user to
  find a provisional pillar would be unsatisfiable. It is asserted by the harness on synthetic
  input instead (AC-3).

The flag is dormant, not wrong — it becomes live the moment a new pillar's primary metric has no
threshold row, or a per-stroke table omits a key, or Phase 54's one-line `seg_reliable` gate is
restored (`ratings.py:203-204` keeps the parameter for exactly that). Handling it correctly by
construction is cheap; **claiming to have fixed a visible bug is not honest**, and the SUMMARY must
say so.

### G21 — The band *colors* are byte-identical between the server and the theme, so the hardcode is latent drift, not a live defect.
`ratings.py:33` -> `good #2d9e5f, ok #d4860a, needs_work #c0392b`.
`tokens.js:40-42` -> `good #2d9e5f, ok #d4860a, needsWork #c0392b`.
`AthleteDetailScreen.js:18`'s hardcoded `BAND_COLOR` therefore renders **exactly the same pixels**
as the three surfaces that read the payload. The defect is real but it is a *drift* defect: the
server owns the color contract (`tokens.js:39` says so in the source), and one client has silently
opted out of it. Nothing visibly changes on that screen when it is fixed. Do not oversell it.

### G22 — What the user actually sees is four different indicator FORMS for one band.
| Surface | Form | Label vocabulary |
|---|---|---|
| `AthletesScreen` | a 10px colored **dot**, 4 per row | none |
| `AthleteDetailScreen` | a **lowercase word** (`good` / `ok` / `needs work` / `—`) | `:16` |
| `DashboardScreen` | a **0-100 number** + a reason chip | none |
| `PillarCards` | a **title-case word** (`Good` / `OK` / `Needs work`) over a 0-100 meter | `:12` |

That is the reported disparity, and it is fully observable. D3 settles it: band label + color is
canonical; the dashboard's 0-100 score stays as a secondary roll-up.

### G23 — `unknown` IS reachable, and it is where the four surfaces genuinely diverge.
`ratings.py:200,207` set `band="unknown"`, `score=None` whenever the primary metric is missing or
not a number (`cv_arm_peak_vel` on a session with too few cycles, for instance) — no threshold
involvement, so unlike `provisional` this fires on real data. The four surfaces answer differently:
- roster -> `rc['unknown']` is undefined -> `BAND_FALLBACK['unknown']` is undefined -> a
  `textMuted` dot, indistinguishable from a rendering failure;
- athlete page -> `BAND_LABEL.unknown` = `'—'` in `textMuted`;
- report card -> the sentence "Not enough data", and the meter is suppressed;
- dashboard -> silently absent from the average.
**`unknown` is the band this plan can actually be verified against on a device**, and the canon has
to name it (see G24).

### G24 — `rating_colors` has only THREE keys, so a server-first lookup is not total.
`ratings.py:33` has no `unknown` entry, and correctly so — `unknown` means "no rating", so there is
nothing for the rating engine to color. The shared module must own that one color itself, or a
fourth band resolves to `undefined` and RN silently draws nothing. Today all four call sites paper
over this with their own trailing `|| colors.textMuted`. ⚠ Do NOT add `unknown` to `RATING_COLORS`.

### G25 — The contract this plan enforces is already written down, and honored by 1 of 4 surfaces.
`src/theme/tokens.js:39`, in the source, above the band tokens:
```
// Rating bands (fallback only — band UI must read colors from the API payload)
```
`AthletesScreen.js:84` obeys it. `PillarCards.js:67-68` obeys it but re-derives it inline.
`DashboardScreen.js:109` obeys it partially (G26). `AthleteDetailScreen.js:18` ignores it (G21).
This is not a new convention to invent; it is an existing one to enforce in code.

### G26 — `DashboardScreen.js:109` mixes the two key vocabularies and works by accident.
`const rc = data?.rating_colors || colors` — band keys are snake_case (`needs_work`), theme keys are
camelCase (`needsWork`). When that fallback engages, `rc.needs_work` is `undefined` on every read;
it renders only because the call site chains `|| colors.needsWork` (`:124`). `rc.ok` and `rc.good`
resolve by coincidence, their key names colliding across the two vocabularies. A latent trap, not a
working fallback; it disappears once the lookup lives in one total function.

### G27 — The label vocabularies disagree on casing, and the canon must pick one.
`AthleteDetailScreen.js:16` -> lowercase. `PillarCards.js:12` -> title case, and no `unknown` entry
(the unknown branch prints "Not enough data" instead, `:78`). Web's
`components/portal/RosterBandCard.js:4` -> `Good / OK / Needs work / No data`.
**Canon = `Good / OK / Needs work / No data`** — it already matches two of three and the coach
portal. ⚠ This is a **visible copy change on the athlete page**: lowercase becomes title case and
`—` becomes "No data". It is the one user-visible change in this plan; judge it at the human-verify.

### G28 — The mobile repo has no test runner and no lint script.
`package.json` scripts are exactly `start / android / ios / web`; no `__tests__`, no jest config, no
eslint config. **"Verify" here cannot mean `npm test`.** This plan brings its own headless harness
into the backend repo, following the 83-05 / 85-01 precedent (`scratch/overlay_render_check.mjs`,
`scratch/marketing_render_check.mjs`).

### G29 — The pure half is genuinely node-importable; the harness needs one rewrite, not a bundler.
`src/theme/tokens.js` has **zero imports** — plain ESM constants — so a harness can `import()` it by
file URL. `src/lib/indicators.js` will `import { colors } from '../theme'`, which Metro resolves and
node ESM does not (no directory-index resolution). The harness reads the module source, rewrites
that one specifier to the `tokens.js` file URL, and imports the result as a `data:text/javascript`
module. No transpile, no JSX, no react-dom — strictly simpler than 83-05's harness, because the
pure module is deliberately RN-free.

### G30 — A blanket "no `colors.needsWork` outside the module" check would false-fail.
`DashboardScreen.js:187` (`<AppText color="needsWork">{error}</AppText>`) and
`AthletesScreen.js:101` (`color={tested ? 'textMuted' : 'needsWork'}`) use the band palette for
things that are **not** pillar bands — a network error and a never-tested athlete. Both are
legitimate and must survive. The static check targets **band-keyed map literals and band ternary
chains**, never the token names. Exact patterns are pinned in Task 1.
