<objective>
## Goal
Ship **item 6 — the brush-bar gesture**: a horizontal drag on the velocity chart's window strip must
keep controlling the window when the finger drifts vertically, instead of being handed to the parent
`ScrollView` mid-drag. The fix is one property on each of two pan responders in **one component**,
which repairs all three consumer screens without touching any of them.

## Purpose
This is the last of the six original user-reported items that is a pure, already-root-caused defect —
the user's words were *"scroll bar feature is annoying — once finger leaves the bar, the scrolling
side to side stops and goes up and down."* The brush strip is the **only** way to zoom the velocity
trace since Phase 60 removed pinch-to-zoom, so when it is stolen mid-drag the chart's one navigation
control is unusable on exactly the screen a coach reads after every swim.

It is planned as its own lane because it is the **only remaining Phase-84 item that touches neither
`RecordScreen.js` nor `CameraView`** — items 2 and 3 both do, and 84-02 already claims
`RecordScreen.js`. This plan therefore has zero file overlap with 84-01, 84-02 or 84-03, needs no EAS
build, and needs no encoder hardware to verify.

## Output
- `../swimnetics-mobile/src/components/VelocityChart.js` — `onPanResponderTerminationRequest` added
  to both `PanResponder.create` configs, each with its reason inline.
- `scratch/gesture_check.mjs` (new, backend repo) — a source-level guard that fails if either
  property is ever dropped, and that proves it is not vacuous by mutating a copy.
- No commit in either repo. No backend change. No `web/` change. No new dependency.
</objective>

Read from code on 2026-08-30. Continues the phase's G-numbering (84-03 ended at G30).

### G31 — CONTEXT's root cause is exact, and the default is confirmed in RN 0.85.3's own source
`node_modules/react-native/Libraries/Interaction/PanResponder.js:520-522`:

```js
return config.onPanResponderTerminationRequest == null
  ? true
  : config.onPanResponderTerminationRequest(event, gestureState);
```

Neither responder in `VelocityChart.js` sets it — the chart-body config runs `:75-94`, the brush
config `:99-118`, and both list only `Grant / Move / Release / Terminate`. So both currently answer
*"yes, take it"* to every request, including the parent `ScrollView`'s. CONTEXT's step-by-step
sequence holds without amendment.

### G32 — `onShouldBlockNativeResponder` needs no change; the fix is one property per responder
`PanResponder.js:468-470` defaults it to **`true`** in RN 0.85.3, not the historical Android-only
`false`. Adding it would be a no-op that reads like a load-bearing line.

### G33 — The bug is WORSE on `RecordScreen` than on the report card, and CONTEXT missed that surface
CONTEXT examined `ReportCardScreen` and `VideoOverlayScreen`. The third consumer is the
post-recording results chart: `RecordScreen.js:994` renders `<VelocityChart … interactive brush
dark />` with **no `onInteractionStart` and no `onInteractionEnd`**, sitting inside the `ScrollView`
opened at `RecordScreen.js:919`. That brush has **no scroll lock whatsoever** — the report card at
least sets `scrollEnabled = false` (`ReportCardScreen.js:538-539`).

This is the argument for fixing it **in the component**: one edit repairs a surface nobody reported,
and it keeps this plan out of `RecordScreen.js`, which 84-02 is already modifying.

### G34 — CONTEXT open question 6 is answered NO, on two independent grounds
`VideoOverlayScreen.js:219` passes neither `interactive` nor `brush`. Both responders are gated on
exactly those props at render (`VelocityChart.js:343` for the body, `:311` for the strip), so on that
screen **neither responder is attached to anything**. Independently, its container is a `SafeAreaView`
(`:200`) and the file contains no `ScrollView` at all. Unaffected twice over — and it stays untouched.

### G35 — A responder does NOT lose the gesture by leaving the view's bounds
Once granted, RN keeps delivering `onPanResponderMove` no matter where the finger travels; the only
way to lose it is termination. So a taller strip or a `hitSlop` would improve the *grab*, not the
*drag*, and would not address the reported symptom at all. Stated explicitly because "make the bar
bigger" is the obvious wrong fix and `BRUSH_H = 30` (`:16`) invites it.

### G36 — The fix has a real cost, and it is the exact mirror of the bug
Refusing termination means a drag that *starts* on the 30 px strip can no longer scroll the page
until the finger lifts — and likewise for a horizontal-dominant drag on the chart body. Two thin dead
zones in a long scrolling report card.

That is a device-feel judgment nobody can make from a chair, so this plan does **not** open with a
decision checkpoint. It implements D6 as written, then puts the tradeoff in front of the user at the
verify with the fallback pre-specified (Task 3), so a "no" is a one-line swap rather than a re-plan.

### G37 — `VelocityChart.js` is the only file in the app with a `PanResponder`
`grep -rn PanResponder src/` in the mobile repo matches nothing outside it. There is no second
instance of this bug elsewhere in the app and no shared gesture helper worth extracting.

### G38 — The guard has to be source-level, and the plan must say so out loud
84-03's **G28** still holds: the mobile repo's `package.json` scripts are `start / android / ios /
web` — no test runner, no linter. And unlike 84-03's pure `indicators.js`, `VelocityChart.js` imports
`react-native` and `react-native-svg`, so it cannot be imported headlessly by rewriting one
specifier. The guard therefore parses the source and asserts on the AST: it proves the
**configuration is present**, never that the **gesture behaves**. Only the device verify proves the
fix, and the harness banner must not imply otherwise.
