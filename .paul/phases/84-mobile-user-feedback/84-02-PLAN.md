<objective>
## Goal
Ship **item 7 — the coach GO marker**: a silent button on both live recording states that stamps
the moment the coach sends the swimmer off, converts it onto the session clock, and delivers it
with the session so `reaction_time` computes on the **first** pass. Switch off the Phase-41
race-start sequence in the same change (D9), since the horn is what currently makes an honest GO
stamp impossible.

## Purpose
This closes **STATE item 15** and fills a metric that is **0 of 99 sessions** today. Every other
piece already shipped in Phase 75-04 — storage (`PUT /sessions/{id}/go-signal`), the metric
(`_compute_reaction_time`), and the anchor (motion onset from `detect_phases`, deliberately not
`dive_start`). The only missing piece was ever the button.

It also retires a false affordance. The phone speaker is inaudible at poolside, so the race-start
horn cues nobody — and because it blares *before* `writeCmd('START')`, it would have made an honest
GO stamp **negative** and thus rejected. Removing it is what makes the marker measurable.

## Output
- `POST /process` accepts an optional `go_signal_s` form field and threads it into `PhaseContext`.
- A `GO` button on `bleState === 'recording'` and `'videoRecording'`, silent, re-pressable.
- The race-start sequence defaults **off** for every user, with the code left intact.
- `reaction_time` fills on newly recorded sessions. **No backfill is possible** — see B4.
</objective>

<grounded_facts>
Measured from both trees on 2026-08-29. **These supersede CONTEXT and the 75-04 docs where they
disagree.**

### G6 — The clock correlation already exists. Only the button was ever missing.
`api.py:1160` and 75-04's CONTEXT D13 both claim phone↔encoder clock sync is deferred. It is not.
`RecordScreen.js:445-447` computes it and has since Phase 47:
```js
const elapsedUs   = (deviceNowUs - sessionStartUs + 2**32) % 2**32;  // uint32 wrap-safe
const startPhoneMs = phoneNowMs - elapsedUs / 1000;                  // encoder t=0, phone clock
```
So `go_signal_s = (goPressPhoneMs − sessionStartPhoneMs) / 1000`. Both api.py's docstring and this
plan's SUMMARY must correct the stale claim.

### G7 — META lands at retrieval, so the conversion cannot happen at press time.
The 8-byte META reply arrives *after* the swim, inside `runRetrieval`. At GO-press time
`sessionStartPhoneMs` is still `null`. **Stash raw `Date.now()`; convert at META**, where
`startPhoneMs` is already a local variable in scope (`:446`).

### G8 — `uploadAndProcess` cannot read React state. Use the established ref-mirror.
`uploadAndProcess` is a `useCallback` whose dep array deliberately excludes video state;
`RecordScreen.js:105` documents the workaround already in use — *"mirror of videoUri —
uploadAndProcess reads it without a dep"*. `videoStartPhoneMs` is `useState` and survives from
`onCameraReady` to the results render, so state persistence is not the problem; **dep-array
reachability is**. Two refs, no new state, no dep-array change.

### G9 — Ordering is already correct: META precedes upload.
`stopRecording`/`stopVideoRecording` → `runRetrieval` → META handler (`:429`) → `DUMP` →
`finishRetrieval` → `saveCSV` → `uploadAndProcess`. The converted value is therefore always ready
before the request is built. No new sequencing is required.

### G10 — Disabling the horn is NOT just a default flip.
`startSequencePrefs.js` reads `v === null ? true : v === '1'`. Flipping the default only affects
users who never touched the toggle. **Anyone who explicitly switched it on has `'1'` in SecureStore
and would keep hearing the horn** — i.e. the users most likely to have opted in are the ones the
fix would miss. The key must be bumped so every stored value is discarded exactly once.

### G11 — A test already asserts the state this plan changes.
`tests/test_api.py:117` — `assert phases["go_signal_s"] is None  # no GO button yet`. It still
passes (the field is optional and absent there), but its comment becomes false and the populated
path has no coverage at all.

### G12 — "Retrieve from Device" is a legitimate no-GO path.
`runRetrieval` is also reachable straight from the `ready` state for sessions the swimmer recorded
with the device's own button. No GO press exists on that path; the field must simply be omitted.
Same for any session where the coach never pressed GO (D8, open question 8).

## B4 — the discontinuity this plan creates, and cannot avoid
No stored session carries a GO time and none can be reconstructed, so `reaction_time` fills **only
for sessions recorded after this ships**. All 99 existing sessions stay null forever. Any surface
that renders it — and `phaseBaseline.js` in particular, which compares against the athlete's last
5 same-stroke sessions — will see a metric that simply begins one day. Worth a one-line note
wherever it renders; that note is **not** part of this plan.

## Deploy ordering (not a boundary — a real constraint)
