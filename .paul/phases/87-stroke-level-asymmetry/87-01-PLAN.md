<objective>
## Goal
Make the **individual arm stroke** a first-class, stored unit for freestyle and backstroke —
`metrics_json.strokes` alongside the existing `metrics_json.cycles` — and derive the
alternating-side asymmetry numbers (tempo, distance, peak velocity) plus per-side consistency
into `metrics_json.session`. Backfill the stored library so the free/back sessions have it.

## Purpose
A freestyle cycle is **two arm strokes**, and the pipeline collapses them before anything can look
at them. A coach cannot see that a swimmer is lopsided — arguably the most common freestyle fault
a 1-D encoder can actually observe — because the data that would show it is discarded inside
`_pair_boundaries`.

**Measured during planning (read-only probe, 2026-08-31, `scratch/_asym_probe.py`):** across the
23 usable annotated freestyle sessions the odd/even contrast is **6.1% median in tempo**
(0.4–29.4%) and **9.4% median in distance per stroke** (0.1–33.2%), clearing the within-side noise
floor (t>2) on 7/23 and 9/23 respectively. Unlike 83-03's cut MAD classifier, this **separates**:
some sessions sit at 0.4%, others at 30%.

## Output
- `metrics.segment_strokes` (new, pure) + a `strokes` key on `compute_session_metrics`'s return
- 7 new session-level keys (3 asymmetry, 4 per-side CV)
- `annotations.annotation_to_overrides` emits `stroke_bounds` from the coach's raw marks
- `api.py` persists `strokes` at both write sites
- `tools/backfill_strokes.py` (new, additive-only), dry-run then applied by the user
</objective>

<decisions>
Settled with the user during planning, 2026-08-31. Recorded because several override what a
reader would otherwise assume from the surrounding code.

**D1 — `metrics_json.strokes`, top-level, beside `cycles`.** User: *"wherever you stored the per
cycle data, store it there."* Strokes are a **segmentation product of `compute_session_metrics`**,
exactly like `cycles`: same call, same two write sites. 83-02's argument for burying `kick_bands`
inside `phases` does not transfer — that object is built by a *different* function
(`compute_phases`) at *three* write sites and could go stale against a re-annotated window.
`strokes` is produced in the same breath as `cycles`, so if one is fresh so is the other. No
`SCHEMA_VERSION` bump: that version lives inside `phases`, and `cycles` has never carried one.

⚠ **The user's premise when answering was that stroke segmentation is already stored. It is not.**
`metrics_json.cycles` is already the *paired* product; the coach's raw marks live in a different
table (`session_annotations.stroke_marks_s`) that the report card never queries; and the auto
boundaries are built and discarded inside `_pair_boundaries` (metrics.py:388-397). This plan has
to make the backend *emit* strokes, not merely re-reduce something on hand. Corrected with the
user before planning proceeded.

**D2 — Asymmetry ships on AUTO sessions too, marked only by the existing `auto` chip.** ⚠ The user
made this call *after* seeing the measurement; it is the highest-risk decision in the phase, so it
is written down rather than softened. `scratch/_asym_auto_vs_truth.py` compared auto-derived
asymmetry against the coach-mark truth on the same 23 sessions: **median error 10.2 percentage
points** against a signal whose median is 6.1%, **Pearson r = −0.06**, agreeing on only **2 of the
7** most-lopsided sessions. The auto number is not a rougher version of the truth; it is unrelated
to it. Cause is **parity, not precision**: un-paired wavelet boundaries land at **1.10× the coach's
mark count** (range 0.50–1.33) and match 88% of marks within 0.35 s, but one extra or missing
boundary **flips the A/B assignment of every stroke after it**. Build it as asked; do not add a
warning banner the user did not request.

**D3 — Sides are `A` and `B`, never left/right.** A 1-D axial encoder cannot observe which arm is
which. Fixed convention: `A` = intervals starting at even array positions of `strokes`, `B` = odd.
Values are **signed** so the sign is stable within a session and the UI can name the slower side.

**D4 — The Swimming section's usual-range strips do NOT change with the toggle.** They stay
cycle-level: their baselines are five *cycle-level* swims deep (`phaseBaseline.js`), so a
stroke-level value under a cycle-level band would be a false comparison. The two `needs_cycles`
registry specs (`sr_dps_coupling`, `dead_spot_timing`) are therefore untouched by this phase.

**D5 — Backfill is a NEW additive-only tool.** It writes exactly two things —
`metrics_json.strokes`, and the new keys merged into `metrics_json.session` — and never touches
`cycles`, `phases`, `initial_phase` or `data_quality`. Same one-key discipline as
`tools/backfill_phases.py`. The user runs it, as with every prior backfill.

**D6 — Backstroke is included, and is unverifiable.** Library census measured 2026-08-31:
freestyle 45 sessions (24 annotated), **backstroke 2 total, 0 annotated**, butterfly 29,
breaststroke 20, udk 5. Backstroke shares freestyle's code path exactly
(`MARKS_PER_CYCLE` = 2, the same paired wavelet in `SEGMENTER_BY_STROKE`), so including it costs
nothing — but no backstroke claim in this phase rests on a measurement. Confirms STATE item 10; do
not report it as validated.
</decisions>

## AC-1: Strokes are emitted for alternating-arm strokes only
```gherkin
Given a freestyle or backstroke trace with a resolvable swim window
When compute_session_metrics runs
Then its return dict carries a "strokes" list whose entries have the same field set as "cycles"
  (start_idx, end_idx, duration_s, dist_m, impulse_m, mean_vel_ms, trough_vel_ms, dead_spot_s,
   coast_fraction, arm_peak_idx, arm_peak_vel, kick_peak_idx, kick_peak_vel, arm_kick_delay_s,
   arm_kick_vel_ratio) plus stroke_num
And for butterfly, breaststroke, "im", "udk", an unknown string, or None the key is present with
  the value None — one arm entry IS one cycle there, and a second array would duplicate cycles
  and be free to drift from it
```

## AC-2: Cycle output is byte-identical — no drift
```gherkin
Given any trace and any stroke_type
When compute_session_metrics runs before and after this plan
Then result["cycles"] and every pre-existing key of result["session"] are unchanged
And the existing suite still passes at its 505 baseline with no pre-existing test modified to
  accommodate the change
```

## AC-3: Coach marks drive strokes on annotated sessions
```gherkin
Given an annotation carrying stroke_marks_s and a stroke_type whose marks_per_cycle > 1
When annotation_to_overrides runs
Then it returns "stroke_bounds" = consecutive pairs of ALL marks, not marks[0::2]
And "cycle_bounds" and every other returned key are byte-identical to before this plan
And at marks_per_cycle == 1 "stroke_bounds" is absent, since it would equal cycle_bounds
```

## AC-4: Asymmetry is signed, documented, and gated on sample size
```gherkin
Given a strokes list with at least 3 usable strokes on each side
When the session summary is built
Then session carries arm_asym_tempo_pct, arm_asym_dps_pct and arm_asym_peak_vel_pct — each
  signed as (mean A − mean B) over their mean, as a percentage — plus cv_stroke_interval_a,
  cv_stroke_interval_b, cv_stroke_dps_a and cv_stroke_dps_b
And with fewer than 3 usable strokes on either side, or no strokes at all, all seven are None
  rather than a number computed from one or two samples
```

```gherkin

  metrics_json.initial_phase, metrics_json.go_signal_s and the once-only metrics_json_auto
```

       `extract_cycle_peaks` + `_derive_item_metrics` over it. Return under a new `"strokes"` key.
