<objective>
## Goal
Add a one-tap "Record with Video" mode to the iOS app: the app commands the ESP32 to
START over BLE and starts the in-app camera together, records both through the swim,
then STOPs both, dumps + processes the tether session, and opens a playback screen where
the velocity trace is synced to the video. Sync is metadata-based, both anchors on the
phone wall-clock:

    video_origin_s = sessionStartPhoneMs − videoStartPhoneMs
      sessionStartPhoneMs : from the device META reply, clock-correlated (Phase 22-01)
      videoStartPhoneMs   : Date.now() captured by the app at recordAsync() start

The app times its own camera, so videoStartPhoneMs is exact (no creationTime guessing).
The two recordings need only OVERLAP — META + the recordAsync timestamp align them.
On playback, VelocityChart's existing markerTimeS cursor tracks the stroke and a live
m/s readout updates; a manual ±offset nudge + the in-frame 5 Hz LED correct the small,
fixed camera warm-up latency.

## Purpose
The phone-native, integrated overlay — "a screen where the overlay lives." In-app camera
keeps Swimnetics foreground (no native-Camera backgrounding), and buffer-and-dump means
BLE isn't needed during the swim anyway — so the iOS BLE/Camera conflict doesn't apply.
This screen's checkpoint validates the metadata sync on real footage, superseding the
parked 22-02 manual laptop demo (kept as a fallback).

## Output
- "Record with Video" mode in RecordScreen (BLE START/STOP + in-app camera, reusing the
  existing dump/process pipeline) → produces {velocity, sessionStartPhoneMs, videoUri,
  videoStartPhoneMs}
- New `VideoOverlayScreen.js` — pure playback: synced cursor + m/s readout + ±nudge
- expo-camera + expo-video added (NATIVE — requires an EAS build)
- Go/no-go verdict on sync accuracy + BLE-while-camera concurrency at the checkpoint
