<objective>
## Goal
Make **real GoPro-size clips actually upload, without OOMing the server**, and give the coach a clear
message when a file is too large or won't play. Three code changes + one Supabase config gate:
1. Raise the `videos` bucket file-size limit (patch_11) so Storage stops rejecting >50 MB uploads.
2. A **memory-safe** size guard in `POST /sessions/{id}/video`: reject oversized before buffering,
   and stream the accepted file to Storage from its spooled temp file instead of `await file.read()`.
3. Client-side format/size handling in `VideoPane.attach()`: reject over-cap before upload, guide on
   unplayable formats, and recommend H.264 .mp4.

## Purpose
67-01 shipped the sync mechanic but it is only usable with tiny clips. TWO gates block real footage
(CONTEXT R1, verified): `POST /video` does `await file.read()` — the whole file into RAM, OOM on a
big clip — and the `videos` bucket was created with **no `file_size_limit`** (`patch_07:59-61`), so
it inherits Supabase's ~50 MB default and rejects real GoPro clips at the Storage layer. This plan is
the honest "how robust is it" answer.

## Output

- `api.py`: `MAX_VIDEO_BYTES` + size pre-check (413) + streamed upload.
- `tests/test_api.py`: oversized-video rejection test.
- `web/components/portal/VideoPane.js`: pre-upload size check + `<video onError>` guidance + format hint.
</objective>

## Decision (delegated to me by the user): cap = 500 MB
`MAX_VIDEO_BYTES = 500 * 1024 * 1024` (524288000 bytes). A single-swim clip is ~100–300 MB at 1080p;
500 MB gives margin while bounding Storage cost. Named constant on both ends so it is trivially
adjustable. The bucket limit (patch_11) and the API constant MUST match.
